# 인수인계 — BY-332 웹 배포 + 세션 제출 실기기 검증 (2026-08-01)

전 화면 원격 웹뷰 셸 전환(BY-327 묶음)이 코드상으로는 끝났다. 남은 두 가지는 **배포 URL 확보**와
**실기기에서 세션 제출이 실제로 서버에 저장되는지 확인**이고, 둘 다 검증 환경(빌드·기기)이 있는
쪽이 이어받는 게 빠르다.

## 지금 브랜치 상태

```
dev
 └─ integration/BY-327-웹뷰-이관     ← BY-328·329·330·331·334 + 팀원 BY-335(#21) 모두 반영됨
     └─ feature/BY-333-네이티브-셸-전환  ← PR #25 (OPEN, base=integration)
```

`integration`이 dev로 가는 최종 PR은 PR #25가 머지된 뒤에 만든다. 순서를 바꾸면 셸 전환이 빠진
채 웹 화면만 dev에 들어간다.

## 아키텍처 한 줄 요약 (이게 바뀐 부분이다)

**네이티브는 껍데기만 남았다.** 탭 바 + 화면 스택 + 카메라 권한 게이트 + 익명 등록 + 웹뷰 호스트가
전부다. 홈·기록·설정·온보딩·세션은 전부 `apps/web`이고, 앱은 `app.json`의
`extra.webBaseUrl`이 가리키는 **원격 HTTPS 주소**를 웹뷰로 연다.

- 웹을 고치면 **웹만 배포하면 앱에 즉시 반영된다** — 스토어 심사 불필요.
- 앱 번들에 웹 자산을 넣던 구조(로컬 lighttpd 서버, `assets/web-dist`, `sync-web`)는 전부 삭제됐다
  ([ADR 0005](../adr/0005-bundled-web-assets-over-localhost-server.md)는 Superseded).
- 네이티브 화면과 웹 화면 사이의 대화는 브리지 메시지 5종뿐이다
  ([packages/types/src/bridge.ts](../../packages/types/src/bridge.ts)).

# 1. BY-332 — 웹 배포 파이프라인 + 배포 URL

## 왜 이게 먼저인가

`webBaseUrl`이 비어 있으면 앱은 모든 탭에서 "화면을 불러오지 못했어요" 폴백만 띄운다. **이 값이
채워지기 전까지는 아래 2번(세션 제출 검증)도 시작할 수 없다.** 로컬 dev 서버 주소로 임시 검증은
가능하지만(§2-B), 최종 확인은 실배포 URL로 해야 한다.

## 요구 조건 — 이걸 못 지키면 세션 화면이 죽는다

정적 호스팅이면 어디든 되지만, 아래 넷은 협상 불가다.

| 조건 | 왜 | 확인 방법 |
|---|---|---|
| **HTTPS 필수** | `getUserMedia`는 secure context에서만 동작한다. http면 카메라가 안 열리고 세션이 아예 시작되지 않는다 | 브라우저 주소창 자물쇠 |
| **`.wasm` → `application/wasm`** | MediaPipe가 `WebAssembly.instantiateStreaming`으로 로드한다. MIME이 틀리면 조용히 fallback하거나 실패한다 | `curl -I <url>/mediapipe/wasm/<파일>.wasm` |
| **`/models/*.tflite`가 200 + 바이너리** | SPA fallback을 `/*` → `index.html`로 걸어두면 모델 요청에 **HTML이 돌아온다.** 에러도 안 나고 감지만 죽는다 — 가장 찾기 어려운 실패다 | `curl -I <url>/models/efficientdet_lite0_int8.tflite` → `content-type`이 `text/html`이면 잘못된 것 |
| **SPA fallback은 라우트에만** | `/home`·`/records`·`/settings`·`/room/1`은 새로고침으로 직접 들어올 수 있어야 한다(웹뷰가 매번 그 URL로 로드한다) | `curl -I <url>/room/1` → 200 |

**추가로 넣을 것: COOP/COEP.**

```
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp
```

멀티스레드 wasm 경로를 여는 헤더다. ADR 0005가 서버를 고를 때 이 헤더 지원을 기준으로 삼았던
이유가 그대로 유효하다 — 없으면 Vision 추론이 단일 스레드로 떨어지고, 그 상태로 성능을 재면
"WebView가 느리다"는 잘못된 결론이 나온다(ADR 0003의 네이티브 전환 트리거를 잘못 당길 위험).

⚠️ COEP를 켜면 **cross-origin 리소스가 전부 차단된다.** 설정 → 문의하기의 구글 폼 iframe이
여기 걸린다. 켠 뒤 문의하기 화면을 반드시 확인하고, 깨지면 그 경로만 `credentialless`로 완화하거나
문의하기를 외부 링크로 돌린다.

## API 호출은 웹에서 나가지 않는다 — 헷갈리기 쉬운 부분

웹 페이지는 HTTPS인데 백엔드는 `http://52.78.219.53:8080`이다. 브라우저 규칙대로면 mixed content로
막힌다. **그래서 세션 제출만 네이티브가 대신 쳐 준다** — 웹이 `submit-session` 메시지로 완성된
요청 본문을 넘기고, 네이티브 `fetch`가 POST한 뒤 `submit-result`로 돌려준다
([apps/mobile/lib/sessionSubmitRelay.ts](../../apps/mobile/lib/sessionSubmitRelay.ts)).

- **홈·기록의 통계 조회는 이 우회가 없다.** 웹에서 직접 `fetch`한다. 즉 **백엔드에 HTTPS가
  붙거나 CORS 허용이 열리기 전까지 홈·기록의 실데이터는 실패한다.** 배포 후 홈이 비어 보이면
  버그가 아니라 이것일 가능성이 높다 — 먼저 devtools Network를 본다.
- 근본 해법은 백엔드에 도메인 + HTTPS를 붙이는 것이다. 그때 `app.json`의
  `NSAllowsArbitraryLoads`와 `usesCleartextTraffic`도 같이 걷어낸다(심사 전 필수).

## 배포 후 할 일

1. `apps/mobile/app.json`의 `extra.webBaseUrl`에 배포 URL을 넣는다. **커밋 기본값은 빈 문자열**이니
   실제 값을 커밋하는 건 이때가 처음이다.
2. 위 표의 `curl -I` 네 줄을 실제로 돌려 붙인다 — PR 본문에 출력 그대로 넣으면 리뷰가 빨라진다.
3. 앱을 다시 열어 탭 3개가 뜨는지 확인. 여기까지 되면 §2로 넘어간다.

# 2. 실기기 세션 제출 검증

## 무엇을 확인하는가

**세션이 끝난 뒤 서버에 실제로 저장되는가** 하나다. 화면상으로는 결과가 잘 나오는데 저장만 안 되는
실패가 가능한 구조라(제출은 브리지를 타고 나간다) 눈으로만 보면 놓친다.

## 검증 순서

1. 앱 실행 → 홈 → **집중 시작**
   - 카메라 권한 시트가 뜬다(네이티브가 띄운다). 거부하면 권한 안내 화면으로 간다 — 이것도 정상 경로다.
   - 허용 후 가이드(G1~G5) → **집중 시작하기** → 세션 화면으로 넘어가야 한다.
   - ⚠️ 여기서 홈으로 튕기면 그건 BY-334에서 고친 히스토리 경합의 회귀다. 바로 보고.
2. **1분 이상** 세션을 돌린다(1분 미만은 미달 종료 경로로 빠져 저장되지 않는다 — 의도된 동작).
   중간에 자리를 비우거나 폰을 들어 비공부 이벤트를 몇 개 만든다.
3. 화면 안의 **종료** 버튼으로 끝낸다.
   - "저장 중..."이 잠깐 뜨고 → 결과 화면(S4)으로 넘어가면 성공이다.
   - "다시 제출" 버튼이 보이면 **제출 실패**다. 눌러서 재시도되는지도 같이 본다.
4. 결과 화면의 **확인** → 네이티브 홈 탭으로 돌아와야 한다(웹 홈이 웹뷰 안에 열리는 게 아니라,
   모달이 닫히면서 탭이 드러나는 게 맞는 동작이다).
5. **기록 탭에서 방금 세션이 보이는지 확인** — 이게 진짜 검증이다. 여기 안 보이면 저장 실패다.
   (단, 홈·기록 조회는 위에서 말한 CORS/HTTPS 이슈에 걸릴 수 있으니, 안 보이면 서버 DB나
   API를 직접 한 번 확인해 저장 자체가 됐는지 갈라 본다.)

## Android 추가 확인

- 세션 중 **하드웨어 뒤로가기가 먹히지 않아야 한다.** 먹히면 웹뷰가 파괴되면서 측정한 시간이
  통째로 사라진다 — 그래서 일부러 막아 뒀다.
- 반대로 **로딩 중이거나 "화면을 불러오지 못했어요"가 뜬 상태에서는 뒤로가기가 되어야 한다.**
  둘 다 막으면 나갈 방법이 없어진다. 두 방향 다 확인.

## iOS 추가 확인

- 설정·기록에서 **가장자리 스와이프 뒤로가기**가 동작한다(웹뷰 히스토리를 되돌린다).
- 세션 화면에서는 스와이프로 빠져나가지지 않는다(새로 로드된 라우트라 히스토리가 비어 있다).

## 실패했을 때 어디를 보는가

| 증상 | 1순위 원인 | 확인 |
|---|---|---|
| 전 탭이 "화면을 불러오지 못했어요" | `webBaseUrl` 미설정/오타 | dev 빌드면 폴백 화면에 `(dev) app.json extra.webBaseUrl 미설정`이 같이 뜬다 |
| 세션 화면은 뜨는데 카메라가 안 켜짐 | secure context 아님(http) 또는 OS 권한 거부 | 주소가 `https://`인지, OS 설정에서 카메라 권한 상태 |
| 감지가 아무것도 안 잡힘 | `/models/*.tflite`가 HTML로 서빙됨 | §1의 `curl -I` |
| "다시 제출"이 계속 뜸 | 브리지 relay 실패 또는 서버 4xx/5xx | Safari 웹 인스펙터(iOS 16.4+, dev 빌드는 `webviewDebuggingEnabled`가 켜져 있다) / Metro 콘솔 |
| 결과 확인을 눌러도 탭으로 안 나옴 | `navigate-home` 미수신 | Metro 콘솔에 브리지 로그 |
| 탭 눌렀는데 크롬이 열림 | 오리진 판정 실패 | `webBaseUrl` 오리진과 실제 로드 URL 오리진이 같은지 |

**웹뷰 안을 들여다보는 법**: iOS는 Mac Safari → 개발자 메뉴 → 기기 이름 → 해당 웹뷰.
Android는 Chrome `chrome://inspect`. dev 빌드에서만 노출된다.

# 3. 배포 URL 없이 먼저 검증하고 싶다면 (§2-B)

`webBaseUrl`에 로컬 Vite dev 서버 주소를 넣으면 된다. 자세한 절차(안드로이드 `adb reverse`,
iOS는 mkcert HTTPS 필요, AP isolation 환경에서는 cloudflared 터널)는
[apps/mobile/CLAUDE.md](../../apps/mobile/CLAUDE.md)의 "웹 dev 서버로 화면 띄우기" 절에 있다.

⚠️ **이 값을 커밋하지 말 것.** 남은 채 배포되면 릴리스 앱이 존재하지 않는 dev 서버를 본다.

# 4. 아직 안 한 것 (의도적으로 미룸)

우선순위 낮다고 판단해 넘긴 것들이다. 필요하면 티켓으로 올린다.

- iOS에서 홈 → 가이드 진입 후 **앞으로 가기 스와이프**로 가이드가 다시 보인다. 파괴적이지 않아 보류.
- `집중 시작` 더블탭 가드 없음 — 빠르게 두 번 누르면 메시지가 두 번 나갈 수 있다.
- U1 업데이트 안내 시트가 네이티브·웹 양쪽에 있다(중복). 어느 쪽을 남길지 미정.
- [docs/runbooks/local-dev-build.md](../runbooks/local-dev-build.md)의 web-dist 관련 절이 무효다
  (문서 상단에 배너를 달아 뒀다). 전면 개정은 배포 방식이 확정된 뒤에.
