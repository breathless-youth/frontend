# 릴리즈 기록

앱은 모든 화면을 웹뷰로 열기 때문에 앱 바이너리와 웹 배포가 각자 나간다. 이 문서는 어느 빌드가
어느 채널에 올라가 있고 무엇을 전제로 하는지, 그 조합만 남긴다. 커밋 해시나 빌드 상세 같은 원천
데이터는 EAS 빌드 기록과 GitHub Actions `Deploy web` 실행 기록에 있으니 여기에 다시 적지 않는다.

## 기록 규칙

- 스토어 제출, TestFlight·Play 내부 테스트 업로드, dev → main 머지를 한 사람이 그 자리에서
  아래 표에 한 행을 추가한다.
- 앱 빌드는 그 빌드의 커밋에 git 태그를 남긴다. iOS는 `ios/<버전>-<빌드번호>`, Android는
  `android/<버전>-<빌드번호>` 형식이다 (예: `ios/26.37.0-6`).
- 웹은 main 머지 커밋에 `web/<버전>` 태그를 달고, 그 태그로 GitHub Release 노트를 쓴다
  (예: `web/26.41.0`).
- 빌드 커밋의 원천은 EAS 기록이고 `cd apps/mobile && npx eas-cli build:list`로 확인한다.
- 비고에는 호환 여부를 판단할 때 필요한 내용만 한 줄로 적는다. 포함하거나 빠진 기능, 지원하는
  capability 정도면 충분하다.
- capability는 셸이 웹에 쿼리로 알려주는 지원 표시를 말한다 (예: `share=1`, `cameraGate=1`).

## 버전 규칙 (BY-417, 2026-09-07)

기계가 읽는 버전은 플랫폼별 `YY.WW.P` 세 자리 정수다.

| 자리 | 뜻                                             |
| ---- | ---------------------------------------------- |
| `YY` | ISO 주 기준 연도 두 자리 (2026년이면 `26`)     |
| `WW` | ISO 8601 주차 (월요일 시작, 1~53)              |
| `P`  | 그 주차 안에서 몇 번째 릴리즈인지 (0부터 센다) |

- **원천은 파일 두 개다.** 앱은 `apps/mobile/app.json`의 `expo.version`, 웹은 `apps/web/package.json`의 `version`. 두 값은 릴리즈 PR(`dev` → `main`)에서 올린다.
- **`WW`와 `P`에 0을 채우지 않는다.** `27.1.0`이지 `27.01.0`이 아니다. iOS는 버전 문자열을 정수 세그먼트로 비교해서 앞자리 0이 안전하지 않다.
- **주차가 바뀌면 `P`는 0부터 다시 시작한다.**
- **연말에는 `26.53`과 `27.1`이 섞인다.** ISO 주 기준 연도라 2027-01-01(금)은 아직 `26.53`이고 2027-01-04(월)부터 `27.1`이다. 이때 `27.1`이 더 최신이다.
- **앱의 `P`는 그 주차의 몇 번째 스토어 제출인지**를 뜻하고 EAS 빌드 번호와 다르다. EAS 번호는 실패한 빌드에도 오른다. 빌드 번호는 `eas.json`의 `appVersionSource: remote`로 EAS가 관리하며 `app.json`에 `buildNumber`·`versionCode`를 넣지 않는다.
- **웹의 `P`는 그 주차의 몇 번째 `main` 배포인지**를 뜻한다.

### 올리는 법

릴리즈 PR을 열기 전에 `dev`에서 저장소 루트에서 돌리고 그 결과를 커밋해 PR에 포함한다. 스크립트는 현재 브랜치의 값을 읽으므로 다른 브랜치에서 돌리면 CI 검사가 거부하는 값이 나온다. 웹만 나가는 주는 `--web`, 앱도 제출하는 주는 `--app`을 더한다.

```bash
pnpm release:bump --web          # 웹만 배포하는 주
pnpm release:bump --web --app    # 앱도 제출하는 주
```

스크립트(`scripts/bump-version.mjs`)가 오늘 날짜의 ISO 주차를 계산해, 현재 값이 같은 주차면 `P + 1`을 아니면 `YY.WW.0`을 쓴다. 값을 손으로 고치지 않는다.

### CI 검사

base가 `main`인 PR에서만 `ci.yml`의 `version-check` job이 `scripts/check-version.mjs`로 검사한다.

- 두 값이 `YY.WW.P` 형식이어야 한다.
- 웹 버전은 직전 `main`보다 **커야** 한다.
- 앱 버전은 직전 `main`보다 **작지만 않으면** 된다. 앱을 제출하지 않는 주를 허용하기 위해서다.

### 사용자에게 보이는 라벨

설정 화면의 "버전 정보" 행은 앱 버전과 웹 버전을 합쳐 한 줄로 보여준다(`apps/web/src/features/settings/settingsInfo.ts`의 `appVersionLabel`).

- 같은 주차면 `YY.WW.<A|I><앱 P>.<웹 P>` 한 표기로 합친다. 예를 들어 Android 앱 `26.37.2`와 웹 `26.37.5`는 `26.37.A2.5`가 된다.
- 주차가 다르거나 플랫폼을 판별할 수 없거나 앱이 구형식이면 `26.36.3 / 26.37.0`처럼 나란히 적는다.
- 앱은 2주에 한 번쯤 나가고 웹은 매주 나가므로, 앱이 안 나간 주에 나란히 표기가 보이는 것은 정상이다.
- 앱 버전이 없는 브라우저 단독 접속에서는 웹 버전만 보여준다.

### 전환

- 전환은 다음 스토어 제출부터 적용한다. 첫 값은 릴리즈하는 주차의 `YY.WW.0`이고, 릴리즈 PR에서 `pnpm release:bump --web --app`으로 정한다.
- Remote Config의 `latest_version`은 새 빌드가 스토어에 실제로 노출된 뒤에 새 형식으로 게시한다(아래 "최소 지원 버전 정책"의 절차). 먼저 게시하면 기존 사용자에게 아직 받을 수 없는 버전의 권장 업데이트가 뜬다. `min_supported_version`은 이번에 바꾸지 않는다.
- CalVer 값은 기존 `^\d+\.\d+\.\d+$` 검사를 그대로 통과하고 숫자 세그먼트 비교에서 `1.0.2`보다 크므로, 강제·권장 업데이트 판정 코드는 손대지 않는다.

## 최소 지원 버전 정책 (BY-586, 2026-09-04)

- **원천은 prod Firebase 프로젝트(`focusmakers-prod`)의 Remote Config `min_supported_version`이다.** 문자열 `x.y.z`. 앱은 부팅 시 지난 실행에서 받아 둔 값을 활성화해 `expo.version`(네이티브 앱 버전)과 비교하고, 낮으면 웹뷰 대신 OS 알림창으로 막는다(`apps/mobile/lib/forceUpdate.ts`·`forceUpdateAlert.ts`).
- **반영 시점은 "다음 접속"이다.** 접속은 콜드 스타트, 또는 30분 이상 백그라운드에 있다가 돌아온 때다. 앱을 켤 때는 fetch 최소 간격을 무시하고 서버 값을 새로 받아 최대 1.5초 기다린 뒤 판정한다. 그 안에 받으면 강제 대상은 홈이 뜨기 전에 막히고, 늦으면 지난 값으로 먼저 판정해 스플래시를 걷은 뒤 새 값이 오면 다시 판정한다(`apps/mobile/lib/forceUpdate.ts`). 30분 이상 백그라운드 뒤 복귀 때도 서버 값을 새로 받아 다시 판정한다(`apps/mobile/lib/updateOnConnect.ts`). 그래서 게시 직후 다음 접속에 강제·권장 모두 걸린다. 앱을 쓰는 중에는 끼어들지 않고(실시간 수신 없음), 공부 세션 중이면 세션이 끝난 뒤에 적용한다. 받기에 실패하면 지난 값으로 판정한다. 이 동작은 그 다음 바이너리부터고, 26.42.0 이하 바이너리는 예전처럼 "다음 실행"(최대 1시간 + 재실행 1회)에 걸린다.
- **값을 못 읽으면 막지 않는다(fail-open).** 형식이 `x.y.z`가 아니거나 비어 있거나 활성화가 1초 안에 끝나지 않으면 통과한다. 그러니 값은 반드시 세 자리 숫자 버전으로 넣고 게시한다.
- **올리는 절차**: 스토어 심사 통과 후 → Firebase 콘솔 prod → Remote Config → `min_supported_version` 값 변경 → 변경사항 게시. dev 프로젝트에서 같은 값으로 먼저 리허설한다. 절대 현재 스토어 최신 버전보다 높게 넣지 않는다(전원 차단).
- **플랫폼별로 다르게 줄 때**는 키를 나누지 않고 콘솔 조건을 쓴다: 조건 탭에서 "적용 대상: 앱"으로 `iOS 앱`·`Android 앱` 조건을 만들고, `min_supported_version`에 "새 조건에 대한 값 추가"로 각각 값을 넣는다. 기본값 `1.0.0`은 어느 조건에도 안 걸릴 때의 안전값으로 남긴다. 앱 코드는 같은 키 하나만 읽으므로 변경이 없다.
- **구버전 바이너리(BY-586 이전 빌드, iOS 1.0.1(2)·Android 1.0.2(5) 이하)**는 네이티브 게이트가 없어 웹 `apps/web/src/features/force-update/version.ts`의 상수 `MIN_SUPPORTED_VERSION`으로만 막을 수 있다. 그 바이너리를 막아야 할 때는 상수를 올리고 웹을 배포한다. BY-586 이후 바이너리는 웹뷰 URL에 `nativeUpdateGate=1`을 붙여 웹 게이트를 건너뛴다.
- **알림창 문구도 콘솔에서 바꿀 수 있다.** 같은 프로젝트의 `force_update_title`·`force_update_message`·`force_update_button`(string). 키가 없거나 비어 있으면 앱에 들어 있는 기본 문구(BY-533 카피)를 쓰므로 만들지 않아도 된다. 플랫폼별 문구는 위와 같은 조건으로 나눈다. 반영은 역시 "다음 접속".
- BE 최소 버전 API 경로(BY-535·536·579)는 이 정책으로 대체됐다.
- **권장 업데이트는 같은 프로젝트의 `latest_version`이다.** 앱 버전이 이 값보다 낮으면(막히지는 않을 때) 홈 위에 "나중에"가 있는 알림창을 최신 버전당 한 번 띄운다(`apps/mobile/lib/recommendedUpdateAlert.ts`). 출시 때마다 올리는 값이라 `min_supported_version`과 분리한다: 스토어 심사 통과 후 → `latest_version` = 새 버전 → 게시. iOS 단계적 출시 중이라 스토어에 아직 안 보이는 사용자도 있을 수 있는데 "나중에"가 있으니 무해하다. 기본값 `0.0.0`은 아무에게도 띄우지 않는다. 플랫폼별로 버전이 다르면 콘솔 조건(플랫폼·"앱 버전 <")으로 값을 갈라 준다. 문구는 `recommended_update_title`·`recommended_update_message`·`recommended_update_later_button`·`recommended_update_confirm_button`(string, 선택)으로 콘솔에서 바꿀 수 있고 없으면 앱 초안 문구다.

### 백엔드 (순서 1, 2, 3)

- 백엔드는 ① 만들기·내 그룹·그룹 홈 ② 공개 그룹·신청 ③ 초대·멤버 관리 ④ 공부방 STOMP ⑤ 그룹 푸시 ⑥ 신고·차단 순서로 dev에 올라온다(BY-1124).
- 실기기 확인표는 로컬 계획 문서 `2026-11-03-group-rooms-p7-measure-release.md`의 Task 4에 있고, 결과는 밤 작업 결과 페이지에 남긴다.
- 푸시 `link` 값은 차이 목록 `2026-11-03-swagger-gaps.md`의 G3 표를 따른다.
- 옛 앱은 그룹 경로를 부르지 않으므로 그룹 API는 웹보다 먼저 운영에 나가도 된다.
- 신고 Slack 채널 설정값이 비어 있으면 신고 알림이 나가지 않으므로, 운영 배포 전에 채널과 담당자를 정해 넣는다.

### 웹 배포 (순서 4)

- 하위 계획 PR은 `[feat] BY-1125 제목`으로 `dev`에 머지한다.
- 웹은 `main` 머지 커밋에서 `Deploy web`이 돌아 배포되고, 그 커밋에 `web/<버전>` 태그를 단다.
- dev → main `[release]` PR은 ruleset `protect-main-dev` 때문에 작성자가 아닌 팀원 1명의 승인이 있어야 머지된다.
- 작성자는 자기 PR을 승인할 수 없으므로 PR을 열 때 승인할 사람을 함께 정한다.
- `groupRooms=1`이 없는 지금 바이너리에는 지금 소셜 홈과 숫자 4자리 초대코드 흐름이 그대로 보인다.

### 법적 문서 (순서 5)

- 공지는 시행 7일 전부터 하고, 이용자에게 불리하거나 권리에 중대한 영향을 주는 변경이면 시행 30일 전부터 한다(개인정보처리방침 15절, 이용약관 제3조).

- 시행일은 공지일에 7일 또는 30일을 더한 날이고, 순서 6의 스토어 출시와 순서 7, 8의 강제 업데이트는 시행일보다 앞설 수 없다.

### 스토어 제출 (순서 6)

- 스토어 개인정보 표시는 `privacy-policy-group-rooms.md` 5절의 결정대로 바꾼다.
- 제안: 심사를 통과해도 바로 출시하지 않고 App Store는 수동 출시, Play는 관리형 게시로 두었다가 시행일 이후에 출시한다.
- 앱 버전은 위 "버전 규칙"대로 올리고, 순서 7과 8에 넣는 값은 이 버전이다.
- 새 바이너리는 `groupRooms=1`을 항상 붙이고 심사는 운영 서버로 하므로, 순서 3의 그룹 API와 순서 4의 웹이 운영에 나간 뒤에만 심사에 올린다.
- 앱은 출시 뒤 이 표시를 지울 수 없으므로, 그룹 화면을 막아야 할 때는 `groupRooms=1`을 무시하는 웹을 배포해 되돌린다.
- 심사 메모에는 마이크를 쓰는 화면까지 가는 길(그룹을 혼자 만들고, 그 그룹의 공부방에 들어가 마이크를 누른다)을 적는다.
- Play Console에 올린 뒤 지원 기기 목록의 차이를 보고, 마이크(`android.hardware.microphone`)가 필수로 잡혀 빠지는 기기가 있는지 확인한다.

### 강제 업데이트 (순서 7, 8)

- `latest_version`을 먼저 게시하고 `min_supported_version`은 그 뒤에 게시한다.
- Play 단계적 출시가 100%가 되기 전에 `min_supported_version`을 올리면 아직 새 버전을 받을 수 없는 사용자가 막히므로, 100%가 된 뒤에 올린다.
- 스토어에 새 버전이 보이기 전에 `min_supported_version`을 올리면 아직 받을 수 없는 버전 때문에 모두가 막힌다.
- 한 스토어만 먼저 열리면 그 플랫폼 조건(`iOS 앱` 또는 `Android 앱`)에만 값을 올리고, 다른 스토어가 열린 날 그 플랫폼 조건을 올린다(위 "플랫폼별로 다르게 줄 때").
- prod 프로젝트(`focusmakers-prod`)에 게시하기 전에 dev 프로젝트에서 같은 값으로 리허설한다.
- 웹 `MIN_SUPPORTED_VERSION`은 `nativeUpdateGate=1`이 없는 BY-586 이전 바이너리만 막고, 그 뒤 바이너리는 Remote Config 값으로 막힌다.
- 웹 상수는 출시 날에만 바꾸며, `version.test.ts`에 새 값 테스트를 먼저 더해 실패를 본 뒤 상수를 바꾸고 `pnpm --filter web exec vitest run src/features/force-update`로 확인한다.

### 정리 티켓 (순서 9)

- 호출이 0인지는 백엔드가 `POST /api/rooms`와 `POST /api/rooms/join` 호출 수로 확인한다.
- FE는 옛 소셜 홈 `routes/SocialHomePage.tsx`를 삭제한다.
- FE는 `routes/InviteCodeSharePage.tsx`를 삭제한다.
- FE는 `routes/InviteCodeJoinPage.tsx`에서 앱 안 숫자 4자리 입력을 삭제한다.
- FE는 `features/social-room/inviteCode.ts`와 `InviteCodeInput.tsx`를 삭제한다.
- FE는 `lib/roomApi.ts`의 `createRoom`을 삭제한다.
- FE는 `LiveRoomKind`에서 `invite`를 뺀다.
- FE는 `lib/groupRoomCapability.ts`와 `hasGroupRooms()` 분기를 삭제한다.
- 앱은 `remoteQueryParams.ts`의 `groupRooms` 표시를 삭제한다.
- 백엔드는 `POST /api/rooms`, `POST /api/rooms/join`, 숫자 4자리 코드를 삭제한다.
- 옛 흐름을 삭제하면 Meta `invite_shared`를 보내는 곳이 없어지므로, 그때 개인정보처리방침 9절의 "초대 공유 기록"을 빼도 되는지 본다.
