# 0019. Android 프로필 사진은 앱이 시스템 사진 선택기로 골라 줄인 JPEG를 웹에 넘긴다

- Status: Accepted
- Date: 2026-10-28
- Relates to: [Android 프로필 사진 네이티브 선택기 설계](../superpowers/specs/2026-10-28-BY-1059-android-profile-photo-picker-design.md), [ADR 0014](./0014-webview-video-transfer-to-native.md), [ADR 0017](./0017-android-app-lock-local-module.md), 위키 `.ai/product/specs/BY-404-룸-참여.md`

## 배경

프로필 사진은 웹이 파일 입력으로 받아 512px JPEG로 줄인 뒤 올린다. A23(Android 14, WebView 156)에서 카메라로 찍은 약 15MB 사진(8160×6120)은 웹뷰가 넘긴 `File`을 어떤 방법으로도 읽지 못했다(`NotReadableError`). 웹 코드로는 우회할 수 없어 사진 읽기를 앱이 맡는다. ADR 0014는 웹이 만든 파일을 앱으로 보내는 방향이고, 이 결정은 앱이 만든 바이트를 웹으로 보내는 첫 경로다.

## 결정

### 앱

- `apps/mobile/modules/profile-photo-picker`에 Android 전용 로컬 Expo 모듈 `ProfilePhotoPicker`를 두고 함수는 `pick()` 하나만 연다.
- `pick()`은 시스템 사진 선택기(`PickVisualMedia`, 이미지만)를 열고 고른 사진을 512px 정사각형 JPEG(품질 85)의 base64로 돌려준다.
- 사용자가 선택기를 닫으면 `null`이고, 사진을 읽지 못하거나 JPEG로 바꾸지 못하면 reject한다.
- 원본 크기를 먼저 읽고, 짧은 변이 512 이상 남는 가장 큰 2의 거듭제곱 배율로 줄여 디코드한다.
- 원본을 그대로 풀면 약 200MB라 메모리 부족으로 앱이 죽을 수 있어 줄여 디코드한다.
- EXIF 방향대로 세우고 가운데 정사각형을 잘라 512로 맞추며, 디코드와 압축은 메인 스레드 밖에서 한다.
- 방향은 없어도 되는 값이라 EXIF를 읽지 못하면 돌리지 않고 그대로 쓴다.

### 브리지

- 웹은 `pick-profile-photo`에 요청 `id`를 실어 보내고, 앱은 같은 `id`의 `profile-photo-result`로 `picked`, `cancelled`, `failed` 중 하나를 답한다.
- 앱은 모듈이 없거나 사진을 읽지 못하거나 JPEG로 바꾸지 못하면 `failed`로 답한다.
- 결과가 수십 KB라 ADR 0014처럼 조각으로 나누지 않고 메시지 하나로 보낸다.
- 웹 파서는 `picked`의 `data`가 빈 문자열이어도 받고, 쓸 수 있는 사진인지는 받는 쪽이 판정한다.
- 웹은 `failed`와 본문이 비었거나 base64로 풀리지 않는 `picked`를 모두 `UnusablePhotoError`로 끝낸다.

### 웹

- 앱은 Android에서 모듈이 있을 때만 웹뷰 URL에 `profilePhotoPicker=1`을 붙이고, 웹은 이 표시가 있을 때만 앱 선택기를 쓴다.
- 표시가 없는 옛 Android 앱과 iOS, 브라우저는 웹 파일 입력을 쓴다.
- 웹은 받은 JPEG를 다시 줄이지 않고 기존 순서(업로드 주소 받기, S3에 올리기, 등록)로 올린다.
- 사용자가 선택기를 닫으면 업로드를 하지 않고 토스트와 분석 이벤트도 보내지 않는다.
- 선택기는 권한 없이 열리므로 `android.blockedPermissions`와 매니페스트 권한은 바뀌지 않는다.

## 검토한 대안

- **웹 파일 입력 유지**: 바이트를 먼저 읽는 우회까지 시도했지만 큰 카메라 사진은 읽기 자체가 실패했다.
- **expo-image-picker**: iOS 빌드에도 새 네이티브 의존성이 들어가고, 고른 사진을 캐시 파일로 복사해 돌려줘서 512px로 줄이는 코드를 따로 써야 한다.
- **원본을 조각으로 웹에 넘기기**: 15MB 사진이 20MB 문자열이 되고, 웹뷰가 다시 디코드하면서 같은 메모리 문제를 만난다.

## 결과와 제약

- 앱은 고른 사진을 파일로 남기지 않고 메모리에서만 처리한다.
- 서버로 가는 것은 사용자가 고른 사진을 줄인 512px JPEG뿐이고, 웹 파일 입력 경로와 같다.
- 개발 로그에는 사진 본문 대신 길이만 남긴다.
- 사용자가 고르는 시간을 정할 수 없어 웹은 시간 제한 없이 응답을 기다리고, 그동안 사진 버튼에 진행 표시가 보인다.
- 앱이 답을 보내면 `picked`, `cancelled`, `failed` 어느 경우든 웹의 요청이 끝나므로, 깨진 응답 때문에 웹이 계속 기다리는 일은 없다.
- 선택기가 열린 사이 Android가 앱 화면을 다시 만들면 Expo가 늦게 온 결과를 버린다.
- 그래서 앱은 화면이 없어질 때 기다리던 선택을 취소해 `cancelled`로 답하고 선택 중 표시를 푼다.
- 이때 사용자가 고른 사진은 올라가지 않고, 다시 골라야 한다.
- A23에서 "활동 유지 안 함"을 켜고 확인한 결과, 웹뷰는 다시 만들어지지 않고 프로필 화면이 남았으며 진행 표시가 꺼지고 선택기도 다시 열렸다.
- 앱은 선택기를 한 번에 하나만 열고, 열려 있는 동안 온 요청에는 `cancelled`로 답한다.
- 모듈 빌드 설정에 `androidx.activity`를 적지만, 앱이 react-android를 거쳐 이미 싣고 있는 라이브러리라 새 의존성은 아니다.
- 네이티브 코드가 들어가 Android 앱은 다시 빌드해 출시해야 켜지고, iOS는 다시 빌드하지 않는다.
