# 0020. 그룹 공부방 소리는 영상과 같은 P2P 풀메시로 보내고, 마이크를 끄면 아무것도 보내지 않는다

- Status: Proposed
- Date: 2026-11-03
- Relates to: [ADR 0006](./0006-p2p-mesh-stomp-over-livekit.md), [ADR 0004](./0004-expo-camera-for-permission-api-only.md), 위키 `decisions/0002-social-video-p2p.md`, 위키 `product/specs/BY-1123-그룹-공부방.md` 18절과 26절, 그룹 공부방 설계 `2026-11-02-group-study-rooms-design.md`의 소리 절(`docs/BY-1125-group-rooms-design` 브랜치), 스파이크 브랜치 `spike/BY-1125-mic`

## 배경

그룹 공부방(BY-1123)은 멤버끼리 이야기할 수 있게 마이크를 쓴다. 지금 공부방은 영상만 WebRTC P2P 풀메시로 보내고(ADR 0006), 앱은 마이크 권한을 막아 두었다(ADR 0004). 소리를 P2P 메시에 더하는 일은 구조 변경이라 구현 전에 승인이 필요해서, 2026-11-03에 스파이크 브랜치에서 웹 구현을 만들어 브라우저와 기기에서 확인했다. 브라우저 확인은 마쳤지만 iPhone은 개발 서버에 HTTPS로 접속할 길이 없어 한 항목도 확인하지 못했고, Android는 한 대로 할 수 있는 일부만 확인했다. 이 초안은 확인한 사실로 정할 수 있는 것과 iPhone 확인을 기다리는 것을 구분해 적었다. 로드맵의 P5(공부방 소리)와 P6(앱 마이크 권한)은 이 결정을 따른다.

## 결정

소리는 영상 연결마다 오디오 칸 하나를 더해 보내고, 마이크를 끈 동안에는 아무것도 보내지 않는다. 아무것도 보내지 않는 방식 가운데 무엇을 쓸지는 iPhone 확인 뒤 정한다.

### 전송

- 공부방 소리는 영상과 같은 `RTCPeerConnection` P2P 풀메시로 보내고, 소리를 위한 미디어 서버나 별도 연결은 만들지 않는다.
- 연결마다 오디오 트랜시버 하나를 영상 칸 뒤에 둔다.
- 마이크 트랙은 어댑터 함수 하나가 `getUserMedia`로 얻고, 이때 `echoCancellation`, `noiseSuppression`, `autoGainControl`을 켠다.
- UI 컴포넌트는 `getUserMedia`, `RTCPeerConnection`, Web Audio 생성자를 직접 부르지 않는다.

### 협상

- offer를 보내는 쪽은 `createOffer` 전에 `sendrecv` 오디오 트랜시버가 하나만 있게 하고, 지금 마이크 트랙을 송신기에 붙인다(꺼져 있으면 `null`).
- ICE 재시작처럼 같은 연결에서 offer를 다시 보낼 때는 협상된 오디오 트랜시버를 다시 쓰고 새로 만들지 않는다.
- answer 쪽은 오디오 트랜시버를 미리 만들지 않는다.
- answer 쪽은 `setRemoteDescription(offer)` 뒤, `createAnswer` 전에 offer가 만든 오디오 트랜시버를 `sendrecv`로 바꾸고 지금 마이크 트랙을 `replaceTrack`으로 붙인다.
- `addTransceiver`로 미리 만든 트랜시버는 원격 offer의 m-line과 짝지어지지 않아서(JSEP, RFC 8829 5.10절), answer 쪽이 미리 만들면 그쪽 소리가 상대에게 가지 않는다.
- 오디오 송신기는 협상된 오디오 트랜시버(`mid`가 있고 멈추지 않은 것)에서 먼저 찾는다.
- 지금 마이크 트랙을 기억해 두고, 나중에 생기는 연결에도 offer와 answer 어느 경로로든 붙인다.
- `preferVp8`은 영상 트랜시버에만 코덱 선호를 건다(오디오 트랜시버에 영상 코덱을 걸면 `InvalidModificationError`가 난다).
- 기존 `setLocalStream`이 `getSenders()[0]`을 카메라 송신기로 쓰므로, 오디오 칸은 늘 영상 칸 뒤에 만들거나 송신기를 종류로 찾는다.
- 오디오 단계의 오류는 따로 잡아서, 소리 협상이 실패해도 영상 연결은 끊기지 않게 한다.

### 받기와 재생

- 영상 타일에 넘기는 스트림은 지금처럼 영상만 담는다.
- 상대 소리는 오디오 `ontrack`이 오는 즉시 사람별 오디오 스트림으로 따로 보관하고, 영상 알림을 기다리지 않는다.
- 오디오 트랙의 mute, unmute, ended 이벤트는 영상 타일을 바꾸지 않는다.
- 타일의 `<video>`는 계속 `muted`이고, 소리는 오디오 재생기만 낸다.
- 사람별 음량과 소리 끄기는 `createMediaStreamSource`에서 `GainNode`를 거쳐 `destination`으로 가는 Web Audio 경로로 한다.
- iOS WebKit은 미디어 요소의 `volume`을 바꾸지 못해서, 사람별 음량에 미디어 요소 `volume`을 쓰지 않는다.
- Chrome에서는 같은 스트림을 음소거한 `audio` 요소에도 붙여야 Web Audio에 소리가 들어와서 그 요소를 함께 붙인다.
- 말하는 중 표시는 `AnalyserNode`로 읽은 소리 크기로 정한다.
- 재생과 `AudioContext` 재개는 사용자의 탭 안에서 시작한다(WKWebView는 미디어 재생에 사용자 제스처가 필요하고 `AudioContext`는 `suspended`로 시작한다).
- 이 재생 방식은 Chrome에서만 확인했고, iPhone과 Android WebView에서는 확인하지 못했다.

### 마이크 끄기

- 마이크를 끄면 아무것도 보내지 않는다.
- TURN 서버의 한계가 초당 패킷 수라서, 2026-11-03에 사용자가 비용을 이유로 이 방향을 골랐다.
- 끄고 켤 때 다시 협상하지 않는다.
- 끈 동안에는 마이크 트랙의 `enabled`를 켜지 않아서, 끄는 방식을 바꾸는 순간에도 마이크 소리가 나가지 않게 한다.
- 아무것도 보내지 않는 방식은 `보내지 않기`와 `트랙 멈추기` 가운데 iPhone 확인 뒤 고르며, 그때까지 열린 항목이다.

| 방식          | 끌 때                                                                    | 켤 때                                                |
| ------------- | ------------------------------------------------------------------------ | ---------------------------------------------------- |
| `보내지 않기` | 모든 오디오 송신기에 `replaceTrack(null)`을 하고 캡처는 열어 둔다        | 같은 트랙을 `replaceTrack`으로 다시 붙인다           |
| `트랙 멈추기` | `replaceTrack(null)` 뒤 마이크 트랙을 `stop()`해 OS가 마이크를 놓게 한다 | `getUserMedia`로 새 트랙을 얻어 모든 송신기에 붙인다 |

Chrome과 Galaxy S21에서 확인한 차이는 아래와 같다.

| 확인한 것                                | `보내지 않기`   | `트랙 멈추기`                  |
| ---------------------------------------- | --------------- | ------------------------------ |
| 끈 동안 상대가 받은 패킷 (Chrome)        | 0 pkt/s         | 0 pkt/s                        |
| 끈 뒤 Android 마이크 표시                | 남았다 (3/3)    | 사라졌다 (3/3)                 |
| 다시 켜는 시간 (Android)                 | 2, 2, 2ms       | 293, 292, 313ms                |
| 다시 켤 때 권한 창 (Android)             | 뜨지 않았다     | 뜨지 않았다                    |
| Android 앱의 오디오 출력 스트림          | 유지됐다        | 켜고 끌 때마다 새로 만들어졌다 |
| iPhone 주황 점, 소리 경로, 배경음 이어짐 | 확인하지 못했다 | 확인하지 못했다                |

### 개인정보

- 소리는 P2P로 상대 멤버에게만 가고, TURN을 거치는 연결에서도 TURN은 암호화된 데이터를 거쳐 보내기만 한다.
- 녹음과 저장 기능을 두지 않고, 소리를 앱 서버로 올리는 경로도 두지 않는다.
- 로그와 분석 이벤트에는 소리 데이터를 남기지 않는다.

## 측정 결과

### 브라우저

스파이크 코드를 저장소의 `playwright-core` 1.63으로 띄운 headless Chrome에서 가짜 미디어 장치로 확인했다. 실제 `createPeerMesh` 두 개를 가짜 신호 채널로 이었고, 개발 서버 밖으로 나가는 요청(`/api`, `/ws`, 분석)은 모두 막아 백엔드에 닿지 않았다. 소리 크기는 440Hz 테스트 소리의 RMS이고, 테스트 소리의 계산값은 약 0.18이다.

| 확인한 것                         | 결과                                                                                                  |
| --------------------------------- | ----------------------------------------------------------------------------------------------------- |
| 협상                              | offer 쪽과 answer 쪽 모두 `0:video`, `1:audio`가 `sendrecv`로 협상됐고 양쪽 `senders[0]`이 영상이었다 |
| 양방향 소리                       | answer 쪽이 들은 크기는 0.176에서 0.178, offer 쪽은 0.177에서 0.178이었다                             |
| answer 쪽 단계를 끈 대조 실험     | answer 쪽 오디오 칸이 송신 트랙 없이 `recvonly`로 남았고 offer 쪽은 0을 들었다                        |
| 영상을 보내지 않는 상대           | 타일 알림이 없어도 소리는 따로 와서 0.177~0.178로 들렸다                                              |
| 타일 알림                         | 영상 트랙만 실렸다                                                                                    |
| `web-audio`만                     | 받은 크기와 나간 크기가 모두 0이었다                                                                  |
| `web-audio`와 음소거 `audio` 요소 | 받은 크기와 나간 크기가 0.178이었고, 음량 50%에서 나간 크기가 0.089, 소리 끄기에서 0이었다            |
| `element`                         | 0.177이었다                                                                                           |
| 가짜 마이크                       | `getSettings()`에서 `echoCancellation`, `noiseSuppression`, `autoGainControl`이 모두 켜져 있었다      |
| 꺼진 채 끄는 방식 바꾸기          | 어느 방향으로 바꿔도 `enabled = true` 쓰기가 없었다                                                   |
| 다시 켜는 시간                    | 같은 트랙은 0ms, 새 트랙은 16~24ms였다                                                                |

보내는 쪽 오디오 통계는 아래와 같다. 페이로드는 `bytesSent` 변화량이고, 회선 추정은 여기에 RTP 헤더(`headerBytesSent`)와 패킷마다 38B(SRTP 태그 10B, UDP 8B, IPv4 20B)를 더한 값이다. RTCP와 TURN 뒤 구간은 넣지 않았고, 모두 TURN을 거치지 않은 연결에서 읽었다.

| 보내는 것                 | 페이로드      | 회선 추정             | 패킷        |
| ------------------------- | ------------- | --------------------- | ----------- |
| 테스트 소리               | 32.3~32.4kbps | 58.6kbps              | 약 50 pkt/s |
| 켠 마이크 (가짜 장치)     | 22.4~24.9kbps | 48.8kbps              | 50 pkt/s    |
| `enabled`로 끈 마이크     | 1.2kbps       | 약 27~38kbps (계산값) | 50 pkt/s    |
| `보내지 않기`로 끈 마이크 | 0             | 0                     | 0           |
| `트랙 멈추기`로 끈 마이크 | 0             | 0                     | 0           |

- `enabled`로 끈 상태의 회선 값은 조작판에서 읽은 값이 아니라 헤더를 더해 계산한 추정값이다.
- 켠 마이크 값은 가짜 장치 소리라서, 실제 목소리의 값은 기기에서 다시 확인해야 한다.

### Galaxy S21

2026-11-03 06:02~06:15에 Galaxy S21(SM-G991N, Android 15)과 개발 앱 26.45.0으로 혼자 일회용 방에 들어가 확인했다. 웹은 Mac 개발 서버를 `adb reverse`로 `http://localhost:5173`에 열어 보안 컨텍스트를 얻었고, 카메라는 끈 채였다.

- 첫 `마이크 켜기`에서 OS 권한 창이 한 번 떴고, 그 뒤 9번 켤 때는 새 트랙을 얻은 3번을 포함해 다시 뜨지 않았다.
- 허용한 뒤 마이크는 `VOICE_COMMUNICATION` 소스로 열렸고 플랫폼 에코 제거(`Acoustic Echo Canceler`)가 붙었다.
- 마이크를 열자 오디오 모드가 `MODE_NORMAL`에서 `MODE_IN_COMMUNICATION`으로 바뀌었고, WebView가 `setCommunicationDevice`로 통신 장치를 스피커로 정했다.
- `트랙 멈추기`로 마이크를 놓자 WebView가 `clearCommunicationDevice()`를 불렀고 오디오 모드가 `NORMAL`로 돌아갔다.
- 말소리가 없는 방에서 내 마이크 크기는 10번 모두 0.00이었다.

| 끄는 방식     | 끈 뒤 캡처  | 끈 뒤 `TYPE_MICROPHONE` | 끈 뒤 오디오 모드  | 다시 켜는 시간            |
| ------------- | ----------- | ----------------------- | ------------------ | ------------------------- |
| `enabled`     | 열려 있었다 | 남았다 (3/3)            | `IN_COMMUNICATION` | 0, 0, 0ms (같은 트랙)     |
| `보내지 않기` | 열려 있었다 | 남았다 (3/3)            | `IN_COMMUNICATION` | 2, 2, 2ms (같은 트랙)     |
| `트랙 멈추기` | 없었다      | 사라졌다 (3/3)          | `NORMAL`           | 293, 292, 313ms (새 트랙) |

- `TYPE_MICROPHONE`은 SystemUI가 초록 표시의 마이크 부분을 그리는 항목이다.
- 초록 점 자체는 세 방식 모두에서 켜져 있었는데, 공부방이 카메라를 열어 둔 채였기 때문이다.
- `트랙 멈추기`에서는 켜고 끌 때마다 앱의 AAudio 재생 스트림 번호가 327, 343, 359, 375로 바뀌었고, 나머지 두 방식으로 여섯 번 켜고 끄는 동안에는 327로 유지됐다.
- 이 교체가 상대 소리나 배경음에서 들리는 끊김이 되는지는 들어 보지 못해 확인하지 못했다.
- 일시정지된 방에서는 배경음이 재생되지 않아서 배경음 확인(4번)은 할 수 없었다.

## TURN과 수용량

- coturn은 Oracle Cloud 오사카 리전 Always Free A1(2 OCPU, 12GB) 한 대가 STUN과 TURN을 함께 맡는다(ADR 0006 정정).
- 송신 데이터는 월 10TB까지 무료이고, 넘는 양은 GB당 $0.0085다.
- 2026-09-04 부하 측정에서 이 서버의 한계는 대역폭이 아니라 초당 패킷 수(약 2만 개)였다.
- Opus는 20ms마다 패킷을 하나 보내 스트림마다 초당 50개를 쓰고, 영상 스트림은 약 36개를 쓴다.
- 2026-09-07부터 11-03까지 TURN 중계 비율은 연결 끝점 기준 10%, 연결 기준 약 18~20%였다(이벤트 775건).

아래 값은 6명 방에서 연결의 20%가 TURN을 거친다고 보고 부하 측정에서 얻은 패킷 한계로 계산한 추정치이며, 실제 동시 접속으로 확인한 값이 아니다.

| 소리를 보내는 방식                     | 서버 한 대의 동시 인원 추정 |
| -------------------------------------- | --------------------------- |
| 영상만 (지금)                          | 약 560명                    |
| 끈 동안에도 보냄 (`enabled`)           | 약 230명                    |
| 끄면 보내지 않음, 마이크를 켠 사람 10% | 약 490명                    |

- 끈 동안에도 보내면 동시 인원 추정이 영상만일 때의 절반 아래로 떨어져서, 끄면 아무것도 보내지 않기로 했다.
- `RTCPeerConnection`을 `bundlePolicy: "max-bundle"` 없이 만들어서, 상대가 BUNDLE을 받아들이기 전까지는 연결을 만들 때마다 오디오용 전송 경로와 TURN 할당이 하나씩 더 생긴다.
- 스파이크는 `bundlePolicy`를 바꾸지 않았고, 늘어나는 할당의 양도 측정하지 않았다.

## 검토한 대안

- **SFU나 서버 믹싱**: 소리가 미디어 서버를 거쳐 서버에서 녹음할 수 있는 상태가 되고, 6명 정원에서는 확장 이점 없이 서버 비용과 운영 부담만 생긴다(ADR 0006).
- **미디어 요소 `volume`으로 사람별 음량 조절**: 구현은 가장 간단하지만 iOS WebKit이 `volume`을 바꾸지 못해 iPhone에서는 음량이 바뀌지 않는다.
- **`track.enabled = false`로 끄기**: 계획의 처음 방식이고 다시 켜는 데 0ms였지만, 끈 동안에도 무음 패킷이 초당 약 50개씩 나가 TURN 서버의 패킷 한계를 빨리 채운다.
- **answer 쪽에도 오디오 트랜시버를 미리 만들기**: 계획의 처음 방식이었지만 미리 만든 트랜시버는 offer의 m-line과 짝지어지지 않아, Chrome 대조 실험에서 answer 쪽 소리가 상대에게 가지 않았다.
- **소리를 영상 타일 스트림에 함께 싣기**: 스파이크의 첫 구현이었지만 영상이 오지 않는 상대의 소리가 재생기에 붙지 않았고, 타일의 음소거된 `<video>`가 Chrome에서 Web Audio 동작을 바꿔 재생 방식을 제대로 비교할 수 없었다.

## 결과와 제약

### 앱 권한과 문서

- 스파이크 커밋 `aebbef4c`는 기기 확인용으로 `app.json`의 `android.blockedPermissions`에서 `RECORD_AUDIO`를 빼고, `RECORD_AUDIO`와 `MODIFY_AUDIO_SETTINGS` 권한과 iOS `NSMicrophoneUsageDescription` 임시 문구를 넣었다.
- 이 권한 변경은 스파이크 브랜치에만 있고 dev에 올리지 않는다.
- 실제 마이크 권한은 P6에서 열고, 최종 권한 문구는 그때 사용자와 정한다.
- P6에서 권한을 열 때 ADR 0004의 마이크 서술, `apps/mobile/CLAUDE.md`의 마이크 금지 문장, SCR-S2의 마이크 항목을 함께 고친다.
- 이 ADR이 승인되면 루트 `CLAUDE.md` 개인정보 원칙의 멀티룸 문장과 그룹 공부방 설계 문서의 소리 절도 이 결정에 맞춘다.

### 네이티브 오디오 세션

- Android에서는 앱 쪽 설정 없이 WebView가 마이크를 열 때 통신 모드로 바꾸고 통신 장치를 스피커로 정했다.
- 다만 혼자 있는 방이라 실제로 스피커에서 상대 소리가 나는지는 듣지 못했다.
- iOS에서 마이크를 켜면 소리가 수화기로 바뀌는지, 네이티브 오디오 세션 설정이 필요한지는 확인하지 못했다.
- 필요하다고 나오면 실기기에서 검증한 방법만 P6에서 넣고, 검증되지 않은 네이티브 라이브러리는 설치하지 않는다.

### 6명 부하

- 6명 방에서 기기마다 연결 다섯 개에 소리까지 더했을 때의 발열과 영상, 측정 끊김은 측정하지 못했다(5번).
- TURN 서버 쪽 한계는 위 추정치로만 봤다.

### 버전이 섞인 방

- 지금 운영 `ontrack`은 트랙 종류를 보지 않고 스트림을 타일에 넘겨서, 소리를 보내는 웹과 그 전 웹이 한 방에 있으면 그 전 웹의 타일이 오디오 트랙 때문에 바뀌거나 비워질 수 있다.
- 이 내용은 코드를 읽고 내린 판단이고 확인하지 않았으며, 스파이크는 한 방의 모든 기기가 스파이크 개발 서버를 쓰게 해서 이 경우를 피했다.

### 기존 코드에서 확인한 것

- 공부방은 카메라를 끈 것으로 보여 주는 동안에도 전면 카메라를 열어 둔다.
- Galaxy S21에서 입장부터 퇴장까지 CameraService 목록에 앱이 활성 카메라 클라이언트로 남아 있었고, `CAMERA` appop의 지속 시간은 10분 34초였다.
- 코드에서는 `useStudyRoomSession`이 마운트 때 카메라를 켜고 언마운트 때만 끄며, 일시정지는 카메라를 놓지 않는다.
- 스파이크 전부터 있던 동작이고, 개인정보 문제로 따로 다룰지는 사용자 결정이 남아 있다.
- 카메라 없이 offer에 답한 기존 멤버는 미리 만든 영상 칸이 협상되지 않은 채(`mid`가 `null`) 남고 영상을 `recvonly`로 답해서, 나중에 카메라를 켜도 그 영상이 새 멤버에게 가지 않는다(Chrome에서 확인했다).
- 소리는 위 협상 규칙으로 이 문제를 피했지만 영상 쪽은 바뀌지 않았고, 기기 확인(9번)은 막혔다.

### 남은 확인

- iPhone 항목과 두 기기가 필요한 항목은 iPhone이 개발 서버에 HTTPS로 접속할 길이 없어 모두 막혔다.
- 확인 중 자동 실행 권한 검사가 공개 터널(`cloudflared tunnel`)을 거부했고, 다른 터널이나 호스팅으로 우회하지 않았다.
- 다시 하려면 사용자가 터널을 직접 열거나 허용하거나, `mkcert` 루트 인증서를 iPhone에 설치해 신뢰한 뒤 `VITE_DEV_HTTPS=1`로 개발 서버를 띄워야 한다.
- iPhone 개발 빌드의 프로필은 2026-11-07 16:57(KST)에 만료된다.
- 표에서 막힘인 항목은 HTTPS 경로가 생기면 모두 다시 한다.
- 끄는 방식은 iPhone에서 끈 뒤 주황 점이 꺼지는지, 다시 켤 때 소리가 수화기로 바뀌지 않는지, 껐다 켤 때 배경음이 끊기지 않는지를 보고 `보내지 않기`와 `트랙 멈추기` 중 하나로 정한다.
- `보내지 않기`를 고르려면 iPhone에서 껐다 켠 소리가 상대에게 다시 가는지(12번)도 확인해야 한다.
- 사람별 음량은 iPhone `web-audio`에서 적용되는지(7번)와 무음 모드에서 Web Audio 소리가 나는지(`silentKeepAlive` 비교)를 보고 확정한다.
- iPhone은 1차 확인 때 무음 모드였으므로, 2번, 4번, 7번은 무음 모드 여부를 함께 적는다.
- 블루투스 이어폰(8번)은 사람이 직접 연결해야 한다.
- Android 배경음 확인(4번)은 일시정지 중에는 배경음이 나지 않으므로 카메라를 켜고 얼굴 가리기를 쓴 채로 해야 한다.
- Android `트랙 멈추기`에서 재생 스트림이 바뀔 때 들리는 끊김이 있는지 확인한다.
- Android WebView도 Chrome처럼 음소거한 `audio` 요소 없이는 Web Audio에 소리가 들어오지 않는지 확인한다.
- `bundlePolicy`를 `max-bundle`로 바꿀지는 정하지 않았다.

### 스파이크 브랜치

- 스파이크 코드는 `spike/BY-1125-mic` 브랜치에 남기고 dev로 PR을 올리지 않는다.
- 브랜치는 그룹 공부방 설계 문서 커밋 `d382aae3`에서 시작했고, 개발 앱 마이크 권한은 `aebbef4c`, 웹 구현은 `aebbef4c..084aa099`(`a2a6bd02`, `084aa099`)에 있다.
- P5 구현자는 `peerMesh.ts`의 오디오 협상과 `micSpike.ts`의 재생기, 끄는 방식 제어, 통계 읽기를 참고한다.
- 스파이크 웹 코드는 `import.meta.env.DEV`일 때만 돌고, 운영 빌드 결과물에 조작판 문자열이 없는 것을 확인했다.
- 협상 규칙의 동작은 버리는 스모크 스크립트로만 확인했고, 단위 테스트는 `findAudioSender`의 세 경우뿐이다.
- 기존 `peerMesh` 테스트는 스파이크 플래그를 끈 채로 돌려 운영 동작을 계속 검사하게 했다.

## 위키에 제안할 변경

위키는 고치지 않았다. 사용자가 확인한 뒤 위키 PR을 올린다.

- `decisions/0002-social-video-p2p.md`의 결정(안)에 소리 항목을 더하고, 결과 / 영향에 이 ADR을 가리키는 줄을 더하자고 제안한다.

```diff
 3. 영상 공유는 **사용자가 명시적으로 켠 경우에만**, WebRTC **P2P**로 사용자 간 직접 전송한다
+4. 그룹 공부방 소리도 **사용자가 마이크를 켠 동안에만** 영상과 같은 WebRTC **P2P**로 상대 멤버에게 직접 보내고, **녹음·저장하지 않는다**
```

```diff
 - frontend에 WebRTC 스택 추가, backend에 시그널링 서버 역할 추가
+- 소리를 P2P 메시에 더하는 구현 결정은 frontend 저장소 `docs/adr/0020-group-room-audio-in-p2p-mesh.md`에 있다
```

- 같은 위키의 그룹 공부방 명세 18절 "소리는 서버를 거치지 않고 녹음하거나 저장하지 않는다"는 TURN 중계와 맞지 않으므로, 26절처럼 "소리는 녹음하거나 저장하지 않고, TURN은 암호화된 데이터를 거쳐 보내기만 한다"로 맞추는 것도 함께 제안한다.
