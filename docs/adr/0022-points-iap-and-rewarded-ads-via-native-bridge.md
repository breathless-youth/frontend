# 0022. 포인트 결제는 RevenueCat, 보상형 광고는 AdMob으로 셸이 맡고 웹과는 브리지로 주고받는다

- Status: Accepted
- Date: 2026-11-16
- Relates to: [포인트와 꾸미기 상점 설계](../superpowers/specs/2026-11-09-points-economy-design.md), [ADR 0001](./0001-webview-based-study-room-architecture.md), [ADR 0003](./0003-phased-rollout-webview-mvp-then-native.md), [ADR 0010](./0010-native-firebase-analytics-for-push-targeting.md)

## 배경

포인트 상점은 포인트 충전 묶음과 캐릭터 세트를 스토어 결제로 팔고, 보상형 광고를 본 사용자에게 포인트를 준다. 디지털 재화라 iOS와 Android 모두 스토어 인앱결제를 써야 한다.

화면은 모두 원격 웹에 있다(ADR 0001, ADR 0003). 결제 창과 광고는 네이티브 SDK만 띄울 수 있어서 웹과 셸이 일을 나눠야 했다.

포인트는 돈과 이어진다. 앱이 "결제가 끝났다", "광고를 다 봤다"고 알리는 것만으로 포인트를 주면 요청을 꾸며 포인트를 받을 수 있어서, 지급은 서버가 결제 사업자와 광고 사업자에게 직접 확인한 뒤에 해야 했다.

원격 웹은 스토어의 예전 앱에도 바로 배포된다. 결제와 광고 메시지를 모르는 앱에 메시지를 보내면 답이 오지 않아 화면이 멈춘다.

## 결정

### SDK

- 결제는 RevenueCat(`react-native-purchases` 11.0.2)을 쓴다.
- 광고는 AdMob(`react-native-google-mobile-ads` 17.4.0)의 보상형 광고만 쓴다.
- SDK는 `lib/pointsChargeSdk.ts`와 `lib/pointsAdsSdk.ts`만 불러오고, 나머지 코드는 `lib/pointsCharge.ts`와 `lib/pointsAds.ts`의 공개 함수만 본다.
- 결제 키(`REVENUECAT_API_KEY`)나 광고 단위가 없는 빌드와 네이티브 모듈이 없는 옛 Dev Client에서는 SDK를 불러오지 않고 그 기능을 끈다.
- `test_`로 시작하는 RevenueCat Test Store 키는 운영 빌드에 들어가면 빌드를 실패시킨다.
- 광고 단위는 빌드 종류로 고른다. 서버가 자기 환경의 광고 단위로 본 시청만 보상하기 때문이다.
- AdMob 앱 ID 플러그인은 광고를 띄우지 않는 빌드에도 넣는다. Android는 SDK가 링크된 앱의 매니페스트에 앱 ID가 없으면 시작할 때 죽는다.

### RevenueCat을 고른 이유

- 서버가 App Store와 Google Play의 영수증 검증과 환불 알림을 따로 만들지 않고 RevenueCat의 결제 알림 하나(`POST /api/points/purchases/revenuecat/webhook`)로 지급과 회수를 처리한다.
- iOS와 Android가 SDK 하나와 같은 코드로 결제한다.
- Test Store 키로 스토어에 상품을 등록하기 전에도 실기기에서 결제 흐름을 확인할 수 있다.

### AdMob을 고른 이유

- 서버 확인 콜백(`GET /api/points/ads/admob/callback`)이 있어서 서버가 구글의 서명을 확인한 시청에만 포인트를 준다.
- 광고 등급 상한을 요청 설정으로 걸 수 있다.

### 웹과 셸이 나눠 맡는 일

- 웹은 화면, 상품 목록, 회원 여부 확인, 서버가 지급했는지 다시 읽는 일을 맡는다.
- 셸은 스토어 가격 조회, 결제 창, 구매 복원, 광고 표시만 맡고 포인트나 보유 상태를 판단하지 않는다.
- 브리지 메시지는 `points-charge-prices`, `points-charge-purchase`, `points-charge-restore`, `points-ad-show` 네 가지이고 셸은 같은 `id`의 `-result`로 답한다.
- 셸은 결제와 복원을 한 번에 하나만 처리하고, 진행 중에 온 결제 요청은 `cancelled`, 복원 요청은 `failed`로 답한다.
- 스토어 상품 ID는 영문, 숫자, 점, 밑줄, 하이픈만 받고 그 밖의 값은 SDK에 넘기지 않는다.
- 가격 문구는 스토어가 기기의 통화로 만든 값을 SDK에서 읽고, 서버는 스토어 상품 ID와 받는 포인트만 준다.

### 지급은 서버가 한다

- 셸은 결제 전에 서버가 준 결제용 ID(`GET /api/points/products`의 `revenueCatAppUserId`)로 RevenueCat에 로그인해서 결제 알림에 그 값이 실리게 한다.
- 결제용 ID는 회원번호와 다른 값이고, 서버는 회원번호로 로그인한 결제를 지급하지 않는다(2026-11-16 백엔드 변경).
- 웹이 결제, 구매 복원, 가격 조회 메시지에 결제용 ID를 실어 보내고, 셸은 회원번호로 대신 로그인하지 않는다.
- 비회원은 결제용 ID가 null이라 웹이 결제와 복원 메시지를 보내지 않고 로그인 화면으로 보낸다.
- 웹은 결제 버튼을 누를 때마다 충전 상품 목록을 다시 받아 결제용 ID를 읽고, 받지 못하면 결제 창을 열지 않고 다시 시도하라고 알린다.
- 셸은 광고의 서버 확인 옵션에 사용자 ID를 실어서 구글이 서버에 보내는 시청 확인에 사용자 ID가 실리게 한다.
- 셸의 `completed`와 `rewarded`는 스토어 결제와 광고 시청이 끝났다는 뜻일 뿐이고, 웹은 이 답으로 잔액을 바꾸지 않는다.
- 웹은 결제가 끝나면 잔액이나 상품 보유를 2초 간격으로 30번까지, 광고가 끝나면 오늘 본 횟수를 2초 간격으로 10번까지 다시 읽는다.
- 그동안 서버 값이 바뀌지 않으면 실패가 아니라 "곧 들어온다"고 알리고, 돈이 이미 나갔으므로 다시 결제하는 길을 주지 않는다.
- 구매 복원은 웹이 스토어 결제로 파는 상품의 ID와 결제용 ID를 넘기고, 셸은 그 값으로 로그인해 RevenueCat 복원을 부른 뒤 결제 기록에 그 상품이 있는지로 `restored`와 `nothing`을 답한다.
- 복원으로 결제가 다른 계정에서 넘어오면 RevenueCat이 서버에 알리고 서버가 보유를 바꾸므로, 웹은 복원 직후와 2초, 5초 뒤에 상점과 내 모습을 다시 읽는다.

### 예전 앱과 브라우저

- 셸은 웹뷰 주소에 `points=1`(포인트 브리지를 안다), `pointsCharge=1`(결제할 수 있다), `pointsRestore=1`(구매를 복원할 수 있다), `pointsAds=1`(광고를 띄울 수 있다)을 붙인다.
- 웹은 `points=1`이 있을 때만 포인트 화면과 입구를 열고, 나머지 표시가 있을 때만 그 메시지를 보낸다.
- 앱 안인데 표시가 없으면 충전 칸, 광고 타일, 구매 복원 줄을 그리지 않는다.
- 브라우저에서는 충전 칸 자리에 앱에서 열기 안내를 그리고, 결제 상품은 앱에서 살 수 있다고만 알린다.
- 문제가 생기면 빌드 변수 `VITE_POINTS_DISABLED=1`로 웹을 다시 배포해 포인트 전체를 끈다.

### 광고 요청

- 사용자가 `보기`를 눌렀을 때만 광고를 불러오고, 공부를 측정하는 화면에는 광고를 넣지 않는다.
- SDK를 시작하기 전에 광고 등급 상한을 전체 이용가(G)로 건다.
- 맞춤 광고는 허용하고, 맞춤 광고를 끄는 옵션과 아동 대상 표시는 넣지 않는다(2026-11-16 결정).

### 회원만 결제한다

- 보상 받기, 광고, 충전, 결제 상품 구매, 구매 복원은 회원만 한다.
- 셸의 인증 상태에는 회원 여부가 없어서 웹이 버튼을 누르는 순간에 막고 로그인 화면으로 보낸다.
- 서버도 비회원의 요청을 `403 MEMBER_ONLY`로 거절한다.

## 검토한 대안

- **스토어 SDK를 직접 붙이기**: 서버가 두 스토어의 영수증 검증, 환불 알림, 중복 지급 방지를 각각 만들어야 한다.
- **웹 결제**: 앱 안에서 쓰는 디지털 재화는 스토어 정책상 인앱결제를 써야 한다.
- **앱이 광고 시청 완료를 서버에 알리기**: 요청을 꾸미면 광고를 보지 않고 포인트를 받을 수 있다.
- **포인트 화면을 네이티브로 만들기**: 화면을 웹에 두는 방침(ADR 0001, ADR 0003)과 어긋나고, 상품을 고칠 때마다 앱을 다시 내야 한다.
- **메시지 하나로 결제와 지급 결과를 함께 답하기**: 지급은 서버가 알림을 받은 뒤에 일어나서 셸이 알 수 없고, 셸에 서버 조회를 더하면 판단이 두 곳으로 나뉜다.

## 결과

- 지급이 RevenueCat과 구글의 알림에 의존한다. 알림이 늦으면 포인트가 보통 몇 초, 길면 1분쯤 늦게 들어오고 웹은 기다리는 창을 띄운다.
- RevenueCat이나 구글의 알림이 끝내 오지 않으면 돈이 나갔는데 포인트가 없는 사용자가 생긴다. 웹은 문의 링크를 보여 주고, 복구는 서버와 운영이 맡는다.
- 결제, 복원, 광고 요청에는 시간 제한이 없다. 사용자가 결제 창이나 광고에 머무는 시간을 정할 수 없기 때문이고, 셸이 답하지 않으면 그 화면의 버튼은 화면을 다시 열 때까지 풀리지 않는다.
- 셸이 회원 여부를 모르므로, 웹을 거치지 않고 브리지 메시지를 직접 보내면 비회원도 결제 창을 띄울 수 있다. 이때도 포인트는 서버가 회원에게만 준다.
- 결제와 광고 SDK가 들어가 앱 심사를 다시 받는다. 맞춤 광고를 허용하므로 개인정보 처리방침, App Store 개인정보 라벨, Play 데이터 보안에 광고 식별자와 구매 내역을 넣기 전에는 이 빌드를 스토어에 내지 않는다.
- 운영 빌드에는 운영용 RevenueCat 키(iOS, Android)와 스토어 상품 등록이 필요하다. 키가 없으면 충전과 결제 상품, 구매 복원이 꺼진 채로 나간다.
- staging에는 그 서버가 받는 광고 단위가 없어 광고가 꺼져 있다.
- 실기기 스파이크(BY-1242, BY-1243)의 SDK 후보 비교 표와 기기별 확인 결과는 이 문서에 담지 못했다. 정리되면 이 문서에 더한다.
- SDK 버전을 올릴 때는 RevenueCat의 복원 결과 모양(`nonSubscriptionTransactions`)과 AdMob의 요청 설정 이름이 그대로인지 확인한다.
