# 홈 개편 v3 백엔드 연동 확인

작성: 2026-11-07. BE dev 머지 후 배포된 Swagger와 서버 소스를 확인하고 FE 연동을 마쳤다. 이 문서는 기존 요청 초안을 실제 명세와 검증 결과로 갱신한 기록이다. 기획·서버 명세의 공식 기준은 `.ai` 팀 위키와 BE Swagger다.

- 기존 목표 API는 BY-1165와 [BE PR #144](https://github.com/breathless-youth/backend/pull/144)를 확인해 재사용했다.

서버 소스 기준은 `17ae022c67214b42b206a6e769bfa7bd9bccbbe1`이다. [미션 ADR](https://github.com/breathless-youth/backend/blob/17ae022c67214b42b206a6e769bfa7bd9bccbbe1/docs/adr/0045-home-start-mission.md), [미션 운영 문서](https://github.com/breathless-youth/backend/blob/17ae022c67214b42b206a6e769bfa7bd9bccbbe1/docs/runbooks/home-mission.md), [플래너 API 문서](https://github.com/breathless-youth/backend/blob/17ae022c67214b42b206a6e769bfa7bd9bccbbe1/docs/api/planner.md)를 배포 Swagger와 대조했다.

## 공통 요청

새 미션·목표 요청은 `Authorization: Bearer accessToken`과 `API-Version: 1`을 사용한다. 계정 식별은 토큰으로 처리하므로 `userId`를 쿼리로 보내지 않는다. 응답은 별도 envelope 없이 JSON 본문으로 받는다.

## 시작 미션

| 기능           | 메서드와 경로                                  | 요청 본문 |
| -------------- | ---------------------------------------------- | --------- |
| 미션 조회      | `GET /api/home/mission`                        | 없음      |
| 단계 완료 확인 | `POST /api/home/mission/steps/{step}/complete` | 없음      |

`step`은 `1` 또는 `2`다. 조회와 완료 확인은 같은 형태의 응답을 반환한다.

```json
{
  "version": "home-v3",
  "startsOn": "2026-11-07",
  "completedSteps": 0,
  "currentStep": 1,
  "eligible": true,
  "measuredFocusSec": 0
}
```

- `completedSteps`는 사용자가 완료 확인한 단계 수로 `0`, `1`, `2`를 반환한다.
- `currentStep`은 현재 단계의 `1` 또는 `2`이며 전체 완료 후에는 `null`이다.
- `eligible`은 서버가 판단한 현재 단계의 완료 조건 충족 여부다.
- `measuredFocusSec`은 시작일 이후 인정되는 날짜별 측정 순공 합계 중 최댓값이다.
- `version`과 `startsOn`은 서버가 관리한다.

### 인정 규칙

1단계는 활성 과목이 1개 이상이면 충족한다. 생성 시점과 생성 화면은 관계없으며 기존 과목도 인정한다. 완료 확인 전에 모두 삭제하면 미충족이고, 완료 확인한 단계는 이후 삭제로 취소되지 않는다.

2단계는 `startsOn` 이후 **현지 달력 날짜 하루의 원본 MEASURED 순공 합계가 300초 이상**일 때 충족한다. 같은 날짜의 여러 세션은 합산하고 다른 날짜는 합산하지 않는다. 수동 기록과 시작일 이전 날짜는 제외하며 자정을 걸친 세션은 기존 현지 자정 분할값을 사용한다. 1단계 확인 전에 달성한 날짜도 인정한다. 이전 초안의 여러 날짜 누적과 공개 시각 분할 문구는 이 규칙으로 대체했다.

완료한 단계는 계정에 유지되고 날짜가 바뀌어도 초기화하지 않는다. 같은 단계의 완료 요청을 다시 보내면 현재 저장 상태를 반환하며 다음 단계까지 진행하지 않는다. 조건 미충족, 단계 건너뛰기와 잘못된 단계 요청은 `400 BAD_REQUEST`로 처리한다. 계정 통합 때는 더 진행된 완료 단계를 유지한다.

FE는 과목 수나 홈 통계로 미션 조건을 다시 판단하지 않고 서버의 `currentStep`과 `eligible`을 표시한다. 완료 응답 성공 전에는 단계를 바꾸지 않으며 오류에는 재시도를 제공한다.

## 홈·플래너 공통 목표

| 기능           | 메서드와 경로                                                 | 요청                                |
| -------------- | ------------------------------------------------------------- | ----------------------------------- |
| 날짜 목표 조회 | `GET /api/planner/goals/{date}`                               | 날짜를 명시한다.                    |
| 날짜 목표 저장 | `PUT /api/planner/goals/{date}?calendar=HOME&timeZone={IANA}` | `{ "goalSec": 0..86400 }`을 보낸다. |
| 기본 목표 조회 | `GET /api/planner/goals/default`                              | 추가 본문이 없다.                   |
| 기본 목표 저장 | `PUT /api/planner/goals/default?timeZone={IANA}`              | `{ "goalSec": 0..86400 }`을 보낸다. |
| 기본 목표 삭제 | `DELETE /api/planner/goals/default`                           | 성공 시 `204`를 받는다.             |

날짜 목표 응답은 `goalSec`, `individualGoalSec`, `defaultGoalSec`를 반환하며 각각 `number | null`이다. 기본 목표 조회·저장 응답은 `goalSec: number | null`이다. `goalSec`는 정수 초 단위이고 서버는 1초 단위를 허용하며 홈 UI는 30분씩 조절한다.

FE 홈에서는 날짜별 플래너 조회인 `GET /api/planner/days/{date}?timeZone={IANA}`의 `goal`과 할 일을 읽는다. 플래너와 동일한 계정·날짜·시간대 캐시를 사용해 별도 목표 저장소를 만들지 않았다.

### 날짜와 0 처리

- 홈은 기기 시간대의 00시 기준 날짜를 사용한다.
- 플래너의 기존 오늘 판정과 통계는 05시 기준을 유지한다.
- `calendar=HOME`은 날짜 목표 `PUT`에만 전달한다.
- HOME 저장은 현지 오늘과 과거 날짜를 허용하고 미래 날짜는 거절한다.
- 일반 플래너 저장·삭제의 날짜 허용 규칙은 기존 05시 기준을 유지한다.
- 홈의 날짜 목표 `0`은 `PUT`으로 저장하고 `DELETE`로 바꾸지 않는다.
- 개별 목표 `0`도 기본 목표보다 우선하며 기본 목표 변경으로 덮어쓰지 않는다.
- 날짜 목표 저장 후 기본 목표 저장만 실패하면 FE에서 기본 목표만 다시 저장한다.

인증 실패는 `401 UNAUTHORIZED`로 처리한다. 필수 값 누락·범위 오류는 `400 VALIDATION_FAILED`, 잘못된 날짜·calendar는 `400 BAD_REQUEST`로 처리한다. 홈 진행률의 분자는 기존 00시 기준 홈 통계를 사용한다.

## 실제 개발 서버 검증

별도 테스트 계정과 과목으로 활성 과목 1개 인정, 실제 1단계 완료, 동일 단계 재요청, 미충족 2단계의 `400`, 날짜 목표 `0`과 기본 목표 우선순위를 확인했다. 브라우저의 실제 `/home`에서 목표 `30,600초` 저장과 이후 날짜 목표 `0` 저장도 확인했다. 검증 후 해당 계정을 삭제해 `204`를 받았다.

초기 목표 편집 UI 검증에서는 미션 완료 상태만 fixture였고 목표 요청은 실제 개발 서버에 보냈다. 이후 iOS 실기기에서 원본 MEASURED 두 건의 같은 날 순공506초와 실제 2단계 완료·즉시 목표 영역 전환까지 확인했다. 재설치와 다른 기기 동기화는 여전히 남아 있다. 상세 결과는 [프론트엔드 구현 현황](2026-11-07-home-v3-implementation.md)에 기록했다.

## 추가 집계 정합성 확인 요청 — 2026-11-08 iOS QA

새 API 요청이 아니라 기존 세션 전체 값과 과목 구간 값의 일관성 확인이다. 개발 환경의 실제 MEASURED 기록에서 아래 값이 제출 응답과 단건 GET200에 동일하게 남았다.

| 항목                | 실제 응답             |
| ------------------- | --------------------- |
| 전체 공부 시간      | 150초                 |
| 전체 순공 시간      | 49초                  |
| 수학 구간           | 공부105초·순공51초    |
| 국어 구간 합계      | 공부44초·순공0초      |
| 과목 구간 순공 합계 | 51초 — 전체보다2초 큼 |

실제 수학 시작 후 국어로 바꾸고, 서버 체크포인트를 WebView 재로드로 복원한 뒤 일시정지 상태에서 제출한 기록이다. 복원 뒤에도 국어와 같은 시작 시각을 유지했다. 가짜 시간·이벤트·React 상태는 주입하지 않았다.

실제 이벤트와 기존 `SubjectSegmentSplitter`를 대조해 구간·AWAY·PAUSE를 각각 정수 초로 먼저 절삭하는 원인을 재현했다. 수학 구간은 `105.272 − 2.855 − 52.805 = 49.612`초여서 마지막에 절삭하면49초다. 기존 구현은 `105 − 2 − 52 = 51`초를 만든다. FE가 응답 값을 임의로 보정하지 않았다. 기존 ADR-0023이 조기 절삭 정책을 명시하므로 구현 적용 때 정책 문서도 정정해야 한다. 부모 합계는 별도로 신뢰하며 과목 공백·행별 절삭·서브초 이벤트 생략이 있어 이 수정만으로 모든 과목 합계와 부모의 완전 일치를 보장하지 않는다.

현재 서버의 일일 통계에는49초 세션이 포함되지 않았고 홈은 기존 공부554초·순공506초를 표시했다. 단건 저장 성공을 홈 합계 증가 검증으로 대신하지 않았다. 기록과 연결된 오늘 국어 선택 제거는 실제409 CONFLICT였으므로 기록·선택을 보존했고 DB 등으로 우회하지 않았다. 기존 할 일 두 건은 원래11/7·미완료 상태로 유지됨을 실제 앱 GET으로 재확인했다.

근거는 별도로 보관한 로컬 QA 결과다. API 주소·인증 정보·카메라 원본과 계정별 식별자는 PR에 포함하지 않는다.

### 집계 정밀도 수정 후보 — 적용 전 검토 자료

별도 로컬 검토 자료에 splitter·고정 회귀 JUnit·ADR 정정안 3파일을 준비했다. 원본 알고리즘 복사본과 정밀도 후보를 같은11개 고정 기대값으로 실행해 원본6실패·후보0실패였다. 실제 기록 이벤트, 분할 불변성, 소수 PAUSE, 정수/빈 이벤트/전체 정지/서브초 생략/과목 공백 경계를 포함한다. 조기 절삭은 공부·순공 양쪽을 바꾸므로 순공만 수정한 것으로 설명하지 않는다. `git apply --check`도 통과했다.

이 결과는 격리 알고리즘 재현이며 backend 저장소 전체 Gradle 검사나 실제 적용·배포 검증은 아니다. backend 저장소는 변경하지 않았고 현재 저장 기록도 유지했다. backend AGENTS의 Jira 선행 규칙에 맞는 티켓 매핑, 통합 회귀검사, 정책 검토 후 적용하고 동일 실제 측정·전환·복원·제출로 재검증해야 한다. 이 PR에는 FE 계약 설명만 포함하고 BE 패치는 포함하지 않는다.
