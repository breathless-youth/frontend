# 공부 세션 Vision 파이프라인 설계 (2026-07-27)

## 목표와 범위

[2026-07-26 세션 상태 모델·서버 계약 설계](./2026-07-26-session-state-model-and-contract-design.md)가 **"상태를 어떻게 정의하고 서버로 어떻게 보내는가"** 를 확정했고, 그 문서는 스스로 **"실제 Vision 모델 로딩·추론은 범위 밖"** 이라고 명시했다. 이 문서가 그 빈칸을 채운다.

확정하는 것은 다음 다섯 가지다.

1. `apps/web`을 WebView에 **어떻게 올리고** 모델·wasm을 **어떻게 전달하는가**
2. EfficientDet-Lite0을 **어떤 런타임으로** 돌리는가
3. 카메라 프레임을 **어떤 주기·해상도·스레드로** 처리하는가
4. 모델의 검출 결과를 **어떤 규칙으로** 감지 신호(`away`/`phone`)로 바꾸는가
5. 가속도 센서가 **어떤 계산으로** `device` 신호를 만드는가

근거는 세 가지다. `ai-wiki`의 확정 결정(`product/mvp-scope.md`, `product/policies.md`, `product/roadmap.md`, `project/architecture.md`), 위 세션 상태 모델 스펙, 그리고 `frontend/CLAUDE.md`의 아키텍처·프라이버시 경계다. 셋 다에 없는 값은 **상수로 열어두고 "미확정"으로 표시**한다.

**범위 밖**: 화면 프레젠테이션(S1–S6·G1–G5는 구현 완료), 서버 계약 변경, 멀티룸/LiveKit, 모델 학습(`vision` 레포 과제).

## 1. 서빙 — 앱 번들 + localhost HTTP 서버

`apps/web`의 빌드 산출물과 모델·wasm을 **앱 번들에 동봉**하고, 네이티브가 띄운 **로컬 HTTP 서버**가 그것을 서빙한다. WebView는 `http://localhost:{port}/room/:id`를 연다.

```
앱 실행
 └─ 네이티브가 로컬 HTTP 서버 기동
      루트: assets/web-dist/   (127.0.0.1 바인딩, 외부 접근 불가)
 └─ WebView가 http://localhost:{port}/room/:id 로드
      ├─ index.html · JS · CSS
      ├─ efficientdet_lite0.tflite
      └─ mediapipe tasks-vision wasm
```

네트워크는 기기 밖으로 나가지 않는다. `localhost`는 기기 내부 주소이므로 비행기 모드에서도 동작하고, 이것이 mvp-scope의 **"세션은 네트워크 없이 완전히 동작한다"** 를 화면 로드 시점부터 구조적으로 보장한다.

### 왜 원격 URL이 아닌가

원격 배포본을 로드하면 세 가지가 깨진다. 첫째, **첫 실행에 네트워크가 필요**해 오프라인 정책이 화면 로드 단계에서 무너진다. 둘째, 모델·wasm을 Service Worker 캐시에 의존하게 되는데 OS가 캐시를 정리하면 그 사용자는 세션을 **아예 시작할 수 없다.** 셋째, 첫 세션에서 모델을 내려받는 동안 감지가 돌지 않아, mvp-scope가 정한 **"별도 준비 화면 없이 홈에서 바로 시작, 카운트다운 없음"** 과 충돌한다.

### 왜 `file://`이 아닌가

번들 동봉만으로 충분해 보이지만 `file://`로 직접 열면 세 가지 제약이 붙는다.

**`getUserMedia` 승인이 기기별로 갈린다.** 브라우저는 secure context(`https` 또는 `localhost`)에서만 카메라를 열어준다. `file://`의 취급은 엔진 구현에 따라 다르고 WKWebView에서 거부된 사례가 보고돼 있다. **로컬 서버는 이 불확실성을 통째로 제거한다.**

**멀티스레드 wasm 경로가 막힌다.** `SharedArrayBuffer`는 COOP/COEP 응답 헤더를 요구하는데 `file://`에는 헤더를 붙일 수단이 없다. 지금 당장 멀티스레드가 필요하지 않더라도, **성능이 모자랄 때 쓸 카드가 아예 없는 것과 남아 있는 것은 다르다.** 이 차이는 ADR 0003과 직결된다 — 그 문서의 네이티브 전환 트리거 1번이 "WebView 기반 Vision의 성능이 목표치 미달임이 실측으로 확인된 경우"인데, `file://`은 성능 상한이 인위적으로 낮아 **그 실측이 WebView의 한계인지 서빙 방식의 한계인지 구분되지 않는다.** 잘못된 근거로 아키텍처를 뒤집을 위험이 있다.

**SPA 라우팅이 깨진다.** `apps/web`은 `react-router-dom`으로 `/room/:id`를 쓰는데, `file://`에는 "모르는 경로는 index.html"을 해줄 서버가 없어 HashRouter로 갈아엎어야 한다. `apps/web`은 독립 브라우저 서비스로도 배포하므로(ADR 0001) 그 URL 오염이 그대로 남는다.

부수 효과로 **오리진이 `http://localhost:{port}`로 고정**되어 WebView가 기억하는 카메라 권한 승인 상태가 앱 업데이트 후에도 유지되고, PC 브라우저 개발 환경(`http://localhost:5173`)과 실행 조건이 같아져 "브라우저에선 되는데 앱에선 안 되는" 종류의 버그가 줄어든다.

### 비용 — Expo Go 이탈

로컬 HTTP 서버는 네이티브 모듈이라 Expo Go에 없다. `expo-dev-client` + EAS Build 체계가 필요하다. `react-native-webview`·`expo-sensors`·`expo-file-system`은 Expo Go에 포함돼 있으므로 **Dev Client를 강제하는 것은 서버 라이브러리 하나뿐이다.**

이 비용은 **새로 생기는 것이 아니라 앞당겨지는 것**이다. Expo Go는 개발 도구이지 배포 수단이 아니므로 V1.0을 스토어에 올리는 시점에 EAS Build는 반드시 필요하다. 실질적으로 새로 드는 것은 **iOS 실기기 Dev Build 설치에 필요한 Apple Developer 계정**뿐이며, 2026-07-27 기준 확보되어 있다.

`eas.json`은 이미 `development`(`developmentClient: true`)·`preview`·`production` 프로파일을 갖고 있으나 `eas init`이 실행된 적이 없어 `app.json`에 EAS 프로젝트 ID가 없다. 스파이크 S1에서 발급한다.

### 로드맵 정합성

| 버전 | 내용                                             | 이 결정의 유효성                                                          |
| ---- | ------------------------------------------------ | ------------------------------------------------------------------------- |
| V1.2 | 로그인 · 비공개 방 · 실시간 상태 공유(영상 없음) | 유지                                                                      |
| V1.3 | **P2P 영상 공유 (WebRTC)**                       | **이 결정이 전제 조건** — `RTCPeerConnection`도 secure context를 요구한다 |
| V1.4 | 공개 방 · 안전장치                               | 유지                                                                      |
| M2+  | 시선 추적 · 자세 분석                            | 유리 — 더 무거운 모델에 멀티스레드 여지가 필요해진다                      |

`file://`을 택하면 V1.3에서 어차피 이 구조로 옮겨야 하고, 그때는 이미 올라간 세션 코드 위에서 서빙 방식을 바꾸는 작업이 된다.

### 빌드 파이프라인

`apps/web` 빌드 → `apps/mobile/assets/web-dist/` 복사 → EAS 빌드. **복사를 누락한 채 앱을 빌드하면 옛 화면이 담긴 앱이 조용히 나오므로**(에러가 나지 않는 종류의 실패), CI에 동기화 검사를 추가한다(§10).

포트는 **동적 할당** 후 WebView URL을 런타임에 조립한다. 고정 포트는 다른 앱과 충돌할 수 있다.

iOS는 `Info.plist`에 로컬 네트워킹 예외가 필요할 수 있다. `app.json`이 바뀌면 `lib/__tests__/permissionCopy.test.ts`가 잡으므로(ADR 0004), 그 테스트를 함께 갱신한다.

## 2. 추론 런타임 — MediaPipe Tasks Vision

`@mediapipe/tasks-vision`의 `ObjectDetector`를 쓴다. `efficientdet_lite0.tflite`를 **변환 없이 그대로** 로드한다.

```ts
const fileset = await FilesetResolver.forVisionTasks("/mediapipe/wasm");
const detector = await ObjectDetector.createFromOptions(fileset, {
  baseOptions: { modelAssetPath: "/models/efficientdet_lite0.tflite", delegate: "GPU" },
  runningMode: "VIDEO",
  categoryAllowlist: ["person", "cell phone"],
  scoreThreshold: VISION_CONFIG.scoreThreshold,
});
const result = detector.detectForVideo(videoEl, performance.now());
```

`categoryAllowlist`로 COCO 80클래스 중 필요한 둘만 남긴다. 우리가 알아야 할 것은 **"사람이 있나 / 폰이 있나"** 뿐이므로 나머지는 후처리 비용일 뿐이다.

### 왜 이 런타임인가

**EfficientDet-Lite0이 MediaPipe `ObjectDetector`의 공식 레퍼런스 모델**이라 변환도 후처리 구현도 필요 없다. `.tflite` 파일 안의 박스 디코딩·NMS를 라이브러리가 처리하고, 라벨과 점수가 바로 나온다.

`detectForVideo(videoElement, timestamp)`가 비디오 프레임 처리를 전제로 설계돼 있어 §3의 고정 주기 루프와 바로 맞물린다. 중간에 canvas를 끼우지 않으므로 프레임 복사가 한 번 줄어든다.

ADR 0001이 **"Vision AI는 MediaPipe Tasks Vision을 브라우저/WebView에서 직접 실행한다"** 고 이미 명시하고 있어 아키텍처 문서와 어긋나지 않는다(그 문서는 Face Landmarker를 예로 들었으나 같은 라이브러리의 다른 태스크다).

### 왜 다른 후보가 아닌가

**ONNX Runtime Web** — EfficientDet 계열 `.tflite`에는 `TFLite_Detection_PostProcess`라는 TFLite 전용 커스텀 연산이 들어 있고, ONNX 표준에 대응 연산이 없다. 변환이 그 지점에서 실패하므로 원본 TF 모델부터 다시 내보내고 **박스 디코딩·NMS를 직접 구현**해야 한다. 구현이 틀려도 정확도만 조금 떨어질 뿐 조용히 틀리는 종류라 검증 비용이 크다. MVP 범위가 아니다.

**tfjs-tflite** — `.tflite`를 그대로 먹고 후처리도 해주지만, 패키지가 장기간 alpha에 머물러 있어 문제 발생 시 참고할 자료가 적다. 그리고 우리는 TFJS의 다른 기능을 쓰지 않으므로 생태계 이점이 없다.

### vision 레포와의 계약

`ai-wiki/project/architecture.md`는 `vision` 레포를 "학습·변환·평가 파이프라인, 모델 산출물"로 정의한다. 현재 비어 있으나, mvp-scope에 **다중 인물 프레임(도서관·자습실) 처리**가 vision 과제로 남아 있어 재학습이 예정돼 있다.

**런타임 선택이 학습 파이프라인을 구속한다.** MediaPipe 경로에서는 vision 레포가 MediaPipe Model Maker로 학습하면 `.tflite` + 메타데이터가 그대로 떨어지고, FE는 **파일만 교체**하면 된다. 이는 architecture.md의 핵심 설계 원칙 **"감지 로직의 교체 가능성 — 감지 모듈과 타이머·세션 로직 사이의 인터페이스를 분리한다"** 를 파일 수준에서 실현한다.

모델은 **MediaPipe 공식 배포본으로 시작**한다. int8·float32 두 변형을 모두 번들에 넣고 스파이크 S3에서 실측 비교한다 — 저조도에서 person을 놓치는 정도가 곧 순공시간 오차이므로, 크기만 보고 int8을 성급히 고르지 않는다.

### 연산 장치

`delegate: "GPU"`(WebGL)로 시도하고 **실패하면 `"CPU"`(wasm)로 폴백**한다. WebView에서 GPU delegate의 안정성이 검증되지 않았기 때문이다. 어느 쪽으로 떨어졌는지는 진단 로그(§8)에 남긴다.

COOP/COEP 헤더는 **기본적으로 끄고 시작한다.** 멀티스레드 wasm이 필요하다고 실측으로 확인되면 그때 켠다. 켜면 웹에서 외부 API를 직접 호출하는 경로가 제약을 받는데(백엔드가 대응 헤더를 주지 않는 경우), WebView 모드는 서버 제출을 네이티브가 담당하므로 영향이 없다. 다만 **브라우저 단독 배포본에는 헤더를 붙이지 않는다** — 그쪽은 웹이 직접 API를 호출한다.

## 3. 프레임 파이프라인

### 프레임 주기 — 고정 200ms

mvp-scope가 "프레임 처리 주기(배터리 소모 vs 감지 반응성)"를 미확정으로 남겨둔 항목이다. **기본값 200ms(5 FPS)를 상수로 두고 M1에서 튜닝**한다.

높은 FPS가 필요 없는 근거는 감지 파라미터 자체에 있다. 가장 짧은 판정이 **0.5초**(폰 사용·기기 조작의 확정 유지시간)이므로, 200ms 간격이면 그 안에 2~3프레임이 들어간다. 초당 30프레임을 돌려도 판정 정확도는 그대로이고 배터리와 발열만 늘어난다.

주기는 함수로 감싼다.

```ts
// 지금은 상수를 돌려주지만, M1에서 적응형(집중 안정 시 느리게)으로 바꿀 때
// 이 함수 안만 고치면 되도록 호출부를 미리 분리해 둔다.
export function nextFrameIntervalMs(phase: SessionPhase): number;
```

### 추론 스레드 — 메인

`detectForVideo`가 `<video>` 엘리먼트를 직접 받으므로 메인 스레드가 자연스럽다. 200ms 중 추론이 50~100ms를 점유하더라도:

- **카메라 프리뷰**는 브라우저가 별도로 그리므로 JS 블로킹과 무관하다
- **타이머**는 초 단위 갱신이라 체감되지 않는다
- **상태 전환 애니메이션**은 CSS `transform`/`opacity`만 쓰면 컴포지터에서 돌아 영향받지 않는다

Web Worker는 `<video>`를 전달할 수 없어 매 프레임 `ImageBitmap`을 만들어 transfer해야 하고, 그 비용이 추론 이득을 상쇄할 수 있다. GPU delegate + OffscreenCanvas 조합의 WebView 동작도 별도 검증이 필요하다. **지금 이 복잡도를 지불할 근거가 없다.**

다만 추론 호출부(`vision/objectDetector.ts`)를 독립 모듈로 두어, 스파이크 S3에서 끊김이 실측되면 **그 모듈만 워커 뒤로 옮긴다.**

### 카메라 해상도

모델 입력은 320×320이므로 카메라 해상도는 **프리뷰 화질용**이다. 너무 낮으면 풀스크린 프리뷰가 뭉개지고, 높으면 배터리·발열·다운스케일 비용이 늘어난다.

```ts
{ video: { facingMode: "user", width: { ideal: 720 }, height: { ideal: 1280 } } }
```

기본값을 상수로 두고 S3에서 조정한다. 리사이즈는 MediaPipe가 내부에서 처리하므로 우리가 canvas로 복사하지 않는다.

### 일시정지 중 동작

**카메라 스트림은 유지하고 추론만 정지한다.**

세션 상태 모델 스펙 §2가 "일시정지 진입 시 감지기를 정지"하라고 정했으나, 그것이 카메라 스트림까지 끄라는 뜻인지는 `SCR-S3-3` Review Checklist에 미확정으로 남아 있었다. 유지하는 쪽을 택하는 이유는 세 가지다. Figma S3-3이 프리뷰를 그대로 보여준다. 배터리 주 소모원은 카메라 피드가 아니라 추론이므로 절감 효과가 대부분 확보된다. 스트림을 끄면 재개 시 `getUserMedia` 재호출로 1~2초 공백이 생겨, 그 구간이 측정되지 않는다.

### 카메라 전환

전/후면 전환 시 기존 트랙을 정지하고 새 스트림을 얻은 뒤 `<video>`에 다시 연결한다. **전환 중에는 추론을 멈추고, 새 스트림이 준비되면 재개**한다. 전환 실패는 기존 `CameraFlipResult`(`no-alternative` / `camera-off`)로 표현해 확정된 토스트 문구를 그대로 쓴다.

## 4. 검출 → 감지 신호 판정

모델은 "cell phone이 이 위치에 이 점수로 있다"까지만 알려준다. **"사용 중"인지는 알려주지 않는다.** 그 변환 규칙을 여기서 정한다.

원시 검출을 boolean 신호로 바꾸는 것이 이 절의 범위이고, 그 뒤의 **유지시간 디바운스(1.5초/0.5초 등)와 상태 전이는 기존 `detection.ts`·상태기계가 그대로 담당**한다.

### 자리 이탈 (`away`) — 관대하게

**score 임계를 낮게 두고, `person`이 하나라도 검출되면 "사람 있음"으로 본다.**

관대한 쪽으로 기울이는 이유는 오탐의 방향 때문이다. 책을 보려고 고개를 숙이거나 거치 각도에 따라 `person`을 놓치면 **공부 중인데 순공에서 빠진다.** mvp-scope의 측정 대원칙 "측정할 수 없는 시간은 집중으로 인정하지 않는다"는 **부풀리지 말라**는 뜻이지 깎으라는 뜻이 아니다. 자리 이탈 오탐은 원칙을 지나치게 적용해 사용자가 실제로 한 공부를 지우는 결과가 된다.

1.5초의 확정 유지시간이 순간적 미검출을 이미 걸러주므로, 낮은 임계와 합쳐지면 실용적인 안정성이 나온다.

**다중 인물의 MVP 동작이 이 규칙으로 자동 정의된다** — 도서관에서 옆 사람이 보이면 "사람 있음"이라 자리 이탈이 아니다. 반대로 **본인이 자리를 떠도 옆 사람 때문에 안 잡히는 오차**가 남고, 이쪽은 순공을 부풀리는 방향이라 대원칙에 어긋난다. **알려진 한계로 명시하고 vision 레포의 다중 인물 과제로 넘긴다** — 임계 조정으로는 풀리지 않는다.

### 폰 사용 (`phone`) — 검출 즉시, 단 교체 가능하게

**`cell phone`이 score 임계 이상으로 검출되면 곧바로 `phone`으로 판정한다** (2026-07-27 리더 결정).

**알려진 한계를 명시한다.** 대부분의 사용자는 공부 중 폰을 책상에 올려두며, 그 폰이 전면 카메라 시야에 들어오면 계속 검출되어 **순공시간이 0에 수렴한다.** 이는 voice-tone의 추정형 문구("~것 같아요")가 흡수하도록 설계된 수준의 오탐이 아니다. 리더는 이 한계를 인지한 상태에서 V1.0 범위를 단순하게 유지하기로 했고, **정교화는 후속으로 반영한다.**

그래서 **판정 규칙 자체를 교체 지점으로 격리**한다.

```ts
export interface DetectionFrame {
  readonly detections: readonly Detection[]; // 라벨 · score · bbox
  readonly previous: readonly Detection[] | null;
  readonly frameSize: { width: number; height: number };
  readonly atMs: number;
}

export interface PhoneUsageRule {
  evaluate(frame: DetectionFrame): boolean;
}

/** V1.0 — 검출되면 곧바로 사용 중으로 본다. */
export const detectedAsUsedRule: PhoneUsageRule;
```

`DetectionFrame`에 이전 프레임과 프레임 크기를 미리 넣어두는 이유는, 후속 규칙 후보들이 **전부 이 두 정보로 구현되기 때문**이다.

| 후속 후보                              | 필요한 정보                | 성격                                                     |
| -------------------------------------- | -------------------------- | -------------------------------------------------------- |
| 박스 크기 임계 (가까이 들면 커짐)      | `frameSize` 대비 bbox 면적 | 단순, 임계 1개. 거치 거리에 민감                         |
| 프레임 간 이동량 (놓인 폰은 안 움직임) | `previous`                 | 놓인 폰을 자연히 걸러냄. 들고 정지하면 놓침              |
| 사람 박스 상단과의 겹침                | 같은 프레임의 person bbox  | 실제 행동과 직접적. 책상에 두고 고개만 숙이면 놓침       |
| 세션 초 N초 기준선 학습                | 세션 시작 시점 스냅샷      | 환경 자동 적응. 구현 복잡, 시작 시 폰을 들고 있으면 오염 |

크기와 이동량은 서로의 약점을 메우는 조합이라 함께 쓰는 것이 유력하다. **이 규칙들을 넣을 때 상태기계·타이머·이벤트 변환은 한 줄도 바뀌지 않는다.**

### 저조도 등 감지 불가

별도 처리가 없다. 모델이 사람을 못 잡는 상태는 `person` 미검출과 같은 경로로 흘러 자연히 `away`가 되고, 이는 mvp-scope가 확정한 대로다("서버에는 `AWAY`로 전송하고 화면 문구도 분기하지 않는다").

### 임계값

`scoreThreshold`(person·phone 각각)는 **상수 모듈에 두고 S3에서 실측 결정**한다. mvp-scope의 감지 파라미터와 같은 성격의 M1 튜닝 대상이다.

## 5. 가속도 센서 — 기기 조작

경계는 세션 상태 모델 스펙 §3이 이미 정했다. **네이티브는 임계 초과 여부(boolean)까지만 만들어 올리고, 유지시간 디바운스(0.5초/2초)는 웹이 한다.** 원시 가속도 값을 초당 수십 개 브리지로 넘기지 않는다.

그 boolean을 만드는 계산을 확정한다.

**최근 300ms 창에서 가속도 크기 `‖a‖`의 표준편차가 임계를 넘으면 `active`.**

```
‖a‖ = sqrt(x² + y² + z²)
active = stddev(최근 300ms의 ‖a‖ 표본) > MOTION_STDDEV_THRESHOLD
```

### 왜 표준편차인가

**중력 방향에 무관하기 때문**이다. 대안이던 "`‖a‖`가 1g에서 벗어난 정도"는 기기가 정지 상태에서 정확히 1g를 읽는다는 가정에 기대는데, 실제로는 거치대 각도·책상 진동·센서 바이어스에 따라 기준선이 흔들려 **기기마다 임계를 다시 잡아야 한다.** 게다가 폰을 들고 가만히 있으면 다시 1g로 돌아와 놓친다.

표준편차는 "가만히 있으면 흔들리지 않는다"만 본다. 정지 상태에서는 센서 노이즈만 남아 편차가 거의 0이고, 만지는 순간 즉시 커진다. **어떤 각도에서도 같은 임계가 통한다.**

기울기 각도 변화를 보는 방식은 손떨림·미세 진동에 둔감하고 각도가 바뀌지 않는 조작을 놓친다.

### 파라미터

`MOTION_WINDOW_MS`(300)와 `MOTION_STDDEV_THRESHOLD` 둘 다 상수 모듈에 둔다. 창 크기는 사실상 고정이고 실제 튜닝 대상은 임계 하나다. mvp-scope의 미확정 항목 "가속도 센서의 '조작' 판정 기준(임계 가속도 값)"이 이것이며, **스파이크 S4에서 기본값을 정한다.**

### 샘플링과 수명

`expo-sensors`의 `Accelerometer`를 쓴다. 샘플링 간격은 상수(기본 50ms = 20Hz)로 두되, 창 안에 표본이 6개 이상 들어가도록 창 크기와 함께 검증한다.

**일시정지 중에는 센서를 정지한다** — 감지 중단 정책과 배터리 양쪽에 맞고, 카메라 추론 정지와 동일한 시점에 일어난다.

## 6. `@focuson/study-core` 신설

세션 상태 모델 스펙 §9와 7차 인터뷰 액션 아이템이 예고한 패키지를 **이번에 만든다.** 지금까지는 상태 계산이 `apps/web` 안에만 있어도 됐지만, 이번 작업에서 **네이티브가 소급 마감(크래시 복구·일시정지 20분 초과 마감)을 수행**하게 되면서 같은 계산을 양쪽이 하게 된다. 두 벌로 두면 순공시간이 갈라질 수 있다.

**담는 것**: 상태 타입(`SessionPhase`·`DetectorKind`), 상태기계와 전이 규칙, 디바운스 판정, 구간 → 서버 이벤트 변환, 타이머 산출, 체크포인트 타입과 소급 마감 계산, 홈·기록 합산 계산.

**담지 않는 것**: 카메라 접근, 모델 로딩·추론, 네트워크, 저장소, React 컴포넌트. `@focuson/types`(서버 계약 타입)만 참조한다.

작업 방식은 **`apps/web/src/features/study-session/`의 기존 순수 모듈(`detection.ts`·`sessionState.ts`·`sessionTimeline.ts` 등)을 이전**하는 것이다. 새로 쓰지 않는다 — 기존 테스트가 함께 옮겨가며 회귀를 막는다. 기존 패키지 관례대로 `lint`/`typecheck`/`test` 스크립트를 모두 노출한다.

**판정 규칙(§4)은 `study-core`에 넣지 않는다.** `Detection` 타입이 MediaPipe 출력 형태에 종속되므로 `apps/web` 쪽에 둔다. 경계는 "boolean 신호가 나온 뒤"부터가 `study-core`다.

## 7. 저장과 전송

세션 상태 모델 스펙 §6·§7이 정한 정책은 그대로다. 구현 수단만 확정한다.

| 대상       | 수단                                  | 이유                                                                                             |
| ---------- | ------------------------------------- | ------------------------------------------------------------------------------------------------ |
| 체크포인트 | `expo-file-system` 단일 파일 덮어쓰기 | 항상 최신 하나만 필요하다                                                                        |
| 미제출 큐  | 세션당 파일 하나                      | 한 세션이 깨져도 나머지가 살아남고, 전송 성공 시 파일만 지우면 된다                              |
| 쓰기 방식  | **임시 파일에 쓰고 rename**           | 10초마다 덮어쓰는 도중 크래시하면 파일이 깨진다. rename은 원자적이라 "옛것 아니면 새것"만 남는다 |

WebView 저장소(IndexedDB·localStorage)에 두지 않는 이유는 스펙 §7 그대로다 — 백그라운드 태스크가 읽을 수 없고 iOS가 정리할 수 있다.

전송 트리거는 세션 종료 직후와 앱 포그라운드 진입 시. `400`은 큐에서 제거하고 로그만 남긴다. 나머지 실패는 사용자에게 노출하지 않는다.

### 서버 재기동과 WebView 복구

iOS가 백그라운드에서 로컬 서버를 종료할 수 있다. 복귀 시 **서버 상태를 확인하고 필요하면 재기동한 뒤 WebView를 리로드**한다. 이 처리가 없으면 복귀했을 때 화면이 비어 사용자가 세션을 잃었다고 느낀다.

리로드 후에는 브리지 `restore-session`으로 체크포인트를 웹에 되돌려 세션을 이어간다(스펙 §10). 백그라운드는 정책상 일시정지이므로 감지 공백은 발생하지 않는다.

## 8. 진단 로그와 프라이버시

mvp-scope는 프레임 주기·가속도 임계·감지 유지시간을 모두 "M1에서 튜닝"으로 미뤄뒀다. **튜닝하려면 판정 근거가 남아 있어야 하는데 현재 설계에 그 장치가 없다.**

**개발 빌드 전용으로만 남긴다.** 프로덕션 바이너리에는 코드가 포함되지 않아 프라이버시 리스크가 0이다.

### 남기는 것 / 남기지 않는 것

`frontend/CLAUDE.md`는 **"카메라 원본 프레임·얼굴 이미지·랜드마크 좌표는 단말 내부에서만 처리한다. 서버 전송·파일/캐시/DB 저장·로그 기록 금지"** 로 못박는다. **검출 박스 좌표도 이 금지에 걸린다고 해석한다** — 좌표는 랜드마크와 같은 성격의 위치 정보다.

| 남긴다                                   | 남기지 않는다          |
| ---------------------------------------- | ---------------------- |
| `person` 유무 (boolean)                  | 프레임 이미지 · 썸네일 |
| 라벨별 최고 score                        | **bbox 좌표 · 크기**   |
| 최종 판정 결과 (`away`/`phone`/`device`) | 얼굴 · 랜드마크        |
| 프레임 처리 소요시간 (ms)                |                        |
| 선택된 delegate (GPU/CPU)                |                        |
| 상태 전이 시각                           |                        |

이 정도로 "임계를 몇으로 하면 오탐이 얼마나 주는가"를 계산할 수 있다.

### 세션 중 서버 전송은 하지 않는다

상태 변화 시점의 **기록**은 이미 확정 설계가 커버한다 — 체크포인트 트리거가 `10초 주기 + 상태 전이 시 + 백그라운드 직전`이라 상태가 바뀔 때마다 파일이 갱신된다.

상태 변화 시점의 **서버 전송**은 현재 계약에 없다. Swagger에 진행 중 세션을 받는 API가 없고, "세션 중 네트워크 0"이 오프라인 정책의 근거다. 필요해지면 **BE 계약 추가 요청 + 오프라인 정책 재검토**가 선행되어야 하는 사안이며, 이 문서의 범위 밖이다.

## 10. 실기기 스파이크

각 단계는 독립적으로 되돌릴 수 있게 만든다. **S1·S2가 §1 전체의 성립 조건**이므로 다른 코드를 쓰기 전에 이 둘을 먼저 확인한다.

### S3 결과 (2026-07-29 · Android 에뮬레이터 Pixel 3 / API 35 WebView + macOS Chrome 150)

**조건부 통과.** 파이프라인은 끝까지 동작하고 서빙·MIME·404 경계는 기기에서 검증됐다. 다만 **§2가 정한 `delegate: "GPU"` 우선을 뒤집었고, §3이 정한 "메인 스레드로 충분하다"는 판단은 실측으로 무너졌다.**

실기기는 여전히 확보되지 않았다(Apple Developer 승인 대기, Android 실기기 미연결). 아래 수치는 **에뮬레이터 1종**이며, 그 한계를 항목마다 표시한다.

#### 1. GPU delegate가 조용히 틀린 값을 낸다 — 이번 스파이크의 핵심 발견

같은 프레임(에뮬레이터 가짜 카메라)을 두 delegate로 돌린 결과다.

| delegate | 모델 | 검출 결과                              | 생성     | 첫 추론 | 정상 추론     |
| -------- | ---- | -------------------------------------- | -------- | ------- | ------------- |
| GPU      | fp32 | `person` **1,648건**, 전부 정확히 0.50 | 9,469ms  | 3,888ms | 604~800ms     |
| GPU      | int8 | `person` **2,775건**, 전부 정확히 0.50 | 10,104ms | 5,913ms | 1,336~1,700ms |
| CPU      | fp32 | **0건** (정답)                         | 8,343ms  | 1,984ms | 401~594ms     |
| CPU      | int8 | **0건** (정답)                         | 15,414ms | 1,587ms | 213~371ms     |

score가 전부 정확히 `0.50`인 것이 결정적 단서다 — 실제 추론 결과가 아니라 초기화되지 않은 출력 텐서로 보인다.

**증상은 성능 문제가 아니라 데이터 오염이다.** 이 쓰레기가 그대로 `personPresent = true`가 되어 **앱이 영원히 "집중 중"이라고 보고한다.** 실제로 세션을 2분 42초 돌려 재현했다 — 화면은 계속 `집중 측정 중`, `순공시간 == 총 공부 시간`, 즉 **집중률 100%가 서버에 저장된다.** `mvp-scope.md`의 "측정할 수 없는 시간은 집중으로 인정하지 않는다"를 정면으로 어기며, 순공시간이 몇 초 어긋나는 것과는 비교할 수 없이 나쁘다.

**따라서 `DELEGATE_ORDER`를 `["CPU"]`로 바꿨다.** GPU를 폴백 뒤에 남기지도 않았다 — 폴백은 "실패했을 때" 발동하는데 **GPU는 실패하지 않고 성공한 얼굴로 틀린 답을 준다.** 잡을 신호가 없다.

**실기기에서 재검토할 것.** GPU가 정상이면 정상 추론이 2.7배 빠르므로 되돌릴 값어치가 있다. 같은 비교를 실기기에서 다시 하고, 정상이면 `visionConfig.ts`의 배열만 `["GPU", "CPU"]`로 돌린다.

#### 2. 메인 스레드 점유 — §3의 전제가 깨졌다

§3은 "200ms 중 추론이 50~100ms를 점유하더라도 타이머는 초 단위라 체감되지 않는다"를 근거로 메인 스레드를 골랐다. 두 가지가 그 전제를 벗어난다.

**첫 호출이 메인 스레드를 8~9초 막는다.** macOS Chrome에서 첫 `detectForVideo`가 8.2초(fp32)·9.0초(int8) 걸렸고, **세션 타이머 표시가 `00:00:01`에 얼어 있다가 `00:00:10`으로 점프**했다(1초 주기 프로브 콜백이 전부 밀렸다가 한꺼번에 실행되는 것으로 확인). Android에서는 같은 비용이 **검출기 생성**으로 옮겨가 8~15초가 걸린다 — 위치만 다르고 총량은 같다. MediaPipe가 초기화를 생성이 아니라 첫 추론에 미루기 때문이다.

**정상 상태도 예산을 넘는다.** 에뮬레이터에서 프레임당 213–594ms(CPU)로, 200ms 목표의 1.1–3배다. 에뮬레이터 CPU가 실기기보다 느리므로 실기기에서는 줄겠지만, 여유가 크지 않다.

**§3이 미리 열어둔 문**("스파이크 S3에서 끊김이 실측되면 그 모듈만 워커 뒤로 옮긴다")**의 발동 조건이 충족됐다.** 워커 이전은 이번 범위에 넣지 않고 **후속 티켓**으로 분리한다(2026-07-29 리더 결정) — 이번 작업의 범위는 배선 완성이고, 워커는 매 프레임 `ImageBitmap` transfer 비용을 다시 재야 하는 별개 판단이다.

#### 4. 남는 지적

- **`int8` vs `fp32`의 정확도 비교는 못 했다.** 에뮬레이터 카메라에 실제 장면이 없어 "저조도에서 person을 놓치는 정도"를 잴 수 없다. `DEFAULT_MODEL_VARIANT`는 §2 방침대로 `fp32`로 둔다 — 속도만 보고 int8을 고르지 않는다. 실기기 과제.
- **에뮬레이터 가짜 카메라가 `person`으로 검출된다**(CPU에서는 0건이지만 GPU 쓰레기 출력과 별개로, 실제 장면이 아니므로 판정 정확도 검증에 쓸 수 없다). 감지 정확도는 실기기에서만 확인 가능하다.
- **`MAX_CONSECUTIVE_DETECT_FAILURES = 5`는 여전히 근거가 없다.** 실측 기회가 없어 `objectDetector.ts` 지역 상수로 남긴다.
- **prebuild를 건너뛰면 옛 자산이 조용히 담긴다.** `android/`가 이미 있으면 `expo run:android`가 prebuild를 건너뛰고, config plugin의 복사가 재실행되지 않아 **APK 안 `web-dist`가 낡은 채로 빌드된다.** 이번에 실제로 겪었다(모델·wasm 없이 빌드돼 감지가 통째로 죽었다). `sync-web:check`는 `apps/web/dist → apps/mobile/assets/web-dist` 한 홉만 검사하고 그 다음 홉은 아무도 보지 않는다. 로컬 빌드 시 `npx expo prebuild -p android`를 먼저 돌릴 것 — 런북에 적었다.

### CI 추가

`apps/mobile/assets/web-dist/`가 현재 `apps/web` 빌드 결과와 일치하는지 검사하는 job을 추가한다. 불일치는 에러 없이 조용히 옛 화면을 배포하므로 자동 가드가 필요하다.

## 11. 테스트

`study-core`는 순수 함수 모음이므로 단위 테스트로 전부 덮는다 — 전이표의 모든 행, 겹침 병합("폰을 보다가 그 폰을 들고 자리를 뜸" → `AWAY` 1건), 타이머 부등식(`0 ≤ focusSec ≤ studySec ≤ 세션 길이 − PAUSE 합`)의 성질 검사, 소급 마감 3갈래.

판정 규칙(`PersonPresenceRule`·`PhoneUsageRule`)은 검출 배열을 받아 boolean을 돌려주는 순수 함수라 픽스처로 검증한다. 후속 규칙을 추가할 때도 같은 테스트 틀을 쓴다.

가속도 표준편차는 샘플 시퀀스 픽스처(정지 · 집어들기 · 진동)로 검증한다.

원자적 쓰기는 쓰기 도중 중단을 흉내내 파일이 깨지지 않는지 확인한다.

브리지 메시지는 양방향 직렬화·역직렬화와 알 수 없는 메시지 무시를 확인한다.

**FPS·발열·배터리는 테스트가 아니라 스파이크 실측**이며, §10에 결과로 남긴다.

## 13. 기존 문서에 반영해야 할 것

이 설계가 채택되면 다음이 갱신 대상이 된다.

- **`SCR-S3-3` Review Checklist** — "일시정지 중 카메라 스트림 유지/중지 정책"이 §3에서 **유지 + 추론만 정지**로 해소된다.

- **ADR 신규** — 서빙 방식(번들 + localhost 서버)과 Expo Go → Dev Client 전환은 구조 변경이므로 ADR 0005로 기록한다. ADR 0003의 "지금은 Dev Client가 불필요하다"는 서술과 `apps/mobile/CLAUDE.md`의 같은 서술이 이 시점에 낡는다.
