## 1. 목적

홈 화면 위에 딤 + 중앙 카드 형태의 공지 팝업을 띄운다. 구성은 배너 이미지 영역(330×186, 옵션),
제목, 본문, "다시 보지 않기" 텍스트 버튼, "확인" 버튼, 우상단 X 닫기. 신기능 홍보 등 운영 공지를
앱 배포 없이 발행·수정·종료할 수 있는 기반을 만든다.

## 3. 백엔드 설계 (backend 레포)

### 3.1 스키마 — Flyway `V9__notice.sql` (V8은 dev의 `V8__add_user_email.sql`이 사용 중)

```sql
CREATE TABLE "notice" (
  "id"         bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  "title"      varchar(100) NOT NULL,
  "content"    text NOT NULL,
  "image_url"  varchar(500),
  "starts_at"  timestamptz NOT NULL,
  "ends_at"    timestamptz,
  "created_at" timestamptz NOT NULL DEFAULT now(),
  "updated_at" timestamptz NOT NULL DEFAULT now()
);
```

- 기존 `notification`·`user_notification`·`push_token`은 그대로 둔다(미사용 스캐폴딩, 개념이 다름).
- 컬럼 타입·명명은 V1__init.sql 관례를 따른다(구현 시 대조).

### 3.2 도메인 — `project.study.notice`

- `Notice` 엔티티(Lombok `@Getter`, protected 기본 생성자 — 레포 관례)
- `NoticeRepository` — 활성 공지 조회 쿼리: `starts_at <= now AND (ends_at IS NULL OR now < ends_at)`,
  `starts_at DESC` 정렬
- `NoticeService`, `NoticeController`
- DTO는 record: `NoticeResponse(id, title, content, imageUrl)` — `starts_at` 등 운영 필드는 노출하지 않는다

### 3.3 API

```
GET /api/notices/active
200 → [ { "id": 1, "title": "...", "content": "...", "imageUrl": "https://... | null" } ]
```

- 인증 없음. **dev 브랜치는 소셜 로그인 도입으로 `anyRequest().authenticated()` 상태라
  `SecurityConfig`에 `GET /api/notices/active` permitAll 추가가 필요하다**(2026-08-15 확인).
  사유: 공지는 로그인 전 사용자에게도 보여야 하는 공개 브로드캐스트이고, 민감정보가 없는
  읽기 전용 GET이다. 레포 규칙대로 사용자 승인 후 반영한다.
- 목록으로 반환한다. "1개만 표시"는 클라이언트 정책이므로 서버는 자르지 않는다.

### 3.4 운영

- 공지 등록·수정·종료용 SQL 예시(등록 INSERT, 조기 종료 `UPDATE ... SET ends_at = now()`,
  S3 이미지 URL 기입 안내)는 **저장소에 넣지 않고 협업툴에 공유한다** — 사용자 결정(2026-08-15).
  구현 완료 후 공유용 문안을 작성해 사용자 승인을 받아 전달한다.

### 3.5 테스트 (Kent Beck TDD, 5-0 승인 후)

- 서비스 단위: 활성 판정 경계(시작 전·활성 중·종료 후·ends_at NULL·정렬)
- 통합(MockMvcTester + Testcontainers): 응답 스키마·빈 목록

### 3.6 프로세스

- dev 브랜치에서 `feature/BY-N-notice-api` 분기
- task-workflow에 준함: 티켓 초안 전문 승인 → 계획·테스트 목록 승인 → 로컬 커밋까지 자율,
  푸시는 승인 후 → PR 본문 전문 승인

## 4. 프론트엔드 설계 (frontend 모노레포)

### 4.1 계약 — `packages/types`

- `NoticeResponse` 타입 추가. 레포 규칙에 따라 **BE Swagger 확정 후** 추가한다.
  작업 순서가 BE → FE인 이유.

### 4.2 게이트 모듈 — `apps/web/src/features/home/notice.ts`

U1 `updateNotice.ts`와 같은 역할 분리: 화면 컴포넌트는 순수 프레젠테이션, 노출 판정은 이 모듈.

- `fetchActiveNotices()` — `GET /api/notices/active`. 기존 statsApi 관례(base URL 주입)를 따른다
- dismiss 저장: `focuson.noticeDismissed.{id}` = `"1"`. 조회 실패는 fail-closed(안 띄움),
  저장 실패는 무시(다음 방문에 한 번 더 뜨는 것이 최악)
- 노출 대상 결정: 활성 공지 중 dismiss 안 된 것 중 최신 1개
- U1 순서 조정(결정 7, 2026-08-16 변경): U2 Host가 흐름 종료(비노출 확정 또는 닫힘)를 알리면
  그때 U1 Host를 마운트한다 — 홈탭이 순서를 소유하는 단일 조정 지점

### 4.3 화면 — `apps/web/src/features/home/NoticePopup.tsx` + `NoticePopupHost.tsx`

- U2 디자인 그대로: 딤, 카드, 배너 이미지(있을 때만, 결정 8), 제목, 본문, 다시 보지 않기, 확인, X
- Host를 `HomeTabPage`에 마운트(U1 Host와 같은 자리). react-query로 조회(`useHomeSummary` 관례)
- 홈 렌더를 막지 않는다: 조회는 비동기, 응답 오기 전에는 아무것도 띄우지 않는다

### 4.4 테스트 (Kent Beck TDD, 5-0 승인 후)

- 게이트 모듈 단위: dismiss 필터·최신 1개 선택·fail-closed·U1 우선
- 컴포넌트: 이미지 유무 렌더 분기, 세 가지 닫기 동선의 콜백 구분
- 시각 검증: Playwright HTML 리포트(6-1 승인 후)

## 5. 비범위

- 공지 쓰기 API, 어드민 화면, 이미지 업로드 API
- 서버 측 유저별 열람 저장(`user_notification` 활용)
- 푸시 알림, 네이티브 셸 노출, 브라우저 랜딩 노출
- 공지 예약 발행 UI(starts_at을 미래로 넣는 것으로 대체)

## 5.1 타겟 공지 연기 (2026-08-16)

특정 사용자(user_id) 타겟 노출은 `?userId=N` 쿼리 방식으로 승인까지 받았으나 **티켓 생성 전에
취소·연기됐다.** 백엔드가 익명 기기 등록을 토큰 발급 방식의 게스트(비회원) 로그인으로 재편할
예정이라, 타겟 공지는 그 이후 **토큰 신원 기반**으로 재설계한다(스푸핑 타협 불필요해짐).
notice_target 테이블 설계(매핑 없으면 전체 공개)는 그때 재사용한다. 게스트 로그인의 BE 계약은
미정(2026-08-16 기준)이며, 확정되면 모바일 등록 호출 교체 → 웹뷰 신원 전달 재설계(statsApi·
Amplitude·스크러빙 연쇄) → 타겟 공지 순으로 진행한다. BY-376(PR #7)·BY-377은 인증 체계와
무관하므로 그대로 완료한다(머지는 사용자가 나중에 직접).

## 6. 작업 순서

1. BE 티켓 → dev 분기 → 마이그레이션·API·테스트 → PR(dev 대상)
2. BE Swagger 확정 → FE 티켓 → `packages/types` 계약 → 게이트 모듈 → 팝업 UI → PR
3. 운영 SQL 안내 문안을 협업툴에 공유 → 첫 공지 등록으로 스모크
