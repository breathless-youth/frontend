# AI-Native Mobile Development Design

## 목적

FocusOn 모바일 MVP를 특정 LLM, 에이전트, MCP에 종속되지 않는 방식으로 개발한다. 모든 AI 도구가 동일한 프로젝트 맥락, 작업 경계, 화면 명세, 검증 기준을 사용하며 Figma 화면을 한 번에 하나씩 안전하게 구현하도록 한다.

## 적용 범위

- 활성 제품 범위는 `apps/mobile`의 앱 셸이다.
- 스터디룸 내부 구현은 `apps/web`이 소유하며 모바일은 WebView로 로드한다.
- 이번 체계는 화면 설계, 디자인 토큰, 모바일 공통 컴포넌트, 화면 조합 및 프레젠테이션 검증을 다룬다.
- 도메인 계산, Vision, RTC, 카메라 어댑터 및 WebView 연결 계약은 다루지 않는다.

## 기본 원칙

1. 저장소 문서가 대화 기록보다 우선하는 영속 컨텍스트다.
2. 공통 규칙은 LLM 중립적으로 작성하고 도구별 문서는 이를 참조한다.
3. 화면은 Figma 프레임과 저장소의 화면 명세를 함께 입력으로 사용한다.
4. MCP 출력은 구현 참고 자료이며 프로젝트에 바로 병합할 완성 코드로 간주하지 않는다.
5. 디자인 시스템은 토큰부터 시작하고 실제 화면에서 반복이 확인된 컴포넌트만 점진적으로 승격한다.
6. AI는 작업 전 허용 파일과 보호 파일을 선언하고 그 경계를 벗어나지 않는다.
7. 완료 주장은 자동 검사와 시각적 검증 결과를 근거로 한다.

## 문서 아키텍처

### 공통 진입점

루트 `AGENTS.md`를 모든 AI 도구의 공통 진입점으로 사용한다. 다음 내용을 짧게 요약하고 상세 문서로 연결한다.

- 프로젝트 목적과 활성 WebView 아키텍처
- 모바일 MVP 작업 범위
- 화면 소유권
- 수정 가능 영역과 보호 영역
- 개인정보 불변 원칙
- 패키지, TypeScript, 테스트 규칙
- Figma/MCP 화면 구현 절차
- 동시 작업 보호 규칙

`CLAUDE.md`와 향후 추가될 도구별 지침은 공통 규칙을 복제하지 않고 `AGENTS.md`를 참조한다.

### AI 개발 문서

```text
docs/ai-development/
  workflow.md
  context-map.md
  boundaries.md
  definition-of-done.md
  prompt-contract.md
  figma-to-code.md
  decisions/
```

- `workflow.md`: 명세, 계획, 승인, 구현, 검증, 기록의 작업 생명주기
- `context-map.md`: 작업 유형별 필수 입력 문서
- `boundaries.md`: 수정 가능 영역, 보호 영역, 동시 작업 충돌 회피 규칙
- `definition-of-done.md`: 공통 자동 검사와 UI 검증 기준
- `prompt-contract.md`: 프로젝트/작업/화면 프롬프트의 입력과 출력 형식
- `figma-to-code.md`: Figma 및 MCP 기반 화면 구현 절차
- `decisions/`: 작업 중 생긴 재사용 가능한 결정과 예외 기록

## 화면 명세 계약

각 화면은 `docs/screens/SCR-NNN-<screen-name>.md` 명세를 갖는다. 화면 명세는 다음 항목을 빠짐없이 포함한다.

- 화면 ID, 이름, 목적
- Figma 파일, 페이지, 프레임 또는 노드 식별자
- 진입 경로와 이탈 경로
- 표시 데이터와 데이터 출처
- 로딩, 빈 상태, 오류, 정상 상태
- 사용자 인터랙션과 내비게이션 결과
- Safe Area, 스크롤, 키보드, 작은 화면 처리
- 접근성 이름, 역할, 상태 및 글자 확대 요구사항
- 재사용할 토큰과 공통 컴포넌트
- 화면 전용 컴포넌트
- 수정 허용 파일과 보호 파일
- 시각적, 기능적 완료 조건

화면별 프롬프트는 이 명세를 복사해 관리하지 않고 파일을 직접 입력으로 사용한다.

## 프롬프트 계약

AI 입력은 세 계층으로 구성한다.

1. 프로젝트 계층: `AGENTS.md`와 관련 아키텍처 문서
2. 작업 계층: Figma 구현, 리뷰, 수정 등 작업 유형별 규칙
3. 화면 계층: 해당 `docs/screens/SCR-NNN-*.md`와 Figma 노드

구현 전에 AI는 다음 형식으로 작업 계약을 출력한다.

```text
이해한 요구사항:
읽은 컨텍스트:
수정할 파일:
수정하지 않을 영역:
재사용할 토큰과 컴포넌트:
구현 순서:
검증 방법:
불확실한 사항:
```

불확실한 사항이 시각적 취향이 아니라 데이터 계약, 권한 또는 아키텍처 경계를 바꾸는 경우 구현 전에 사용자 승인을 받는다.

## Figma에서 코드까지의 화면 단위 흐름

1. Figma에서 한 화면의 정상 상태와 필요한 예외 상태를 완성한다.
2. 화면 명세에 Figma 노드와 동작 요구사항을 기록한다.
3. AI가 컨텍스트 맵에 따라 지침, 토큰, 기존 공통 컴포넌트를 읽는다.
4. MCP로 대상 노드의 구조, 스타일, 에셋 및 컴포넌트 관계를 조회한다.
5. AI가 작업 계약과 변경 파일 목록을 제시한다.
6. 사용자가 경계와 구현 방향을 승인한다.
7. 라우트는 화면 조합만 담당하고 UI 세부 구현은 화면 전용 또는 공통 컴포넌트에 둔다.
8. 타입 검사, 린트, 테스트를 수행한다.
9. iOS와 Android에서 Figma 기준 스크린샷과 비교한다.
10. 재사용 가능한 결정과 의도적인 차이를 문서화한 뒤 다음 화면으로 이동한다.

한 화면이 검증되기 전에 다음 화면 구현을 시작하지 않는다.

## 디자인 시스템 성장 규칙

### 선행 정의

첫 화면 구현 전 다음 의미 기반 토큰의 이름과 사용 규칙만 정한다.

- 색상
- 타이포그래피
- 간격
- 모서리
- 그림자와 고도
- 아이콘 크기
- 상태 및 상호작용 표현

### 컴포넌트 승격

- 첫 사용은 화면 가까이에 구현할 수 있다.
- 두 화면에서 반복되면 API와 차이를 비교한다.
- 세 번째 사용이 확인되거나 제품 전반의 명백한 프리미티브라면 `apps/mobile/components/ui`로 승격한다.
- 비즈니스 데이터, 라우팅 또는 플랫폼 SDK를 포함한 구성 요소는 범용 UI 프리미티브로 승격하지 않는다.
- 공통 컴포넌트는 시각 variant, 크기, disabled/loading 상태와 접근성 계약을 명시한다.

초기 후보는 `AppText`, `Button`, `IconButton`, `TextInput`, `Card`, `Badge`, `Divider`, `Screen`, `Stack`, `Row`와 로딩/빈 상태/오류 표시다. 실제 Figma에서 필요성이 확인된 것만 구현한다.

## 코드 소유권과 충돌 방지

각 작업은 시작 전에 다음 정보를 기록한다.

```text
작업 ID:
담당 AI:
허용 파일:
보호 파일:
의존 중인 작업:
완료 조건:
```

기본 보호 영역은 다음과 같다.

- `apps/mobile/platform/**`
- `apps/mobile/features/study-session/**`
- `packages/study-core/**`
- `apps/mobile/app/room/[id].tsx`
- 다른 에이전트가 생성 또는 수정 중이라고 선언한 파일

UI 작업은 승인된 `apps/mobile/components/**`, `apps/mobile/app/**`의 앱 셸 라우트, 디자인 토큰 및 관련 문서에 한정한다. 기존 변경이 있는 파일을 수정해야 하면 차이를 먼저 확인하고 사용자 또는 해당 작업 소유자의 승인을 받는다.

## 검증 및 완료 정의

모든 모바일 작업은 다음 자동 검사를 통과해야 한다.

```powershell
pnpm --filter mobile lint
pnpm --filter mobile typecheck
pnpm --filter mobile test
```

화면 작업은 추가로 다음을 확인한다.

- iOS와 Android Safe Area
- 작은 화면과 큰 화면에서 잘림 및 불필요한 오버플로 없음
- 키보드가 입력과 주요 동작을 가리지 않음
- 글자 확대 시 핵심 정보와 동작 유지
- VoiceOver/TalkBack용 이름, 역할, 상태 제공
- 로딩, 빈 상태, 오류, 정상 상태 확인
- Figma와 동일한 기준 크기의 스크린샷 비교
- 하드코딩된 의미 색상과 반복 간격이 토큰을 우회하지 않음
- 보호 영역과 개인정보 원칙을 침범하지 않음

의도적으로 Figma와 다르게 구현한 부분은 플랫폼 관례, 접근성 또는 기술 제약과 함께 기록한다.

## 도입 순서

1. LLM 중립 `AGENTS.md`와 컨텍스트 맵을 추가한다.
2. 작업 경계, 완료 정의, 프롬프트 계약을 문서화한다.
3. Figma-to-code 절차와 화면 명세 템플릿을 추가한다.
4. 디자인 토큰의 의미와 이름을 확정한다.
5. 첫 기준 화면의 Figma와 화면 명세를 완성한다.
6. 첫 화면을 전체 파이프라인으로 구현하고 검증한다.
7. 발견된 마찰을 문서와 프롬프트에 반영한다.
8. 검증된 흐름으로 화면을 하나씩 확장한다.

## 성공 기준

- 서로 다른 LLM이 같은 화면 명세로 작업해도 수정 영역과 결과 구조가 일관된다.
- 화면 구현 전에 입력, 수정 파일, 보호 파일, 검증 방법이 명시된다.
- 생성된 화면이 Figma와 시각적으로 비교되고 예외 상태와 접근성이 검증된다.
- 공통 컴포넌트가 실제 반복을 근거로 성장하며 화면 코드가 도메인 및 플랫폼 계층을 침범하지 않는다.
- 작업 결정이 대화 기록이 아닌 저장소 문서에 축적되어 다음 AI가 이어서 작업할 수 있다.
