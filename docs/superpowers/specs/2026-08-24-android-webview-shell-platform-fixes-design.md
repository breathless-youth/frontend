# 안드로이드 웹뷰 셸 플랫폼 장애 대응 설계 (BY-412)

- 날짜: 2026-08-24
- 티켓: BY-412 `[FE] 안드로이드 웹뷰 셸 플랫폼 장애 대응`
- 발견 경위: BY-410 안드로이드 실기기 검증 3건 + BY-413 검증 2건

## 1. 범위

이번 작업이 고치는 것은 6건이다. 아래 번호는 티켓 배경 목록의 항목 번호를 그대로 쓴다.

| #   | 증상                                                                   | 원인                                                                                                                                             |
| --- | ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1   | 시스템 뒤로가기로 홈 이동 후 탭 재진입 시 이전 하위 페이지가 남아 있음 | 탭 웹뷰가 내부 히스토리를 유지한 채 탭만 전환됨                                                                                                  |
| 2   | 실시간 룸에서 화면 회전 미동작                                         | 회전 잠금 해제 예외가 솔로 세션 네이티브 화면(`room/[id]`)뿐. 소셜 룸은 탭 웹뷰 안 웹 라우트라 해제 경로가 없음                                  |
| 3   | 다크모드 미적용                                                        | 웹 테마가 전부 `prefers-color-scheme` 미디어쿼리인데 안드로이드 WebView는 시스템 다크를 웹에 전달하지 않아 항상 light                            |
| 6   | 소셜 룸 카메라 권한 게이트 부재                                        | 솔로 세션만 `start-session` 브리지에서 게이트를 탐. 소셜 룸은 웹 라우팅이라 게이트를 지나지 않음                                                 |
| 7   | 카메라 후면 전환 안됨 (2026-08-25 범위 추가)                           | `flip()`이 기존(전면) 스트림을 살려 둔 채 새 카메라를 먼저 여는데, Android 카메라 서비스는 기존 카메라를 놓기 전에는 반대 카메라 열기를 거부한다 |
| 8   | 권한 화면이 두 번 뜸 (2026-08-25 실기기 검증에서 발견)                 | dev 빌드의 StrictMode effect 이중 실행으로 `request-camera-gate`가 2회 발신돼 게이트가 두 번 돈다                                                |

7의 수정: `flip()`을 정지 후 열기 순서로 바꾸고, 실패 시 이전 카메라를 복원한다(해제 지연 대비 700ms 재시도 1회 — 입장 미리보기의 기존 재시도와 같은 값). 어댑터는 솔로 세션과 공유라 솔로의 안드로이드 전환도 함께 고쳐진다.

8의 수정: `requestCameraGate()`가 진행 중 요청 하나를 모듈 스코프로 공유해 동시 호출이 같은 결과를 쓴다.

입장 미리보기 모달 제거(2026-08-25 확정, iOS·Android 공통): **입장 시 카메라 미리보기 모달을
띄우지 않고 카메라 꺼짐으로 바로 입장한다.** 카메라는 룸 안 컨트롤 바 토글로 켠다. Android에서
미리보기 카메라 획득이 권한 흐름과 얽혀 입장이 깨지는 문제가 반복됐고, 켜고 입장이 기본이면
룸까지의 단계도 하나 더 늘기 때문이다. 게이트는 입장 직전에 그대로 태운다(세션이 마운트 즉시
카메라를 획득하므로). join 실패 시에만 기존 다이얼로그를 미리보기 없이 띄워 재시도를 제공하고,
유예 재입장은 기존대로다.

권한 상태 매핑 수정(2026-08-25): Android는 사용자가 설정 앱에서 권한을 끄면 `denied` +
`canAskAgain: true`가 되는데, 어댑터가 `canAskAgain`을 무시하고 `denied`를 그대로 넘겨 게이트가
요청 단계를 건너뛰었다 — 다이얼로그 없이 안내 화면만 뜨던 원인이다. `getStatus()`가 다시 물어볼
수 있는 거부를 `undetermined`(게이트 의미상 "다이얼로그를 띄워야 하는 상태")로 좁힌다. iOS는 한
번 거부하면 `canAskAgain: false`라 이 분기를 타지 않아 기존 동작이 그대로다. 솔로 세션 게이트도
같은 어댑터를 쓰므로 함께 고쳐진다.

게이트 거부 시 동작(2026-08-25 확정, iOS·Android 공통): **입장하지 않고 소셜 홈으로 돌아간다.**
거부여도 입장을 진행하게 두었더니, 네이티브 권한 안내 화면을 닫는 순간 그 아래에 이미 입장된
룸이 드러났다. 룸은 `set-back-lock`으로 뒤로가기를 잠그고 있어 나가기 버튼 말고는 빠져나갈
수단도 없었다(실기기 확인). join도 부르지 않으므로 자리 예약이 잡히지 않는다.

응답을 못 받는 경우의 판단(2026-08-25 확정): 셸이 웹뷰 URL에 `cameraGate=1`을 붙여 이 메시지를
처리할 수 있음을 알리고, 웹은 그 표시로 무응답의 해석을 가른다.

- 표시가 있으면 무응답·타임아웃을 **차단**으로 본다. 권한을 확인하지 못한 채 룸에 들여보내지
  않는다는 정책이고, 응답할 수 있는 셸의 침묵은 그 자체가 비정상이다. 네이티브 핸들러도 게이트
  실행이 실패하면 `granted: false`로 답한다.
- 표시가 없으면 통과시킨다. 이 메시지를 모르는 구버전 앱에서는 응답이 올 수 없고, 원격 웹은
  구버전 앱에도 즉시 배포되므로 여기서 막으면 그 사용자들의 소셜 룸 입장이 통째로 끊긴다.
  `share=1`과 같은 방식이다.
- 브라우저 단독 접속은 브리지가 없어 즉시 통과한다 — 브라우저 자체 권한 프롬프트를 쓰므로
  OS 권한과 기준이 다르고, 차단 대상이 아니다.

범위에서 뺀 것:

- 인셋 전달(티켓 완료 조건의 "하단바 가림") — 2026-08-24 사용자 결정으로 이번 작업에서 제외.
- 전면 카메라 미러 — dev에 이미 구현되어 있다(`LiveRoomEntry`·`LiveRoomSession`·`ClonedTrackPreview`의 `scale-x-[-1]`).
- iOS 소셜 룸 회전 개방 — 회전 브리지의 네이티브 수신은 Android 전용 가드로 둔다.

## 2. 브리지 메시지 확장 (`packages/types/src/bridge.ts`)

| 방향          | 메시지                                    | 용도                                                                     |
| ------------- | ----------------------------------------- | ------------------------------------------------------------------------ |
| 웹 → 네이티브 | `set-orientation { unlocked: boolean }`   | 룸 진입/이탈 시 회전 잠금 제어 요청. `set-back-lock`과 같은 웹 주도 패턴 |
| 웹 → 네이티브 | `request-camera-gate`                     | 룸 입장을 확정하기 전 권한 게이트 실행 요청                              |
| 네이티브 → 웹 | `camera-gate-result { granted: boolean }` | `request-camera-gate` 응답                                               |
| 네이티브 → 웹 | `theme { scheme: "light"                  | "dark" }`                                                                | 앱 실행 중 시스템 테마 변경 통지. Android 전용 발신 |
| 네이티브 → 웹 | `reset-route { path: string }`            | 탭 웹뷰를 탭 루트 경로로 초기화. Android 전용 발신                       |

파서 갱신: 웹 수신은 `apps/web/src/lib/bridge.ts`의 `parseToWebMessage`, 네이티브 수신은 `apps/mobile/lib/webBridge.ts`의 `parseToNativeMessage`. 모르는 메시지를 흘려보내는 기존 규약 덕에 구형 셸 + 신형 웹, 신형 셸 + 구형 웹 조합 모두 오늘 동작으로 물러난다.

## 3. 항목별 설계

### #1 뒤로가기 후 탭 재진입 시 화면 초기화 (Android 전용)

방향 결정(2026-08-24 사용자 승인): 뒤로가기의 홈 이동은 그대로 두고, 떠나는 탭의 웹뷰를 탭 루트로 초기화한다. 웹 히스토리 우선 back 방식은 채택하지 않았다.

- 네이티브: `app/(tabs)/_layout.tsx`에 Android `BackHandler`를 건다. 뒤로가기 시 활성 탭이 홈이 아니면 그 탭의 초기화 신호를 모듈 스토어(`lib/tabBarVisibility.ts`와 같은 패턴)로 흘리고 `false`를 반환해 기본 동작(홈 탭 이동)은 그대로 둔다. `RemoteWebViewHost`가 신호를 구독해 자기 탭 대상이면 `reset-route { path: 자기 탭 루트 }`를 `injectJavaScript`로 주입한다.
- 웹: App 레벨 훅이 `reset-route`를 받아 `navigate(path, { replace: true })`로 이동한다. 현재 `location.search`를 승계해 `userId` 등 셸 계약 쿼리를 유지한다.
- 탭바 탭 전환으로 떠난 경우는 초기화하지 않는다 — 티켓 범위는 뒤로가기 경로뿐이고, iOS의 탭 전환 동작(히스토리 유지)과 통일을 유지한다.
- 세션 계열 화면은 무관하다: 소셜 룸 세션 중에는 `set-back-lock`이 뒤로가기를 이미 삼키고, 솔로 세션은 별도 네이티브 화면이다.

### #2 회전 브리지

- 웹: `apps/web/src/lib/nativeBackGesture.ts`의 기존 훅 옆에 마운트 동안 `set-orientation unlocked: true`, 언마운트에서 `unlocked: false`를 보내는 훅을 추가하고, 룸 라우트(`/social/room/:id`) 수명에 건다. 진입 미리보기 단계부터 룸 전체가 회전 대상이다.
- 네이티브: `lib/nativeBridgeHandler.ts`가 수신해 **Android일 때만** `unlockForSession()` / `lockPortrait()`(`lib/orientation.ts`)를 부른다. iOS는 무시한다 — 완료 조건 "iOS 동작에 변화가 없다"를 지키기 위해서다. 잠금 호출 실패는 기존 `lockSafely`가 삼킨다.
- 문서 세대 주의: 웹뷰 재로드·렌더러 재생성으로 룸 밖 문서가 새로 뜨면 `unlocked: false`를 되돌릴 주체가 없다. `RemoteWebViewHost`가 **새 문서의 로드 시작(`onLoadStart`)**에서 세로 잠금을 복원한다. 로드 종료가 아닌 이유: 웹의 회전 요청은 React effect에서 나가 나머지 리소스 로드보다 먼저 도착할 수 있어, 종료 시점에 복원하면 방금 연 회전을 같은 로드가 되잠근다(2026-08-25 채점 지적).
- 실기기 확인 항목: Android에서 rn-screens `orientation: "portrait"`(`setRequestedOrientation`)와 `expo-screen-orientation`의 호출 순서 경합. 룸 체류 중 네이티브 화면 전환이 없어 문제없을 것으로 보지만 기기에서 확인한다.

### #3 테마 전달 (Android 전용)

방식 결정(2026-08-24 사용자 승인): 초기 로드는 쿼리 파라미터, 실행 중 변경은 브리지 메시지. 알고리즘 반전(forceDark 계열)은 쓰지 않는다.

- 네이티브: `lib/remoteQueryParams.ts`가 Android에서만 `theme=dark|light`를 붙인다. 값은 **최초 마운트 시점으로 고정**한다 — 테마 변경이 URL을 바꾸면 웹뷰가 통째로 재로드되기 때문이다. 실행 중 변경은 `RemoteWebViewHost`가 `Appearance` 변화를 구독해 `theme` 메시지로 주입한다(Android 전용).
- 웹: 부트 시 쿼리를 읽어 `document.documentElement`에 `data-theme` 속성을 설정하고, `theme` 메시지 수신 시 갱신한다.
- 캐시된 쿼리 보정: 쿼리 값은 모듈 캐시된 공용 파라미터에 들어가므로 테마를 바꾼 뒤 처음 여는 탭이나 재로드된 문서는 옛 값으로 시작한다. `RemoteWebViewHost`가 로드 완료마다 현재 `Appearance` 값을 `theme` 메시지로 실어 정정한다(2026-08-25 채점 지적).
- CSS: `src/index.css`에 다크 변수 블록을 `:root[data-theme="dark"]` 셀렉터로 한 벌 더 둔다. 미디어쿼리와 속성 셀렉터는 순수 CSS로 블록을 공유할 수 없어 값이 두 벌이 되므로, 두 블록을 붙여 두고 동기화 주석으로 짝을 명시한다. `data-theme="light"`는 별도 규칙이 필요 없다 — Android 라이트 기기는 속성이 붙어도 라이트 기본값이 그대로고, Android에서는 미디어쿼리가 항상 light로 평가되어 두 블록이 충돌할 조합이 없다.
- 영향 없음 확인: 세션 오버레이(`sessionTheme.ts`)와 온보딩 오버레이(`coachOverlayTheme.ts`)는 다크 고정값 직접 사용이라 무관하다. 웹 소스에 `dark:` Tailwind variant와 `matchMedia` 사용처는 없다(2026-08-24 검색 확인).
- iOS: 파라미터·메시지를 보내지 않는다. `data-theme` 부재 시 기존 미디어쿼리 경로 그대로다.
- `theme` 쿼리는 분석 화이트리스트(`ALLOWED_SEARCH_PARAMS`)에 추가하지 않는다 — 분석에 불필요하고 `sanitizePath`가 걸러낸다.

### #6 소셜 룸 카메라 권한 게이트 (양 플랫폼 공통)

범위 결정(2026-08-24 사용자 승인): 게이트를 iOS에도 공통 적용한다. 근거 — "묻지 않고 자동 거부"는 안드로이드 WebView 특유의 동작이지만, 거부 상태에서 안내 없이 카메라 획득만 실패하는 공백은 iOS에도 있다. 솔로 세션의 `start-session` 게이트가 이미 양 플랫폼 공통이라 동작도 정렬된다.

- 웹: `LiveRoomEntry`가 입장을 확정하기 전에 `request-camera-gate`를 보내고 `camera-gate-result`를 기다린다. `granted: false`면 입장하지 않고 소셜 홈으로 돌아간다(위 "게이트 거부 시 동작"). 무응답 처리는 셸 표시로 가른다(위 "응답을 못 받는 경우의 판단").
- 대기 시간: 표시가 있는 셸은 **사용자가 OS 다이얼로그에 답할 때까지 기다린다**(2분). 네이티브는 사용자 응답 뒤에야 결과를 보내므로 짧게 끊으면 뒤늦게 누른 허용이 버려진다(2026-08-25 채점 지적). 표시가 없는 셸은 3초 뒤 통과로 확정한다 — 응답이 올 수 없는 셸을 가려내는 용도다.
- 네이티브: `handleBridgeMessage`가 `runCameraPermissionGate()`를 실행한다. 통과면 `camera-gate-result { granted: true }` 응답, `"show-denied-guide"`면 `/permission-denied`를 push하고 `granted: false`를 응답한다. 게이트 실행 자체가 실패해도 `granted: false`로 답한다 — 권한을 확인하지 못한 채 입장시키지 않는다.
- 권한 상태 매핑은 위 "권한 상태 매핑 수정" 참고. 이 어댑터는 솔로 세션과 공유한다.
- iOS 영향: 권한이 이미 허용된 경로는 조회만 하고 즉시 통과라 보이는 변화가 없다. 미결정 상태는 게이트 시점에 OS 다이얼로그가 뜨고, 거부 상태는 안내 화면으로 이어진다(iOS는 한 번 거부하면 OS가 다시 묻지 않으므로 재요청 없이 곧장 안내다). 티켓 완료 조건도 이에 맞게 갱신했다.

| `request-camera-gate` | 플랫폼 무관 발신          | 양 플랫폼 공통 게이트 실행                                 |

## 5. 테스트 방침

구체 케이스 목록은 구현 전 테스트 계획 승인 게이트에서 확정한다. 골격:

- `packages/types` 신규 메시지의 양방향 파서 왕복(웹 `parseToWebMessage`, 모바일 `parseToNativeMessage`) — 정상·필드 누락·모르는 타입.
- 네이티브: `handleBridgeMessage`의 `set-orientation` Android 가드, `request-camera-gate` 통과/거부 분기, 뒤로가기 초기화 신호 발행·구독, `RemoteWebViewHost`의 테마 메시지 주입·로드 완료 시 테마 재주입, 로드 시작 시 세로 복원.
- 웹: `reset-route` 수신 내비게이션(쿼리 승계 포함), 테마 부트 적용·메시지 갱신, 회전 훅의 마운트/언마운트 발신, `LiveRoomEntry` 게이트 대기·타임아웃·거부 분기.

## 6. 검증 계획

- 자동: 전체 lint·typecheck·test 실제 실행 결과로 보고.
- 실기기(Android): 뒤로가기 초기화, 룸 회전, 다크모드, 권한 게이트 4건 재현 안 됨 확인.
- 실기기(iOS): 탭 전환·룸 진입·테마·권한 허용 경로에 변화 없음 확인.
