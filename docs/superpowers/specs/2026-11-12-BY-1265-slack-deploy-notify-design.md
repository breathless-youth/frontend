# BY-1265 배포 Slack 알림과 릴리즈 자동 기록 설계

## 왜

지표 담당 팀원이 Amplitude 차트를 관리하면서 다른 팀원이 배포한 일정까지 손으로 기록하고 있었다. 어느 날 무엇이 나갔는지 알아야 수치 변화를 읽을 수 있는데, 그 정보가 GitHub Release, `releases.md`, EAS 대시보드에 흩어져 있었다.
운영 배포가 실패해도 GitHub 화면을 열어 보기 전에는 아무도 몰랐다.

## 목표

- 운영 웹 배포는 시작부터 끝까지 `#배포-알림`의 메시지 하나로 보이고, 실패하면 머지한 사람이 멘션된다.
- 운영 웹 배포와 EAS 스토어 제출은 Amplitude Release로 남아 모든 차트에 표시된다.
- 운영 웹 배포마다 바뀐 Amplitude 이벤트와 속성이 스레드에 올라간다.
- 매주 월요일 09시에 지난주 배포 지표가 기준선과 함께 올라간다.
- 성공 기준: 배포 일정을 손으로 기록하는 일이 0건이 된다.
- 보조 지표는 운영 배포·스토어 제출이 기록되기까지 걸린 시간과 기록이 빠진 건수다. 켠 뒤 2주 동안의 값을 아래 기준값과 비교한다.

| 대상           | 기준값(10/12~11/08)                                                                                   | 목표                                                       |
| -------------- | ----------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| 웹 운영 배포   | 배포가 끝나고 GitHub Release가 게시되기까지 중앙값 2.7시간, 최대 51.8시간, 29건 중 1건은 Release 없음 | 배포가 끝나고 10분 안에 Slack과 Amplitude에 기록, 누락 0건 |
| 앱 스토어 제출 | production 제출 21건 중 4건은 `ios/`·`android/` 태그 없음(로컬 빌드 1건 포함)                         | 24시간 안에 기록, 로컬 빌드 말고는 누락 0건                |

- 기준값은 지금 남아 있는 기록(GitHub Release, git 태그)으로 계산했다. 팀원이 Amplitude에 손으로 남긴 기록은 조회할 수 없어 기준값에 넣지 못했다.
- 실패한 배포에서 다음 실행이 시작되기까지 걸린 시간은 기준 4주 동안 main 배포 실패가 0건이라 비교 기준으로 쓰지 않는다. 주간 보고에는 계속 표시한다.

## 하지 않는 것

- 스테이징(dev) 배포 알림은 보내지 않는다. 하루 6~12번이라 운영 알림이 묻힌다.
- `web/<버전>` 태그와 GitHub Release는 자동으로 만들지 않는다. 지금처럼 릴리즈 PR을 머지할 때 사람이 쓴다.
- Notion 기록은 팀원 개인 페이지라 다루지 않는다.
- 사용자 지표는 백엔드 일일 리포트(BY-456)와 겹쳐 주간 보고에 넣지 않는다.
- 배포가 끝난 뒤에 쓴 릴리즈 노트는 이미 올라간 메시지와 Amplitude Release에 반영하지 않는다. Amplitude Release API에는 수정 기능이 없다.
- 백엔드 저장소 알림과 조직 공용 composite action은 백엔드 티켓에서 다룬다.

## 구조

Slack, Amplitude, GitHub 호출은 모두 루트 `scripts/`의 `.mjs` 스크립트가 `fetch`로 한다. 워크플로 단계는 스크립트를 실행만 한다.
메시지 조립과 비교·계산은 순수 함수로 두고 같은 이름의 `*.test.mjs`로 테스트한다. 지금 CI의 `pnpm test:scripts`가 실행한다.
새 외부 액션과 새 의존성은 쓰지 않는다. 타입스크립트 파서는 루트 devDependency에 이미 있는 `typescript`를 쓴다.

## 운영 웹 배포 알림

### 흐름

1. `deploy` job에서 체크아웃 직후 main일 때만 시작 메시지를 올리고, 메시지 `ts`를 job output으로 넘긴다.
2. 기존 빌드·배포 단계는 바꾸지 않는다.
3. 새 `notify` job이 `needs: deploy`, `if: always() && github.ref_name == 'main'`로 배포가 끝난 뒤 돈다.
4. `notify` job은 `ts`가 있으면 그 메시지를 결과로 고치고, 없으면 결과 메시지를 새로 올린다.
5. 배포가 성공하면 스레드에 릴리즈 노트, PR 목록, 이벤트 변경을 올리고 Amplitude Release를 만든다.
6. 배포가 실패하면 실패한 단계 이름을 적고 머지한 사람을 멘션한다.

### job을 나누는 이유

- Draft Release는 쓰기 권한이 있어야 API에서 보인다.
- `deploy` job은 외부 패키지를 설치하고 빌드하므로 쓰기 권한을 주지 않는다.
- 그래서 `notify` job만 `contents: write`, `actions: read`를 받고, `deploy` job은 지금 권한을 유지한다.
- `notify` job은 `continue-on-error: true`라서 알림이 실패해도 배포 결과가 바뀌지 않는다.
- 이벤트 비교와 PR 목록에 이전 커밋이 필요해 `fetch-depth: 0`으로 체크아웃하고, 타입스크립트 파서를 쓰려고 루트 의존성만 설치한다.

### 기준이 되는 값

- 이번 버전은 배포한 커밋의 `apps/web/package.json` `version`이다.
- 지난 운영 배포는 main에서 마지막으로 성공한 `Deploy web` 실행(이번 실행 제외)의 `head_sha`다. 태그는 사람이 늦게 달 수 있어 쓰지 않는다.
- 걸린 시간과 실패한 단계는 이번 실행의 jobs API에서 `deploy` job의 시작·종료 시각과 `conclusion`이 `failure`인 첫 단계로 구한다.
- 머지한 사람은 `github.actor`다. `SLACK_USER_MAP`에서 Slack 멤버 ID를 찾고, 없으면 `@here`를 쓴다.

### 릴리즈 노트

- Release 목록(Draft 포함)에서 `tag_name`이 `web/<이번 버전>`이고 본문이 비어 있지 않은 것을 찾는다.
- 배포가 끝날 때 한 번만 찾고 기다리지 않는다. 최근 10건은 모두 Draft가 배포 시작 3~9초 전에 만들어져 있었다.
- 본문의 `## 제목`들을 `·`로 이어(모든 노트에 있는 `## 버전`은 뺀다) "주요 변경" 줄을 만든다.
- 노트가 없으면 "주요 변경" 줄 대신 `릴리즈 노트 없음 · PR N건`을 쓴다.

### PR 목록

- 지난 운영 배포 커밋부터 이번 커밋까지의 커밋 중 `Merge pull request #N from <owner>/<branch>` 커밋을 고른다.
- 머지 커밋 본문의 첫 줄을 PR 제목으로 쓴다.
- 브랜치가 `dev`인 릴리즈 PR은 뺀다.

## 이벤트 변경 목록

- 대상 파일은 `apps/web/src/lib/amplitude.ts`다. 이벤트는 모두 이 파일의 `track("이벤트명", {...})`로 보낸다.
- 타입스크립트 파서로 파일을 읽어, 첫 인자가 문자열 리터럴인 `track` 호출만 모은다. 여러 줄에 걸친 호출도 같은 방식으로 읽는다.
- 둘째 인자가 객체 리터럴이면 최상위 키를 속성으로 모은다. 단축 속성(`{ restored }`)도 키로 센다.
- 펼침(`...rest`)이 있으면 그 이벤트의 속성 목록에 `...`을 표시한다. 펼친 내용은 따라가지 않는다.
- 같은 이벤트를 여러 곳에서 보내면 속성을 합친다.
- 지난 운영 배포와 이번 배포의 목록을 비교해 새 이벤트, 삭제된 이벤트, 속성이 추가·삭제된 이벤트를 고른다.
- 속성 값(계산식)이 바뀐 것은 잡지 않는다. 그런 변경은 diff 링크로 확인한다.
- 바뀐 것이 없으면 `📊 이벤트 변경 없음` 한 줄을 올린다.

## Amplitude Release

- `POST https://amplitude.com/api/2/release`를 Basic 인증(API key, secret key)으로 호출한다.
- `chart_visibility`는 `true`로 두어 모든 차트에 표시한다.
- `release_start`는 UTC `yyyy-MM-dd HH:mm:ss` 형식이다.
- 웹: 제목은 `웹 <버전>`, 시각은 배포가 끝난 시각, 설명은 릴리즈 노트 본문이다. 노트가 없으면 PR 제목 목록을 쓴다.
- 앱: 제목은 `iOS <버전> (<빌드번호>)` 또는 `Android <버전> (<빌드번호>)`, 시각은 제출이 끝난 시각, 설명은 제출처와 커밋이다.
- 만들지 못하면 웹은 스레드에 `⚠️ Amplitude Release를 만들지 못했어요: <에러>`를 남긴다. 다시 시도하지 않는다.

## EAS 제출 기록

### 흐름

1. 매일 03시 KST(UTC 18시)에 돈다. 수동 실행도 된다.
2. `apps/mobile`에서 `pnpm dlx eas-cli@27.7.2 submit:list --platform all --json --non-interactive`로 최근 7일 제출을 가져온다.
3. 상태가 `FINISHED`이고 빌드 프로필이 `production`인 제출만 남긴다.
4. 태그 이름은 `ios/<appVersion>-<appBuildVersion>`, `android/<appVersion>-<appBuildVersion>`이다. 지금 손으로 단 태그와 이름 규칙이 같다.
5. 원격에 태그가 이미 있으면 건너뛴다. 같은 빌드를 두 번 제출한 경우도 여기서 걸러진다.
6. 태그가 없으면 Amplitude Release, `gitCommitHash`에 태그 push, Slack 메시지 순서로 처리한다. Amplitude가 실패하면 태그를 달지 않고 다음 날 다시 시도한다. 태그 push가 실패하면 Slack 메시지를 보내지 않고 실패 알림을 올린다.

### 정한 이유

- 팀이 쓰는 `eas-cli` 21에는 `submit:list`가 없다. devDependency를 올리면 팀원의 로컬 빌드 명령이 바뀌므로 이 워크플로에서만 버전을 고정해 실행한다.
- `submit:list`는 Expo 설정 플러그인을 읽어서 의존성 설치가 필요하다.
- Amplitude Release는 고칠 수 없어서 만든 바로 뒤에 태그를 달아 처리 표시를 남긴다. Release가 중복되는 경우는 Release를 만든 뒤 태그 push만 실패한 때로 줄어들고, 이때 실패 알림에 그 가능성을 적는다. 태그를 단 뒤 Slack이 실패하면 다음 날 다시 보내지 않는다.
- 7일을 넘는 제출은 보지 않는다. 처음 켰을 때 예전 제출이 한꺼번에 올라가지 않게 하려는 것이다.

### 처리 표시를 남길 수 없는 제출

- 로컬에서 빌드해 올려 `submittedBuild`가 비어 있는 제출은 버전과 커밋을 알 수 없다.
- 커밋이 원격 저장소에 없는 제출도 태그를 달 수 없다.
- 두 경우 모두 제출이 끝난 지 24시간이 안 된 것만 Slack에 경고를 한 번 올리고, Amplitude Release는 만들지 않는다.
- 크론이 크게 늦게 돌면 경고가 빠지거나 두 번 갈 수 있다. 3개월에 3건 정도라 받아들인다.

## 주간 보고

- 매주 월요일 09시 KST(UTC 월요일 00시)에 지난주 월요일 00시부터 일요일 24시(KST)까지를 계산한다. 수동 실행도 된다.
- 값은 GitHub API와 `eas submit:list` 기록만으로 계산한다.

| 지표             | 정의                                                                               |
| ---------------- | ---------------------------------------------------------------------------------- |
| 운영 웹 배포     | 주 안에 성공한 main `Deploy web` 실행 수                                           |
| 배포 실패율      | main `Deploy web` 실행 중 실패한 비율(취소는 뺀다)                                 |
| PR→운영 리드타임 | PR이 dev에 머지된 시각부터 그 PR을 포함한 운영 배포가 성공한 시각까지의 중앙값     |
| 실패→다음 실행   | 실패한 실행이 끝난 시각부터 다음 `Deploy web` main 실행이 시작된 시각까지의 중앙값 |
| PR CI 실패율     | `pull_request` 이벤트로 돈 `CI` 실행 중 실패한 비율(취소는 뺀다)                   |
| PR CI 평균 시간  | 같은 실행들의 시작부터 끝까지 평균                                                 |

### 기준선

- 구현할 때 같은 스크립트를 `--baseline`으로 로컬에서 한 번 돌려 10/12~11/08 네 주의 값을 계산하고 `release-metrics-baseline.json`에 저장한다.
- 운영 웹 배포와 앱 제출은 주 평균, 나머지는 네 주 기록을 모두 합쳐 계산한다.
- 실행 기록이 보관 기간을 넘어 사라져도 기준선이 바뀌지 않도록 계산 결과를 파일로 남긴다.

## 실패 처리

| 상황                                  | 동작                                                                                                 |
| ------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| 시작 메시지를 못 올림                 | 결과 job이 메시지를 새로 올린다                                                                      |
| Slack이 `ok: false`로 응답            | HTTP 200이어도 오류로 보고 로그와 job 요약에 남긴다                                                  |
| Amplitude Release 생성 실패           | 웹은 스레드에 경고를 남기고 다시 시도하지 않는다                                                     |
| 시크릿·변수가 비어 있음               | 그 알림만 건너뛰고 경고를 남긴다                                                                     |
| `SLACK_USER_MAP`에 머지한 사람이 없음 | `@here`로 멘션한다                                                                                   |
| EAS 제출 하나를 처리하다 실패         | 나머지는 계속 처리하고, 마지막에 job을 실패로 끝내며 Slack에 `⚠️ EAS 기록 실패 · 실행 보기`를 올린다 |
| 주간 보고 계산 실패                   | job을 실패로 끝내고 Slack에 경고를 올린다                                                            |

- 웹 배포 쪽 알림은 배포 결과에 영향을 주지 않는다.
- 크론 두 개는 실패를 숨기지 않는다. 기록이 빠진 날이 바로 드러나야 한다.

## 테스트

### 단위 테스트

- 이벤트 읽기: 한 줄 호출, 여러 줄 호출, 단축 속성, 펼침 표시, 이벤트 이름이 문자열이 아닌 호출 제외, 같은 이벤트의 속성 합치기
- 이벤트 비교: 추가, 삭제, 속성 추가·삭제, 변경 없음
- 릴리즈 노트: `## 제목` 뽑기, 버전으로 찾기(Draft 포함), 빈 본문, 노트 없음
- PR 목록: 머지 커밋에서 번호와 제목 뽑기, `dev` 브랜치 PR 제외
- 메시지: 진행 중, 완료, 실패, 취소, 멘션 짝짓기와 `@here`
- EAS 거르기: 상태, 프로필, 태그 이름, 이미 있는 태그, 로컬 빌드와 원격에 없는 커밋의 24시간 판정, Android 트랙 이름
- 주간 지표: KST 주 경계, 중앙값, 실패율에서 취소 제외, 실패→다음 실행, 실패가 없는 주

### 실제 호출 확인

- 지금 GitHub·EAS 기록으로 `DRY_RUN=1`을 로컬에서 돌려 26.46.2 → 26.46.3 배포 메시지, 11월 EAS 제출, 지난주 지표가 위 문구대로 나오는지 본다.
- Slack은 시험 채널에 실제로 한 번 보낸다.
- Amplitude Release는 실제로 만들면 팀원의 모든 차트에 표시가 생기므로, 시험 프로젝트가 있을 때만 실제로 호출한다.
- `deploy-web.yml`의 `notify` job은 머지 뒤 첫 운영 배포에서 처음 실제로 돈다.
- `schedule`과 `workflow_dispatch`는 main에 있는 파일만 실행되므로, 크론 두 개는 릴리즈 머지 뒤 수동 실행으로 확인한다.
- `ios/*`, `android/*` 태그에 ruleset이 있는지 확인한다. 있으면 Actions 토큰으로 태그를 push할 수 없다.
