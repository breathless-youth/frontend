# BY-1134 하루 경계와 D-Day를 기기 시간대로 계산 설계

- 티켓: BY-1134 (상위 스토리 BY-1132, 짝 BY-1133 BE)
- 날짜: 2026-11-04
- 서버 결정: backend `docs/adr/0042-user-time-zone.md`

## 목표

웹의 날짜 계산을 KST 고정에서 기기 시간대로 바꾸고, 기기 시간대를 서버에 보낸다. 한국 기기에서는 화면과 숫자가 지금과 같다.
랭킹은 한국 시간 그대로 둔다.

## 기기 시간대

- `deviceTimeZone()`은 `Intl.DateTimeFormat().resolvedOptions().timeZone`을 읽는다. 값이 없으면 `Asia/Seoul`을 돌려준다.
- 표시 언어처럼 문서를 연 뒤 바뀌지 않는다고 보고 부를 때마다 읽는다.

## 날짜 키와 하루 경계

- `todayKstDateKey`, `kstDateKey`, `kstDayStartMs`를 기기 시간대 기준 함수로 바꾸고 이름에서 `Kst`를 뺀다.
  - 날짜 키: `Intl.DateTimeFormat("en-CA", { timeZone })`으로 `YYYY-MM-DD`를 만든다.
  - 하루 시작 시각: 그 날짜의 기기 시간대 00:00에 해당하는 epoch ms. `+9시간` 고정 오프셋을 쓰지 않아 서머타임을 처리한다.
- 날짜 키에 24시간을 더하는 계산(`addDaysToDateKey`, 주 차이)은 UTC 자정 키끼리의 계산이라 시간대와 무관해 그대로 둔다.
- 하루 시작 시각에 `DAY_MS`를 더해 다음 날을 구하는 곳(플래너 05시 창, 수동 기록의 다음 날 판단, `daysAgo`)은 다음 날짜
  키의 하루 시작 시각을 구하는 방식으로 바꾼다. 서머타임 전환일에 하루가 23·25시간이기 때문이다.
- 표시 기본 시간대 `STAT_TIME_ZONE`은 기기 시간대로 바꾼다. 수동 기록의 입력칸 시각(`clockOf`)과 구간 계산
  (`spanFromClocks`, 하루 시작 시각)은 반드시 같은 시간대를 써야 한다.

## 랭킹은 KST 유지

- 현재 구간(`currentSlot`), 구간 남은 시간, 메달의 마감 날짜·시각, 랭킹 기록의 연도는 `Asia/Seoul`을 명시해서 계산한다.
  `STAT_TIME_ZONE` 기본값에 기대지 않는다.
- 기기 시간대가 `Asia/Seoul`이 아니면 랭킹 탭의 보드 대신 해외 랭킹 준비 중 안내를 보여 준다. 문구는 `ranking` 카탈로그에
  ko·en을 함께 넣는다. 서버도 이런 사용자를 한국 랭킹에서 뺀다.

## 서버로 보내기

- 세션 제출(`POST /api/study-sessions`)과 수동 기록(`POST`·`PATCH /api/study-sessions/manual`) body에 `timeZone`을 넣는다.
- 홈 화면이 열릴 때 신원이 준비되면 `PATCH .../profile`에 `{ timeZone }`을 보낸다. 같은 문서에서 같은 값을 이미 보냈으면
  다시 보내지 않는다(sessionStorage). 실패해도 화면에 알리지 않는다. 서버는 다음 세션 제출의 `timeZone`으로도 맞춰진다.
- `packages/types`의 요청 타입에 `timeZone?: string`을 더한다.

## 테스트

- vitest 실행 시간대를 `Asia/Seoul`로 고정한다(설정의 `process.env.TZ`). CI가 UTC라 기기 시간대 함수의 기본 결과가 환경마다
  달라지기 때문이다. 기존 KST 단언은 그대로 통과해야 한다.
- 새 날짜 함수는 서울·뉴욕 시간대를 인자로 넘겨 검증하고, 미국 서머타임 전환일(2026-03-08, 2026-11-01)에 하루 길이와 05시
  창을 확인한다.
- 랭킹 함수는 기기 시간대를 뉴욕으로 바꿔도 KST 결과가 같은지 확인한다.

## 서머타임 전환일 처리

- 없는 시각(뉴욕 3월 전환일의 02:30 등)은 건너뛴 만큼 늦은 시각으로 맞춘다(02:30 → 03:30).
- 두 번 오는 시각(11월 전환일의 01:30 등)은 첫 번째 시각으로 읽는다.
- 플래너는 칸을 현지 벽시계로 나눈다. 23시간인 날의 없는 시각 칸은 비어 있고, 25시간인 날의 두 번 온 시각은 같은 칸에 겹쳐 칠한다.
- 알려진 한계: 두 번 오는 시각의 두 번째에 저장된 수동 기록을 열어 시각 입력칸을 고치면 첫 번째 시각으로 1시간 당겨질 수 있다. 1년에 한 시간, 서머타임이 있는 지역에서만 생기고, 고치려면 폼이 몇 번째 시각인지를 따로 기억해야 해서 이번에는 두지 않는다(2026-11-04 결정).

## 범위 밖

- 해외 랭킹, 랭킹 라벨의 현지 시각 변환
- 시간대가 바뀐 과거 기록의 재계산
- 앱 셸(apps/mobile)의 변경. 셸은 KST 계산이 없다.
