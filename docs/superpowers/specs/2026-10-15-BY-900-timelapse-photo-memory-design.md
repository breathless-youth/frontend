# BY-900 타임랩스 사진 메모리·용량 설계

- 티켓: BY-900 `[FE] 타임랩스 iPhone 사진 용량 줄이기` (상위 BY-822)
- 측정 기록과 스크립트: `.superpowers/by900-measure/` (gitignore)
- 설명 페이지: https://claude.ai/artifact/EHbuc5U7y6QAUHaxcaQoTw

## 문제

결과 화면에 들어가거나 최근 타임랩스 목록에서 공유 창을 열면 미리보기 재생과 공유용 영상 만들기가 동시에 돈다. 두 곳이 각각 `listPhotos`(IndexedDB `getAll`)로 사진 바이트를 전부 메모리에 올려서, 같은 사진이 두 벌 올라간다.

- 사진 크기는 비율에 따라 다르다. 카메라는 휴대폰을 세로로 들어도 1280×720 가로 프레임을 주고, 사진은 높이 720 기준으로 가운데를 자른다. 그래서 9:16은 405×720, 16:9는 1280×720이다.
- iPhone 13 mini 16:9 사진은 장당 224KB이고 360장이면 79MB다. 결과 화면 WebContent footprint는 만들기 중앙값 773MB, 최고 979MB(인코딩 첫머리 1초), 대조 약 675MB였다(xctrace Activity Monitor, 3회).
- 티켓 목표인 "iPhone 타임랩스 하나 약 15MB"는 명세 추정치였고 실측과 맞지 않는다.

## 설계

### 저장소 (`timelapseStore.ts`)

`TimelapseStore`에 두 함수를 더하고 `listPhotos`를 지운다.

```ts
/** 한 타임랩스의 사진 번호를 찍은 순서로 준다. 바이트는 담지 않는다. */
photoSeqs(startedAtMs: number): Promise<number[]>;
/** 사진 한 장의 바이트. 그사이 지워졌으면 null이다. */
readPhoto(startedAtMs: number, seq: number): Promise<ArrayBuffer | null>;
```

- `photoSeqs`는 `getAllKeys(photoRange(startedAtMs))`에서 `seq`만 뽑는다. 솎아내기(`thinningDrops`)가 이미 같은 호출을 쓴다.
- `readPhoto`는 `get("photos", [startedAtMs, seq])`이고 한 번 부를 때마다 짧은 읽기 트랜잭션을 연다.
- 커서는 쓰지 않는다. 장 사이에 디코드·인코딩을 기다리면 트랜잭션이 저절로 닫힌다.

### 미리보기 (`timelapseQueries.ts`, `TimelapsePlayer.tsx`, `useTimelapsePlayer.ts`)

- `timelapsePhotosQuery`는 바이트 대신 `photoSeqs` 결과(번호 배열)를 담는다. 몇 KB라 `gcTime: 0`과 "15MB쯤" 주석은 지운다.
- `TimelapsePlayer`는 `photos: readonly number[]`와 `readPhoto: (seq) => Promise<ArrayBuffer | null>`을 받는다. 결과 카드와 공유 다이얼로그는 `(seq) => store.readPhoto(startedAtMs, seq)`를 넘긴다.
- `useTimelapsePlayer`는 앞쪽 몇 장을 풀 차례에 `readPhoto`로 읽고 디코드한다. 결과가 null이거나 디코드에 실패하면 지금처럼 깨진 장으로 표시하고 건너뛴다.
- 결과 카드가 "사진이 있을 때만 보인다"를 판단하는 조건(`photos.data.length > 0`)은 번호 배열로도 그대로 동작한다.

### 영상 만들기 (`timelapseVideo.ts`)

`photoSeqs`로 번호를 받아 돌면서 장마다 `readPhoto` → 디코드 → 그리기 → 인코더에 넣기를 한다. null이면 깨진 사진처럼 건너뛰고, 진행률과 "한 장도 못 그렸으면 decode 실패" 규칙은 그대로 둔다. 디코드할 때 만드는 `new Blob([bytes])`는 한 장 범위 안이라 그대로 둔다.

### 촬영 (`photoFrame.ts`)

`PHOTO_JPEG_QUALITY`를 0.5로 바꾼다. 워커 `convertToBlob`과 메인 스레드 예비 경로가 같은 상수를 쓴다. 읽는 쪽은 품질과 상관이 없어 예전 사진과 섞여도 된다.

## 오류 처리

- 재생이나 영상 만들기 도중 보관 기한 정리나 삭제로 사진이 사라지면 `readPhoto`가 null을 돌려준다. 깨진 사진과 같은 경로로 건너뛴다. 모든 장이 사라지면 영상 만들기는 지금처럼 `decode` 단계 실패로 끝난다.
- IndexedDB 읽기 자체가 실패하면(예외) 재생기는 그 장을 깨진 장으로 처리하고, 영상 만들기는 지금처럼 `encode` 단계 실패로 기록한다.

## 테스트 범위

테스트 목록과 케이스는 5-1에서 따로 승인받는다. 다룰 범위는 다음과 같다.

- 저장소: `photoSeqs` 순서, 바이트 미포함, 다른 타임랩스 제외. `readPhoto` 값과 없는 사진 null.
- 영상 만들기: 사진을 한 번에 읽지 않고 장마다 `readPhoto`를 부르는지, 중간에 사라진 장을 건너뛰는지.
- 재생기: 앞쪽 몇 장만 읽는지, null인 장을 건너뛰는지.
- `listPhotos`를 쓰던 기존 테스트(저장소·기록기·결과 카드·공유 다이얼로그)는 새 함수로 옮긴다.
- 사진 품질 상수 0.5.

## 검증

### 방법

- 16:9 사진 360장을 넣어 두고 최근 타임랩스 목록에서 공유 창을 연다. 대조(영상이 이미 있어 미리보기만)와 만들기(영상 캐시를 지워 미리보기와 영상 만들기가 함께 돎)를 3회씩 잰다.
- 매번 메모리 정리(GC)를 먼저 돌리고, 공유 창을 열기 직전 값을 기준으로 최고값까지 늘어난 양을 본다. A23은 `dumpsys meminfo` 렌더러 PSS, iPhone은 `xctrace` Activity Monitor의 WebContent footprint다.
- 지금 코드는 `apps/web/src/features/timelapse`만 origin/dev로 잠시 되돌려 같은 날, 같은 기기, 같은 사진으로 잰다.

|                             | 대조   | +221MB    | +144MB    | −77MB (−35%)  |
| Galaxy A23                  | 만들기 | +203MB    | +101MB    | −102MB (−50%) |

| 항목                             | 바꾸기 전        | 바꾼 뒤          |
| -------------------------------- | ---------------- | ---------------- |
| iPhone 16:9 사진 한 장           | 224KB (품질 0.8) | 107KB (품질 0.5) |
| iPhone 16:9 타임랩스 하나(360장) | 약 79MB          | 약 38MB          |
| A23 영상 만드는 시간             | 13.8초           | 14.9초           |

- 영상 만드는 시간이 1.1초 늘었다. 사진을 장마다 따로 읽기 때문이고, 영상은 결과 화면이 뜨자마자 뒤에서 만들기 시작하므로 그대로 둔다(2026-10-15 사용자 결정).
- 15MB 목표는 16:9에서 닿지 않았다(약 38MB). 보관 상한은 결정 표대로 유지한다.
- 9:16 사진은 새로 찍어 재지 않았다. 품질 0.5에서의 크기는 같은 비율로 줄어든다고 보고 추정만 했다.
- 10월 13일 측정(결과 화면 다시 불러오기, 인코딩 첫머리 979MB)과는 방법이 달라 절댓값을 비교하지 않는다. 이번 방법에서 바꾼 코드의 iPhone 최고값은 449MB를 넘지 않았다.
- 지금 코드로 잴 때만 12회 중 2회, 회차 도중 WebContent 프로세스가 바뀌었다. JetsamEvent·크래시 기록은 없어 원인은 확정하지 않았다.

## 문서

- 위키 `product/specs/BY-822-타임랩스.md`: 230·231행의 "약 15MB" 근거와 308·309행의 "실측해 다시 확인" 항목을 실측 표와 보관 상한 유지 결정으로 바꾼다. 위키 PR로 따로 낸다.
- ADR은 쓰지 않는다. 저장 위치·형식·정책이 바뀌지 않는다.
