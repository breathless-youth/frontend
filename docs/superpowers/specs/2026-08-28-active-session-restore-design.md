# 진행중 세션 복구 조회 연동 (BY-452)

- 날짜: 2026-08-28
- 티켓: BY-452 [FE] 진행중 세션 복구 조회 연동으로 재접속 시 이어서 공부
- 연관: BY-447(BE 진행 스냅샷 보고와 서버 자동 확정), BY-448(BE 복구 조회 API),
  BY-449(FE 스냅샷 보고 연동, dev 머지 완료), BY-440(재입장 초기화 취급, 이 문서가 대체한다)

## 배경

BY-449로 세션이 진행되는 동안 30초마다 서버에 누적 스냅샷을 보고하게 됐다.
앱이 최종 제출 없이 죽어도 서버가 마지막 스냅샷으로 세션을 자동 확정해서 기록은 남는다.
하지만 웹뷰가 리로드되면 타이머와 시작 시각이 메모리에서 사라져, 사용자는 이어서 공부하지 못하고 처음부터 다시 시작한다.

BY-448이 그 draft를 돌려주는 `GET /api/study-sessions/active`를 열었다.
이 티켓은 그 조회로 세션을 복원해 이어서 공부할 수 있게 한다.
싱글룸과 소셜룸 모두에 적용한다.

## 목표

- 웹뷰가 리로드돼 진행 상태를 잃었을 때 서버에서 받아와 타이머를 이어 붙인다.
- 사용자가 시작 버튼을 눌러 새로 시작하는 경우에는 옛 세션을 이어받지 않는다.
- 옛 세션을 이어받지 않을 때는 그 자리에서 기록으로 확정한다.

## 범위 밖

- 20분 일시정지 자동 종료 정책의 재검토는 별도 티켓으로 뺀다.
- 백그라운드에서 5분 넘게 머물다 돌아왔는데 웹뷰는 살아 있는 경우의 처리는 다루지 않는다.
  서버가 이미 확정한 세션을 클라이언트가 계속 들고 있는 상태이고, 이 문서의 복원 경로와는 다른 구멍이다.
- 백엔드 변경 없음.

## API 규칙

### 복구 조회

`GET /api/study-sessions/active?userId=N`

```json
{
  "startedAt": "2026-08-28T01:00:00Z",
  "reportedAt": "2026-08-28T01:32:00Z",
  "studySec": 1850,
  "focusSec": 1620,
  "events": []
}
```

- 서버가 보관 중인 draft 가운데 마지막 보고가 가장 최근인 1건을 준다.
- `startedAt`은 그 세션의 시작 시각이고 `userId`와 함께 draft의 멱등 키다.
- `reportedAt`은 마지막 스냅샷의 기준 시각이며, 앱이 죽은 시점의 근사값이다.
- `studySec`과 `focusSec`은 그 시점까지의 누적값이다.
- `events`는 그때까지의 비공부 이벤트 전체이며 진행 중이던 이벤트는 `reportedAt`에서 닫혀 있다.
- `404`는 진행중 세션이 없다는 뜻이다.
- `400`은 요청 오류, `409`는 충돌이다.

### 세션 복구 판별·확인

`POST /api/study-sessions/recovery?userId=N`은 남아 있는 세션의 판별과 확정을 서버가 한 번에 한다.

- `200`이면 그 세션을 기록으로 확정하고 확정된 기록을 돌려준다.
- `404`는 확정할 세션이 없다는 뜻이다.

응답 본문은 확정된 기록이지만 마감이 목적이라 웹은 읽지 않는다.
조회한 값을 클라이언트가 되돌려 제출하는 방식은 두 요청 사이에 다른 요청이 끼어들 수 있어 쓰지 않는다.

## 설계

### 신호를 만든다

룸 화면만 보면 사용자가 시작 버튼을 눌러 들어온 것인지 앱이 죽었다 살아난 것인지 구분할 수 없다.
두 경우 모두 화면이 떴다는 사실만 같게 보인다.
`performance` navigation type이나 부팅 경로 같은 브라우저 신호로 맞히는 방법은 플랫폼마다 신호가 달라 예외가 계속 붙는다.

그래서 신호를 추측하지 않고 만든다.
**시작 버튼이 옛 세션을 치우고 들어간다.**
그러면 룸 화면은 흔적만 보면 된다.

- 들어와 보니 옛 세션이 남아 있다면 아무도 안 치웠다는 뜻이고, 정상 입장이 아니라 복원이다.
- 옛 세션이 없다면 방금 시작 버튼이 치웠거나 애초에 없던 것이고, 새 세션이다.

### 1. 시작 지점에서 옛 세션을 마감한다

시작 버튼을 누르면 화면으로 넘어가기 전에 옛 세션을 정리한다.

```
시작 버튼
  → POST /api/study-sessions/recovery
     404 → 옛 세션 없음, 그대로 진행
     200 → 서버가 기록으로 확정하고 draft를 지웠다
  → 화면 이동
```

응답을 확인한 뒤에 화면으로 넘어가야 순서가 확정된다.
요청을 던져 놓고 화면으로 넘어가면 룸 화면의 조회가 마감을 앞지를 수 있다.

**싱글룸은 `requestSessionStart`가 유일한 통로다.**
홈 탭의 집중 시작과 온보딩 가이드 완료가 모두 이 함수를 지난다.
웹뷰 안에서는 웹이 `start-session`만 보내고 네이티브가 세션 웹뷰를 새로 여는데, 마감이 끝난 뒤에 이 메시지를 보내면 세션 웹뷰가 아직 존재하지 않으므로 조회가 마감을 앞지를 수 없다.

함수가 비동기가 되므로 `FocusStartNavigator.startSession`의 반환 타입을 `Promise<void>`로 바꾸고 호출부 두 곳이 `await`한다.
두 곳 모두 이미 async 흐름 안이라 변경이 작다.

**소셜룸은 `roomApi`의 함수를 용도별로 가른다.**

지금 `joinRoom` 하나가 두 가지 다른 일에 쓰이고 있다.
입장 화면 두 곳은 방에 들어가려고 부르고, `LiveRoomEntry`는 이미 들어온 방의 자리 예약을 갱신하려고 부른다.
같은 요청이라 함수를 공유하고 있지만 뜻이 다르다.
마감을 `joinRoom`에 넣으면 자리 갱신에서도 돌아 방금 복원한 세션을 스스로 지운다.

```ts
// 입장. 옛 세션을 마감하고 방에 들어간다.
export async function enterLiveRoom(userId: number, inviteCode: string): Promise<RoomJoinResponse>;

// 자리 갱신. 이미 들어와 있는 방의 예약 TTL과 iceServers를 새로 잡는다.
export async function renewLiveRoomSeat(
  userId: number,
  inviteCode: string,
): Promise<RoomJoinResponse>;
```

마감은 `enterLiveRoom` 안에만 둔다.
나중에 새로운 입장 방식이 생겨도 그 함수를 쓰게 되므로 마감이 저절로 따라온다.
호출부는 초대코드 입력 화면과 방 만들기 화면이 `enterLiveRoom`으로, `LiveRoomEntry`가 `renewLiveRoomSeat`으로 바뀐다.

**마감이 실패하면 한 번만 다시 시도하고, 그래도 안 되면 그대로 진행한다.**
시작을 막지 않는 이유는 세션이 네트워크와 무관하게 돌아야 하기 때문이다.
전체에 4초 상한을 두고, 넘기면 요청을 끊고 화면으로 넘어간다.
마감하지 못한 세션은 5분 뒤 서버가 자동 확정하므로 기록은 사라지지 않는다.

실패한 채로 진행하면 룸 화면의 조회가 옛 세션을 돌려줘 사용자 의도와 달리 이어받을 수 있다.
실패 사실을 룸 화면에 넘겨 조회를 건너뛰게 하는 방법은 쓰지 않는다.
싱글룸은 웹이 화면을 이동시키지 않고 네이티브가 세션 웹뷰를 새로 열기 때문에 라우터 state로 값을 넘길 수 없고, 소셜룸만 되게 만들면 두 룸의 처리가 갈린다.
네트워크가 끊긴 상태라면 룸 화면의 조회도 함께 실패해 새 세션으로 떨어지는 경우가 대부분이라, 남는 구간이 좁다.

### 2. 룸 화면에서 복원한다

룸 화면이 뜨면 조회하고 결과에 따라 갈린다.

```
룸 화면 진입
  → GET /api/study-sessions/active
     200 → 이어받기
     404 → 새 세션
```

조회가 끝나기 전에는 세션 훅을 마운트하지 않는다.
먼저 마운트하고 나중에 값을 갈아끼우면 사용자가 0분에서 32분으로 튀는 것을 보고, 그 사이에 스냅샷 보고가 나갈 수 있다.

새 모듈 `restoreActiveSession.ts`가 조회를 맡는다.
200이면 복원값을, 404면 `null`을 돌려주고, 나머지는 상태를 실은 오류로 던진다.
응답 타입 `ActiveSessionSnapshotResponse`는 Swagger 그대로 `packages/types`에 추가한다.

새 훅 `useActiveSessionRestore.ts`가 진입 게이트를 맡는다.
마운트할 때 한 번 조회하고 `{ settled, restored }`를 돌려준다.
`userId`가 없으면 조회 없이 즉시 결착한다.

### 3. 복원 값을 타이머에 심는다

`events`를 되접어 타임라인을 재구성하지 않는다.
`toStatusEvents`가 집중 구간을 아예 내보내지 않고 1초 미만 구간도 버리기 때문에, 되접은 타임라인은 원본과 어긋난다.
서버가 준 누적값을 그대로 base로 쓰는 편이 정확하다.

복원값이 있으면 세 가지를 바꾼다.

- 세션 시작 시각을 서버가 준 `startedAt`으로 물려받는다.
- 타임라인을 서버가 준 `reportedAt`부터 일시정지 상태로 연다.
- 서버가 준 누적 `studySec`과 `focusSec`을 base로 얹고, 서버가 준 이벤트를 앞에 이어 붙인다.

타임라인을 `reportedAt`부터 일시정지로 여는 것이 이 설계의 핵심이다.
그러면 앱이 꺼져 있던 공백이 저절로 일시정지 구간이 되어 별도 처리가 필요 없다.
공백은 `studySec`에 들어가지 않으므로 기록이 정확하다.
20분 일시정지 자동 종료 시계도 저절로 `reportedAt`을 가리킨다.
서버 검증에 쓰는 클램프도 그대로 맞는다. 상한이 `(지금 − startedAt) − 일시정지 합`인데 공백이 일시정지에 들어가 있어서 base를 얹어도 상한을 넘지 않는다.

화면에 보이는 값, 스냅샷 보고에 실리는 값, 최종 제출에 실리는 값 모두 base를 더한 값을 쓴다.
이벤트는 서버가 준 것 뒤에 지금 타임라인이 만든 것을 이어 붙인다.

복원값이 없으면 지금 동작과 같다. base는 0이고 앞에 붙일 이벤트가 없다.

**연속한 일시정지를 하나로 잇는다.**
크래시 시점에 이미 일시정지 중이었으면 서버가 준 마지막 이벤트가 `reportedAt`에서 끝나는 일시정지다.
거기에 공백 일시정지를 이어 붙이면 일시정지가 2회로 세져 결과 화면이 사용자가 누른 횟수와 어긋난다.
마지막 이벤트가 `reportedAt`에서 끝나는 일시정지면 그 이벤트를 빼고 타임라인을 그 시작 시각부터 연다.

### 4. 진입 지점

**싱글룸은 `RoomPage`를 둘로 나눈다.**
지금 본문은 이름만 `RoomSessionScreen`으로 바꿔 복원값을 받는다.
새 `RoomPage`가 `userId`를 파싱하고 조회를 걸고, 결착될 때까지 어두운 배경을 유지한다.

**소셜룸은 `LiveRoomEntry`의 입장 조건에 하나를 더한다.**
이미 자리 예약 응답을 기다리는 동안 어두운 배경을 띄우고 있어서 사용자가 보는 화면은 바뀌지 않는다.
복원값은 `LiveRoomSession`을 거쳐 세션 훅으로 넘긴다.

**진입 상태는 일시정지다.**
복귀 후 카메라는 끈 채 사용자가 수동으로 재개한다.
소셜룸은 이미 카메라 끔으로 입장하는 정책이라 그대로이고, 싱글룸은 복원일 때만 일시정지로 뜬다.

**복원 사실을 따로 알리지 않는다.**
기존 일시정지 화면의 `측정을 일시정지했어요`와 `다시 시작하면 이어서 측정돼요`가 그대로 뜬다.
누적 시간이 화면에 살아 있고 사용자가 해야 할 일도 같아서 새 문구가 벌어주는 것이 없다.

**소셜룸 발행에는 추가 코드가 없다.**
상대에게 나가는 값이 `focusSec`인데 복원하면 여기에 base가 이미 얹혀 있어서, 마운트 시 1회 발행이 그대로 복원값을 싣는다.

## 데이터 흐름

```text
정상 시작
  시작 버튼 → 마감 404 → 화면 이동 → 조회 404 → 새 세션, 지금과 동일

옛 세션이 남은 채 새로 시작
  시작 버튼 → 마감 200(서버가 기록으로 확정하고 draft 삭제)
           → 화면 이동 → 조회 404 → 새 세션

웹뷰 리로드로 복원
  화면이 그냥 뜸 → 조회 200 → 일시정지로 열고 이어받기
                → 사용자가 재개 → 같은 startedAt으로 스냅샷 보고 재개
                → 종료 시 최종 제출이 옛 기록을 대체해 한 건으로 남는다
```

## 실패 처리

| 지점           | 응답          | 처리                             |
| -------------- | ------------- | -------------------------------- |
| 시작 버튼 마감 | 404           | 그대로 진행                      |
| 시작 버튼 마감 | 200           | 그대로 진행                      |
| 시작 버튼 마감 | 그 외         | 1회 재시도, 실패하면 그대로 진행 |
| 시작 버튼 마감 | 4초 초과      | 요청을 끊고 그대로 진행          |
| 룸 화면 조회   | 200           | 이어받기                         |
| 룸 화면 조회   | 404           | 새 세션                          |
| 룸 화면 조회   | 400, 409      | 새 세션, Sentry에 1회 남긴다     |
| 룸 화면 조회   | 네트워크, 5xx | 1초 간격 2회 재시도 후 새 세션   |

마감이 실패한 채로 룸 화면에 도착하면 조회가 옛 세션을 돌려줘 이어받게 된다.
드문 경우이고 이어받은 값 자체는 실제로 공부한 시간이라 기록이 틀리지는 않는다.

## BY-440 재입장 초기화를 대체한다

BY-440 설계 2절이 재입장을 처음부터 시작과 같게 취급하기로 확정했고, 그에 맞춰 `LiveRoomSession`의 `baseStudySeconds`를 제거하고 입장 시 `studySeconds` 0을 발행하도록 바꿨다.

그 결정의 근거는 다음이었다.

> 기록은 구간별 별도 세션으로 저장된다. 서버 중복 방지가 갱신이 아니라 무시 방식이라 한 건으로 합칠 수 없다. 그런데 룸 화면 시간은 이전 값에 이어 붙어 화면에는 12분, 기록에는 7분처럼 어긋나 보인다.

이번 티켓에서 그 근거가 사라진다.
서버가 준 `startedAt`을 그대로 물려받으므로 최종 제출이 옛 기록을 대체해 한 건으로 남고, 화면과 기록이 어긋나지 않는다.
그래서 재입장 초기화를 되돌리고 이어받기로 바꾼다.

BY-440이 남긴 마운트 시 1회 발행은 그대로 둔다.
복원이면 `focusSec`에 base가 얹혀 있어 복원값이 나가고, 새 세션이면 0이 나가 상대 화면의 잔상이 지워진다.

## 범위 밖 (수용)

- 앱을 완전히 종료했다가 다시 켜서 시작 버튼으로 들어오면 이어받지 않는다.
  시작 버튼이 옛 세션을 마감하기 때문이며 의도한 동작이다.
  기록은 마감으로 저장되므로 사라지지 않는다.
- 마감이 실패한 채로 룸에 도착하면 사용자 의도와 달리 옛 세션을 이어받을 수 있다.
  네트워크가 끊긴 상태라면 룸 화면의 조회도 함께 실패해 새 세션으로 떨어지는 경우가 대부분이라 남는 구간이 좁다.
- 20분 일시정지 자동 종료가 서버 5분 자동 확정과 겹치지 않는다는 점은 확인했다.
  일시정지 중에도 스냅샷 보고는 계속 나가므로 서버는 보고가 끊겼다고 보지 않는다.
  정책 자체의 재검토는 별도 티켓으로 뺀다.

## 테스트 계획 (개요, 상세 목록은 5-0 게이트에서 승인)

### 조회 모듈

- 200 응답을 복원값으로 변환하는 것.
- 404를 `null`로 돌려주는 것.
- 400과 409를 상태를 실은 오류로 던지는 것.

### 마감

- 마감 요청을 한 번만 보내는 것.
- 404를 실패로 보지 않고 그대로 진행하는 것.
- 실패하면 1회 재시도하고 그래도 안 되면 시작을 막지 않고 진행하는 것.
- 응답이 없어도 4초 상한 안에 반환하는 것.
- `renewLiveRoomSeat`은 마감을 부르지 않는 것.
- 마감이 끝난 뒤에 `start-session`이 나가는 것.

### 진입 훅

- 조회가 결착될 때까지 `settled`가 `false`인 것.
- `userId`가 없으면 조회 없이 즉시 결착하는 것.
- 네트워크 실패에서 2회까지 재시도하고 그 뒤 `restored: null`로 결착하는 것.

### 세션 훅

- 복원값이 있으면 `startedAt`을 물려받는 것.
- 타임라인이 `reportedAt`부터 일시정지로 열리는 것.
- 화면 값이 base를 더한 값인 것.
- 스냅샷 보고와 최종 제출이 base를 더한 값과 이어 붙인 이벤트를 싣는 것.
- `reportedAt`에서 끝나는 일시정지가 공백과 하나로 이어지는 것.
- 복원값이 없으면 지금과 동일하게 도는 것.

### 진입 지점

- 싱글룸이 조회 결착 전에는 세션을 마운트하지 않는 것.
- 소셜룸이 조회 결착 전에는 입장하지 않는 것.
- 복원 시 소셜룸 발행값이 base를 더한 값인 것.
