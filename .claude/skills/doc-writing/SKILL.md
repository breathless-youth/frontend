# 문서 작성 규칙

## 공통 문서 작성 규칙 (Jira 티켓 · PR 본문 · 팀 공유 문안)

팀원이 읽는 글은 AI가 쓴 티가 나지 않는 자연스러운 한국어로 작성한다. 한국어 윤문은
**im-not-ai 스킬**(https://github.com/epoko77-ai/im-not-ai)을 사용한다.
설치돼 있으면 반드시 invoke하고, 없으면 그 원칙(AI 문체 제거)을 따른다.

이 규칙은 팀 문서뿐 아니라 **세션 답변 문체, 트러블슈팅 기록, 이해도 퀴즈에도 적용한다**. AI스러운 말투를 쓰지 않고, 금지 용어 표를 지키며, 헷갈리는 표현은 사전을 참고해 자연스러운 우리말로 쓴다. 세션 답변은 매번 im-not-ai를 invoke하지는 않되 이 원칙을 지킨다.

문서 작성은 반드시 Opus 4.8(`claude-opus-4-8`)로 한다.
- 해당 범위: Jira 티켓 본문, PR 본문, 팀 공유 문안, 도식 페이지
- 모델: 세션 모델이 Opus 4.8이 아니면 Opus 4.8 서브에이전트에 작성을 맡긴다. Opus 5는 쓰지 않는다. 더 최신 Opus가 나와도 자동으로 올리지 않고, 바꿀지는 사용자가 정한다.

- 산문형 본문은 과거형으로 쓴다. 이미 끝낸 작업을 서술하므로 "~한다/~된다"가 아니라 "~했다/~됐다"로 맺는다. 완료 조건·체크리스트처럼 개조식으로 나열하는 항목은 예외로 현재형("~된다")을 그대로 쓴다.
- 파일 경로는 웬만하면 적지 않고 파일명만 쓴다. 팀원이 읽는 Jira·PR·팀 문안이 대상이다. 경로가 꼭 필요한 경우(같은 이름 파일이 여러 곳에 있어 구분이 필요하거나, 위치 자체가 설명의 핵심일 때)만 경로를 적는다. 커밋 계획 표·채점 반영 표처럼 사용자가 에디터에서 바로 열어야 하는 내부 표의 절대경로 규칙은 이와 별개로 그대로 둔다.
- 짝대기(— 대시) 사용 금지. 문장을 나누거나 쉼표로 잇는다.
- 불필요한 괄호 부가설명 금지. 괄호 없이는 문장이 성립하지 않는 내용만 남긴다.
- 지나친 한문 표현 금지. 일상어로 풀어 쓴다 ( 예: "이중 가산된다" → "이중으로 더해진다").
- 기술용어의 억지스러운 영→한 직역 금지. 팀이 실제로 쓰는 표현을 따르고, 통용되는 영어 용어는 그대로 둔다 (예: STOMP 재연결을 "스톰프 재접속"처럼 바꾸지 않는다).
- **영어로 직역했을 때 꾸미기만 하는 부사는 쓰지 않는다.** 빼도 뜻이 달라지지 않으면 무조건 뺀다. `조용히`(silently), `단순히`(simply), `그저`(just), `완전히`(completely)가 이에 해당한다. 뜻이 달라지는 자리라면 부사로 때우지 말고 무슨 일이 일어나는지 풀어 쓴다 (예: "조용히 실패한다" → "오류를 내지 않고 실패한다").
- 금지 용어를 쓰지 않는다. AI 번역투 티가 나는 아래 용어는 팀원이 쓰는 자연스러운 말로
  바꾼다. 표는 피드백을 받을 때마다 계속 추가한다.

| 금지 용어 | 대체 예 |
|---|---|
| 배선 | 연결, 연동 |
| 계약 | 명세, 스펙, 규칙 (백엔드와의 "명세 계약" 형태로 자주 새어 나왔다) |
| 굳다, 굳는다 | 맥락에 맞게 바꾼다: 반영되다, 저장되다, 바뀌지 않는다 등 |
| 소음 | 맥락에 맞게 바꾼다: 불필요한 오류 출력, 잡다한 경고, 거슬리는 로그 등 |
| 옮기다 | 변경하다, 바꾸다 |
| 계승 | 맥락에 맞게 바꾼다: 이어받다, 그대로 쓴다, 물려받다 등 |
| 얹다 | 맥락에 맞게 바꾼다: 다시 작업하다, 옮겨 붙이다, 다시 적용하다 등 |
| 조용히, 조용한 | 맥락에 맞게 바꾼다: 알리지 않고, 보고 없이, 티 나지 않게 등 |
| 침묵 | 맥락에 맞게 바꾼다: 아무 반응이 없다, 알림이 오지 않는다 등 |
| 던지다 | 코드의 `throw`를 뜻하면 `throw`라고 쓴다. 그 외에는 맥락에 맞게 바꾼다: 넘기다, 보내다 등 |
| 구멍, 빈 구멍 | 맥락에 맞게 바꾼다: 빠진 부분, 설명되지 않은 부분, 처리되지 않은 경우 등 |
| 마찰 | 맥락에 맞게 바꾼다: 번거로움, 불편, 걸림돌 등 |
| 상상 | 맥락에 맞게 바꾼다: 근거 없는, 명세에 없는, 임의로 만든 등 |
| 기대다, 기댄다 | 맥락에 맞게 바꾼다: 의존한다, ~에 맡긴다 등 |
| ~하지 않을 이유가 없다 | 간결하게 바꾼다: ~해야 한다, ~하는 편이 낫다 등 |
| 변형(variant 직역) | `variant`를 뜻하면 `variant`로 쓴다. "변형"으로 직역하지 않는다 |
| 승격 | 맥락에 맞게 바꾼다: 정식으로 채택하다, 추가하다, 올리다 등 |

### 가독성 규칙

- **들여쓴 불릿을 최소화한다**.
  기본은 깊이 1의 평평한 불릿이다. 묶음이 필요하면 하위 불릿이 아니라 소제목(`###`)으로 가른다.
  들여쓰기는 상위 항목 없이는 뜻이 성립하지 않는 종속 조건에만 쓰고, 그때도 한 단계까지만 들어간다.
- **불릿 하나는 한 가지만 말한다.** "화면 A가 열리고, B가 동작하고, 실패 시 C한다"처럼 길어지면 하위로 쪼개지 말고 같은 층위의 불릿 여러 개로 나눈다.
- **불릿 하나는 반드시 한 문장으로 끝낸다**. 한 불릿에 두 문장을 잇지 않는다. 꼭 필요한 부연설명은 문장 끝 괄호 안에 넣는다.
- **한 섹션의 불릿이 많아지면 소제목으로 가른다.** 계층으로 접지 말고 섹션을 늘리는 방향으로 푼다.
- **코드로 읽혀야 하는 것은 전부 백틱으로 감싼다.** 파일 경로, 함수·타입·변수명, API 경로, 쿼리 파라미터, 브랜치명, 커밋 해시, 에러 코드, 화면에 그대로 나가는 문구가 대상이다. 여러 줄 요청·응답 예시는 펜스 코드 블록(```)을 쓴다.
- **한 층위 안에서 개조식과 문장을 섞지 않는다.** 평평한 불릿은 완결된 문장("~한다", "~된다")을 기본으로 쓰고, 개조식은 소제목이 맡는다.

예시 (완료 조건 한 절):

```markdown
### 초대코드 입력 화면

* 4칸 숫자 입력이 동작하고, 4자리가 채워져야 `참여하기` 버튼이 활성화된다.
* 없는 코드는 `코드를 다시 확인해 주세요`를 인라인으로 보여주고 입력 화면을 유지한다.
* 정원 초과는 `방이 가득 찼어요`를 인라인으로 보여준다.
* 앞자리가 0인 코드도 4자리 그대로 전송된다.
```

### 코드 주석 규칙

주석은 코드만으로 알 수 없는 것을 설명할 때만 남긴다. 위 공통 문서 작성 규칙(자연스러운 한국어, 금지 용어, 꾸미기만 하는 부사 금지, 가독성 규칙)을 주석에도 그대로 적용한다. 간단한 설명과 "왜"에만 충실하고, 그 밖의 맥락은 적지 않는다.

- **작성 기준**
  - 복잡한 로직 위주로 작성한다. 읽으면 아는 코드에 주석을 달지 않는다.
  - "무엇"이 아니라 **"왜"에 집중한다** — 이 방식을 택한 이유, 지키는 제약, 깨지면 생기는 일.
- **컴포넌트·함수 대표 주석 포맷**
  - 첫 줄은 그 컴포넌트·함수를 대표하는 설명을 명사형으로 쓴다.
  - 대표 설명 뒤로 한 줄을 띄우고 세부 설명을 시작한다.
  - 세부 설명에서 새 문장을 쓸 때마다 그 앞에 한 줄을 띄운다. 한 문장이 길어 줄바꿈만 하는 것은 해당하지 않는다.

  ```ts
  /**
   * 24시간 타임테이블
   *
   * 2분 720칸을 10분 6칸씩 묶어 24행 × 6칸으로 그린다.
   *
   * 칸 색은 전부 토큰이라 라이트·다크가 자동으로 바뀐다.
   */
  ```
- **금지**
  - 마크다운 문법: 제목(`##`), 굵은 글씨(`**`), 표 등을 주석 안에 쓰지 않는다.
  - 티켓 번호: `BY-123` 같은 식별자를 주석에 적지 않는다. 출처는 git blame이 안다.
  - 봇 리뷰·채점 리뷰 언급: "봇 리뷰 반영", "codex 채점 지적" 같은 출처 표기를 남기지 않는다. 반영한 내용만 적는다.
  - 디자인 넘버링: `S4 화면`, `V1.4` 같은 Figma 시안 번호를 적지 않는다. 시안은 바뀌고 번호는 코드에 남아 낡는다.
  - 구체적인 디자인 설명: 색·간격 수치 같은 디자인 세부는 꼭 필요할 때만 적는다. 이유를 설명하는 데 필요 없으면 뺀다.
  - 불필요한 괄호 설명: `(명세)`, `(확정)` 같은 괄호 부가를 붙이지 않는다.

### PR 본문

PR 본문은 리뷰어가 3분 안에 읽고 판단할 수 있어야 한다. 순서는 왜 → 무엇 → 증거다.

- **배경은 왜에서 시작하고 5문장 안으로 끝낸다.** 긴 근거는 ADR이나 Notion 링크로 뺀다.
- **변경은 불릿으로 적는다.** 파일 나열이 아니라 동작이 어떻게 달라졌는지 쓴다.
- **주장 대신 증거를 둔다.** 버그는 입력·지금 결과·고친 결과를 코드로, UI는 Before/After 표로, 성능은 main과 브랜치의 수치로 보인다.
- **CI가 검증하는 출력은 붙이지 않는다.** lint·typecheck·test 결과는 CI가 돌린다. 벤치마크처럼 CI가 안 도는 것만 붙인다.
- **범위 밖과 후속을 적는다.** 일부러 안 한 것과 다음에 할 것을 밝혀 리뷰어가 빠진 것을 묻지 않게 한다.
- **리뷰 포인트에는 이유를 붙인다.** "여기 봐 달라"가 아니라 왜 그 선택을 했고 무엇이 걸리는지 쓴다.
- **대가가 있으면 적는다.** 트레이드오프를 숨기지 않는다.
- **초안은 AI가 써도 본문의 책임은 사람에게 있다.** 올린 뒤 웹에서 직접 읽고 고친다.
